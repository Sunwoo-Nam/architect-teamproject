## 1. 이 PoC가 확인하려는 것

안 1의 구조가 성립하려면 다음 4가지가 실제로 동작해야 한다. 각각이 검증 대상이다.

| # | 확인할 명제 | 실패하면 |
|---|---|---|
| V1 | CandidateSpace Provider가 전수 열거 없이 후보를 공급해도, 전수 열거 방식과 같은 합의에 도달한다 | 메모리 상한과 정확도를 동시에 만족한다는 전제가 무너진다 |
| V2 | constraint hint를 predicate로 변환해 후보 공간을 좁히면, 실제로 생성 후보 수와 라운드 수가 줄어든다 | hint를 OOM 대책으로 쓴다는 raw.md 14행의 전제가 무너진다 |
| V3 | 단계 분리 + 잠정 합의 + backtracking이 단일 결합 협상보다 메모리에서 유리하면서, 계획 최적성 손실이 측정 가능한 범위 안에 있다 | 안 1 §4 말미의 보완 주장이 근거를 잃는다 |
| V4 | 두 단말의 계획 상태를 분리해도 잠정 합의와 재협상이 일관되게 동작한다 | 안 1에 프로토콜 정의가 빠져 있다는 것이 확인된다 |

V4는 안 1에 정의가 없는 항목이다. 본 PoC에서 가장 늦게 다루지만, 결과의 중요도는 가장 높을 수 있다.

## 2. dp02 PoC 재사용 판단

`poc/dp02-a2a-message-hints`의 코드를 검토한 결과다. **본 설계에 맞는 것만 가져오고, 맞지 않는 것은 새로 만든다.**

### 2.1 가져다 쓸 것

| 대상 | 이유 |
|---|---|
| `models.py`의 `IssueSpec`, `HardConstraint`, `ConcessionPolicy`, `PrivateProfile` | 협상 1단계 내부의 표현으로 그대로 유효하다 |
| `utility.py` 전체 | 선형 가법 효용, hard constraint 판정, 선형 양보 threshold. 단계 단위로 그대로 성립한다 |
| `negmas_preferences.py`의 `LinearAdditiveUtilityFunction` + `UFunConstraint` 구성 방식 | 안 1 §5의 "`UFunConstraint`는 생성 후 방어적 검증에 사용" 방침과 일치한다 |
| `hints.py`의 `fixed`/`relaxable` 어휘와 `constraint_hint_valid()` 검증 규칙 | 어휘와 스키마 검증 규칙 자체는 raw.md 15행과 일치한다 |
| `validators.py` | outcome·hint 유효성 검증 패턴 |
| `scenario_loader.py` | YAML 시나리오 로딩 패턴 |
| `batch_runner.py`, `bias_audit.py`의 실행·감사 패턴 | 배치 실행과 생성 축 균형 감사 방식 |

### 2.2 참고만 하고 새로 만들 것

| 대상 | 이유 |
|---|---|
| `scenario_generator.py` | 축 분리와 pairwise 균형 설계는 참고한다. 그러나 본 PoC는 **단계 수·바인딩 강도**라는 새 축이 필요하므로 재작성한다 |
| `metrics.py` | 집계 구조는 참고한다. 지표 자체는 NegMAS 제공 지표로 교체한다(§2.3) |

### 2.3 쓰지 않을 것

| 대상 | 쓰지 않는 이유 |
|---|---|
| `outcome_space.py`의 `enumerate_outcomes()` | `tuple(product(*value_lists))`로 곱집합 전체를 실체화한다. CandidateSpace Provider가 대체하는 대상 그 자체다 |
| `negotiators.py`의 `_candidate_outcomes()` | 매 라운드 전체 공간을 재열거한다. 안 1의 lazy 공급과 정면으로 배치된다 |
| `hints.py`의 `opponent_constraint_hint_fit()`과 `_proposal_score()`의 가중치 경로 | hint를 정렬 가중치(0.15)로만 반영한다. 후보 집합이 줄지 않아 안 1 §5의 공간 절단과 다르다 |
| `models.py`의 `ExperimentGroup`(A1/A2/A3) | dp02의 실험군 구분이다. 본 PoC의 실험군은 다르다 |
| `metrics.py`의 `pareto_dominated`, `pareto_joint_gap` 자체 계산 | NegMAS `calc_outcome_optimality()`로 교체한다 |

## 3. 공통 전제

| 항목 | 결정 |
|---|---|
| Python | 3.12 |
| NegMAS | `negmas==0.15.7` (dp02와 동일 버전 고정) |
| 협상 프로토콜 | 런타임은 `SAOMechanism`. TAU는 Stage 5의 오프라인 기준선으로만 사용 |

| 가상환경 | `poc/co-planning/.venv` 별도 생성. dp02 venv를 공유하지 않는다 |

## 4. 단계별 계획

각 단계는 **진입 조건 → 산출물 → 종료 판정**으로 기술한다. 종료 판정을 통과하지 못하면 다음 단계로 넘어가지 않는다.

### Stage 1 — 단일 단계 협상 커널과 CandidateSpace Provider

**목적:** V1 검증. 전수 열거 없이 협상이 성립하는지 확인한다.

**진입 조건:** 배치 크기 K의 초기값 결정. (단말 메모리 예산이 아직 없으므로 임시값으로 시작하고 Stage 5에서 재산정한다)

**산출물**

| 모듈 | 역할 |
|---|---|
| `models.py` | dp02에서 이식한 `IssueSpec`·`PrivateProfile` 등 + 본 PoC용 `StageSpec` |
| `effective_space.py` | 로컬 hard constraint를 반영한 EffectiveOutcomeSpace 정의. 값 목록만 보관하고 곱집합을 만들지 않는다 |
| `candidate_space.py` | `next_batch(limit, constraints, exclusions, context)`. 내부는 generator 기반. 호출 간 상태를 유지해 중복을 내지 않는다 |
| `negotiators.py` | `SAONegotiator` 상속. `propose()`/`respond()`가 provider를 통해서만 후보에 접근한다 |
| `runner.py`, `logging.py` | 단일 단계 실행과 구조화 로그 |

**종료 판정**

1. 소형 시나리오(4 issue × 5 값 = 625)에서 dp02의 전수 열거 negotiator와 **합의 결과가 일치**한다 — provider가 후보를 잃지 않음을 증명한다
2. 동시 보관 후보 수가 항상 K × 라운드당 배치 요청 횟수 상한 이하임이 계측된다
3. 대형 시나리오(5 issue × 16 값 = 1,048,576)에서 dp02 방식은 peak 메모리가 예산(50MB)을 초과하고, provider 방식은 초과하지 않는다

판정 1은 dp02 negotiator가 실제로 실행되어야 하므로 소형 시나리오를 쓴다. 판정 3은 dp02 방식이 판정선을 넘어야 비교가 성립하므로 대형 시나리오를 쓴다. 3항이 raw.md 13행의 OOM 주장을 실증하는 실험이다.

세부 계약은 [01-Stage1-구현-계약.md](01-Stage1-구현-계약.md)에 있다.

### Stage 2 — constraint hint의 공간 절단

**목적:** V2 검증. hint가 정렬 보정이 아니라 공간 절단으로 동작하게 한다.

**진입 조건:** 다음 2건 확정 필요.
- fixed hint의 철회 절차 유무 (세션 내 단조인가, 철회 가능한가)
- N자에서 동일 issue에 상이한 fixed가 올 때의 처리 — 2자 단계에서는 발생하지 않으므로 Stage 6까지 유예 가능

**산출물**

| 모듈 | 역할 |
|---|---|
| `hints.py` | dp02의 `fixed`/`relaxable` 어휘·검증 이식 + `session`·`stage`·`actor`·`base offer`·`revision` 필드 추가 |
| `hint_predicate.py` | `fixed` → `issue == offered value` predicate 변환 |
| `effective_space.py` (확장) | `LocalCandidateSpace ∩ active fixed predicates` 계산. 원본 OutcomeSpace는 수정하지 않는다 |
| `negotiators.py` (확장) | 수신 hint를 provider의 `constraints` 인자로 전달. **정렬 가중치 경로는 만들지 않는다** |

**종료 판정**

1. hint 수신 후 provider가 생성하는 후보 수가 감소한다 (계측값으로 제시)
2. hint 있음/없음 조건에서 peak 후보 보관량과 라운드 수를 비교한 표가 나온다
3. 교집합이 공집합인 시나리오에서 `INFEASIBLE` 거절이 발생하고 충돌 issue가 기록된다

### Stage 3 — PlanGraph 2단계 실행

**목적:** 바인딩을 통한 단계 연결이 동작하는지 확인한다. 시나리오는 영화 → 식사.

**진입 조건:** fixed hint의 유효 범위 확정 — 해당 단계에서만 유효한가, 후속 단계로 승계되는가. 승계한다면 어떤 조건에서 무효화되는가.

**산출물**

| 모듈 | 역할 |
|---|---|
| `plan.py` | `PlanGraph`, `StageSpec`, `Binding`, `StageAgreement` 정의 |
| `compiler.py` | (노드 의제 + 상위 합의 + 바인딩 + 로컬 컨텍스트) → EffectiveOutcomeSpace + ufun |
| `orchestrator.py` | 단계 순차 실행, 합의를 `TENTATIVE`로 저장, 후속 단계에 전달 |
| `scenarios/movie_dinner.yaml` | 2단계 시나리오 1건 |

**종료 판정**

1. 영화 단계 합의 후 식사 단계의 EffectiveOutcomeSpace 크기가 실제로 감소한다 (전/후 수치)
2. 두 단계 모두 합의에 도달한다
3. 바인딩 규칙을 바꾸면 하위 공간이 그에 맞게 바뀐다 (규칙이 데이터로 동작함을 확인)

### Stage 4 — backtracking과 no-good

**목적:** V3의 전반부. 후속 단계 실패 시 선행 단계로 되돌아가는 경로를 만든다.

**진입 조건:** backtracking 상한값 결정.

**산출물**

| 모듈 | 역할 |
|---|---|
| `plan_state.py` | 단계 상태(`TENTATIVE`/`COMMITTED`/`INFEASIBLE`), revision, no-good 기록 |
| `orchestrator.py` (확장) | 실패 조합을 no-good으로 기록하고 가장 가까운 선행 단계로 복귀. 재협상 시 이전 합의를 `exclusions`로 전달 |
| `scenarios/` | 하위 단계가 반드시 결렬되도록 설계한 시나리오 |

**설계 고정 사항:** no-good은 **로컬 기록으로 한정한다.** 상대에게 전송하면 fixed/relaxable보다 훨씬 많은 선호 정보가 나가고, 누적 시 상대 Utility Function 역추론이 가능해진다. 전송이 필요하다는 판단이 나오면 별도 항목으로 분리해 다룬다.

**종료 판정**

1. 의도적 결렬 시나리오에서 backtracking이 발생하고 최종 합의에 도달한다
2. backtracking 없이 실행한 경우와 계획 최적성을 비교한 수치가 나온다 — 안 1 §4 말미의 보완 주장을 직접 검증한다
3. 상한 초과 시 제약을 임의 완화하지 않고 사용자 결정 요청 지점에서 정지한다

---

### Stage 5 — 정확도 측정 하네스

**목적:** V3의 후반부. 안 1 §6의 지표를 실제로 계산한다.

**산출물**

| 모듈 | 역할 |
|---|---|
| `optimality.py` | `calc_scenario_stats` → `calc_outcome_distances` → `estimate_max_dist` → `calc_outcome_optimality` 파이프라인 |
| `plan_optimality.py` | 단계 결합 공간을 구성해 계획 최적성 계산 (소규모 시나리오 전용) |
| `baselines.py` | 손실 원인 분해용 3회 실행 — SAO@운영 `n_steps`, SAO@큰 `n_steps`, TAU |
| `metrics.py` | 집계·요약 |

**종료 판정**

1. 소규모 oracle 시나리오에서 단계 최적성과 계획 최적성이 계산된다
2. 3회 실행의 차이로 "라운드 상한 손실"과 "전략 손실"이 분리되어 나온다
3. 계측된 결과로 Stage 1의 K 초기값을 재산정한다

**위험:** TAU는 후보 집합 크기에 비례해 라운드가 늘고 메커니즘이 모든 제안을 누적 보관한다(`gb/mechanisms/tau.py`의 `_offers`·`_acceptances`·`_proposals`). 오프라인이라도 시나리오 크기를 작게 잡아야 한다. TAU가 CandidateSpace Provider와 결합 가능한지(고유 제안 요구를 `exclusions`로 만족시킬 수 있는지)를 이 단계에서 먼저 확인한다.

### Stage 6 — 시나리오 생성기와 N자 확장

**목적:** 단일 시나리오 관찰을 매트릭스 측정으로 확장한다.

**산출물**

| 모듈 | 역할 |
|---|---|
| `scenario_generator.py` | 축: 단계 수 / 단계당 issue 수 / 바인딩 강도 / 참여자 수 / 난이도 |
| `bias_audit.py` | 축 간 pairwise 균형 감사 |

**진입 조건:** N자에서 동일 issue에 상이한 fixed가 올 때의 처리 확정 (Stage 2에서 유예한 항목)

**종료 판정**

1. 축 간 균형이 감사로 확인된다
2. 3자·4자 시나리오에서 Stage 1~4의 동작이 유지된다
3. 난이도(`opposition_level`)를 통제 변수로 둔 결과 표가 나온다

### Stage 7 — 계획 상태 분리

**목적:** V4 검증. **안 1에 정의가 없는 부분이므로, 이 단계의 산출물은 코드보다 설계 발견이 중요하다.**

Stage 1~6은 단일 프로세스에서 계획 상태를 공유하므로, 잠정 합의의 양자 동기화 문제가 드러나지 않는다. 이 단계에서 각 참여자의 `PlanState`를 분리하고 메시지로만 동기화한다.

**확인할 상황**

| 상황 | 확인 내용 |
|---|---|
| 한쪽이 `TENTATIVE`, 다른 쪽이 `COMMITTED` | 상태 불일치가 검출되는가 |
| 재협상 요청을 상대가 거부 | 요청 측이 어떤 상태로 남는가 |
| 양쪽이 동시에 다른 단계에서 backtracking 시작 | 교착 또는 무한 반복이 발생하는가 |
| backtracking 상한 초과 후 양측 사용자가 서로 다른 결정 | 계획이 갈라지는가 |

**종료 판정**

1. 위 4가지 상황에서 시스템이 무엇을 하는지 관찰 결과가 나온다
2. 안 1에 추가해야 할 프로토콜 항목 목록이 도출된다

---

### Stage 8 — LLM 기반 PlanGraph 생성

**목적:** raw.md 12행의 "다양한 co-planning 시나리오 확장성"을 확인한다.

이 항목만은 결정론 실험으로 답이 나오지 않는다. "사전 정의 템플릿으로 새 시나리오를 커버할 수 있는가"는 템플릿을 추가해 보면 확인되지만, "LLM이 생성한 PlanGraph가 자원 상한과 어휘 제약을 지키는가"는 LLM을 넣어야만 확인된다.

이 시스템에서 LLM이 관여할 지점은 네 곳이며, 본 단계가 다루는 것은 두 번째 하나다.

| 지점 | 본 PoC와의 관계 |
|---|---|
| IDS Intent → PlanningIntent 변환 | IDS는 본 PoC의 입력이므로 범위 밖 |
| **PlanGraph·issue 어휘 동적 생성** | **본 단계의 대상** |
| 사용자 선호 → Utility Function 유도 | §6에서 전제로 제외한 부분 |
| 협상 전략(`propose`/`respond`) | 불필요. raw.md 15행이 와이어를 `offer + issue별 fixed/relaxable`로 규정하므로 협상 메시지에 LLM이 개입할 여지가 없다 |

**진입 조건:** V1~V3 확인 완료. 구조가 성립하지 않은 상태에서 LLM을 얹으면 무엇이 실패했는지 구분되지 않는다.

**측정 항목**

| 항목 | 의미 |
|---|---|
| 생성 PlanGraph의 스키마 준수율 | 노드·간선·바인딩이 정의된 형태를 지키는가 |
| issue 어휘 크기 위반율 | 생성된 어휘가 세션 컴파일러의 공간 상한을 넘기는 비율 |
| 민감 어휘 생성 건수 | 값 목록에 사유·질환·신원이 직접 들어간 건수 |
| 바인딩 정합성 | 상위 단계에 없는 issue를 하위 바인딩이 참조하는 오류 |
| 결정론 템플릿 대비 계획 최적성 | 같은 과제를 사전 정의 템플릿으로 처리했을 때와 비교 |

**종료 판정**

1. 위 5개 항목의 측정값이 나온다
2. 어휘 크기·민감도 검증을 생성 측(프롬프트 제약)과 컴파일러 측(거부) 중 어디에 두어야 하는지 판단 근거가 나온다
