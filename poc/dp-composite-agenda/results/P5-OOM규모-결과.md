# P5 결과 — full이 OOM하는 규모에서 seq vs pool 비교

> 측정: S11(하루 풀 플랜)을 축 수·축당 값으로 키워 **최대 10축×10값 = 100억 조합**까지.
> 각 규모에서 pool·seq를 시드 20개로 돌려 메모리·합의율·합의 품질을 비교. full은 실측
> 가능한 하한(≤977만 조합)까지 직접 돌리고 그 위는 외삽. 원자료: `oom_stress.jsonl`.
> 재현: `.venv/bin/python scripts/run_oom_stress.py --seeds 20`

## 왜 FC 달성률 대신 "진짜 효용 짝비교"인가

이 규모에선 FC 달성률(U(합의)÷U(x\*))을 쓸 수 없다 — x\*를 구하려면 100억 개 전수열거가
필요한데 그게 바로 여기서 불가능한 것이다(오라클 한도 200,000). 대신 각 전략이 **실제로
낸 합의 하나의 진짜 전체 효용**을 판정기의 봉인 프로파일로 직접 계산해(점 하나 평가라 공간
크기와 무관), 같은 시드에서 pool과 seq를 짝지어 비교한다. 정규화용 x\*만 빠질 뿐 **우열과
격차는 정확히** 잰다.

## 1. 메모리·시간 — full은 못 돌고, 두 안은 산다 (핵심)

| 규모 | 조합 수 S | **full** (peak / 시간) | pool peak | seq peak |
|---|--:|--:|--:|--:|
| 6축×5 | 15,625 | 0.2MB / 0.2s (실측) | 77KiB | 122KiB |
| 8축×5 | 390,625 | 3.1MB / 4.1s (실측) | 99KiB | 131KiB |
| 10축×5 | 9,765,625 | **69MB / 108s** (실측) | 134KiB | 152KiB |
| 10축×8 | 1.07e9 | ~7GB / **3.3시간** (외삽) | 167KiB | 154KiB |
| **10축×10** | **1e10** | **~69GB / 30.8시간** (외삽) | **169KiB** | **152KiB** |

- **pool·seq는 100억 조합에서도 ~150–170KiB**로 평평하다. 공간이 64만 배 커져도 메모리가
  사실상 그대로다(전수열거를 안 하니까). 협상 자체도 60–75ms에 끝난다.
- **full의 진짜 벽은 시간이다.** full 메모리는 유효 후보 수에 비례(공간 전체가 아니라
  membership 하드로 걸러진 후보만 물질화)라 외삽이 근사적이지만, **시간은 전수순회라 S에
  정확히 정비례**한다. 977만 조합에서 이미 108초가 걸렸고, 100억이면 **약 31시간**이다.
  메모리(~69GB)로 죽지 않더라도 시간으로 실행 불가다. 온디바이스(모바일) 기준으론 둘 다 아웃.
- 977만 조합은 full이 **완주는 했다**(69MB/108s). 즉 "full은 무조건 크래시"가 아니라
  "**쓸 수 없을 만큼 느려지고 무거워진다**"가 정확한 실측 결론이다.

## 2. 합의율 — 고차원에서 seq가 무너진다 (새 발견)

| 규모 | pool 합의율 | **seq 합의율** |
|---|:--:|:--:|
| 6축×5 | 100% | 100% |
| 8축×5 | 100% | 80% |
| 10축×5 | 100% | **65%** |
| 10축×8 | 100% | **65%** |
| 10축×10 | 100% | 85% |

**pool은 전 규모에서 100% 합의**한다. seq는 축이 늘수록 합의율이 65~85%로 떨어진다 —
1/3 가까이 **결렬(약속을 못 잡음)** 한다. 원인은 seq의 구조다: 축을 하나씩 확정하며
낙관적 완성 하한으로 거르고, 막히면 백트랙하는데 **상한이 2회**뿐이다. 축이 많아지면 앞 축의
이른 확정이 뒤 축을 막는 경우가 늘고, 2회 백트랙으로는 못 빠져나와 결렬한다.

이는 P4에서 seq의 **강점**이었던 "축별 커밋(중단 시 앞 축 보존)"의 **정확한 이면**이다 —
축별로 커밋해 복구는 싸지만, 그 순차·조기확정 구조가 고차원에서 **취약**해진다. pool은 원본
공간 단일 세션에서 압축 풀 + deepening으로 협상해 결렬 없이 합의에 도달한다.

> **주의 — threshold 밑 수락은 합의율에서 빼지 않는다.** 성립한 합의 중 진짜 효용이 자기
> threshold(0.4) 밑인 건("threshold 밑 수락")이 노이즈 전제에서 몇 건 있다(pool·seq 각 ~20건
> 중 1건, 10축×8의 pool만 5건). 이는 에이전트가 부분 정보(agent_view)로 threshold를 재다 생기는
> **별개의 무결성 항목**이지 "합의 실패"가 아니므로, 합의율(딜 성사 여부)과 **직교**한다. 따라서
> 위 합의율은 원시값 그대로 두고, threshold 밑 수락은 §6에서 별도로 센다. (§6 완벽 정보 전제에선
> 뷰=진실이라 이 오수락이 0이 된다.)

## 3. 합의 품질 — pool ≥ seq (짝비교)

| 규모 | pool 효용µ | seq 효용µ | pool−seq (짝, 진짜효용합) | pool 승 |
|---|--:|--:|--:|:--:|
| 6축×5 | 1.433 | 1.422 | +0.011 [−0.090, +0.112] | 10/20 |
| 8축×5 | 1.273 | 1.141 | **+0.151 [+0.047, +0.255]** | 11/16 |
| 10축×5 | 1.279 | 1.256 | +0.082 [−0.026, +0.189] | 7/13 |
| 10축×8 | 1.180 | 1.117 | +0.051 [−0.050, +0.152] | 7/13 |
| 10축×10 | 1.285 | 1.210 | +0.087 [−0.034, +0.209] | 11/17 |

- **모든 규모에서 pool의 평균 효용이 seq 이상**이고, 짝비교 평균차가 전부 양수다. 8축×5는
  95% CI가 0을 넘어 **유의**하게 pool 우세, 나머지는 방향은 pool이지만 CI가 0을 포함(짝 표본이
  적어 — seq 결렬로 짝 성립 시드가 줄어듦).
- **이 짝비교는 오히려 seq에 유리하게 편향**돼 있다: 양쪽 다 합의한 시드만 비교하므로,
  seq가 결렬한 **어려운 시드(seq가 못 푼 것)** 는 애초에 빠진다. 그걸 감안하면 실질 격차는
  표의 숫자보다 크다.

## 4. 종합 — 이 측정이 답한 것

**"full이 OOM하는 규모(최대 100억 조합)에서 두 설계안은 어떻게 동작하는가?"**

1. **둘 다 산다.** pool·seq 모두 ~150KiB / 60ms로 완주. full은 31시간·수십 GB로 실행 불가.
   조합 폭발(이 프로젝트의 근본 문제)을 두 안 다 흡수함을 **100억 규모에서 실증**했다.
2. **그 규모에서 pool이 seq보다 낫다.** ① 합의율 100% vs 65~85%(seq는 고차원에서 자주 결렬),
   ② 합의 품질도 pool ≥ seq(모든 규모 양수, 8축×5 유의). 신뢰성·품질 양쪽에서 pool 우세.
3. seq의 고차원 결렬은 P4 REC 강점의 이면 — 축별 커밋이 복구는 싸게 하지만 순차·조기확정이
   고차원에서 취약. **배포 맥락이 "고차원 + 복구 잦음"이면 두 안의 상반된 성질이 정면 충돌**한다.

## 5. 미검증 ① 해소

P4 §5의 미검증 ①("pool의 FC 우위는 4축에서 측정 — 고차원에선?")이 이 측정으로 채워진다:
**고차원(10축·100억)에서도 pool은 seq 이상의 합의 품질을 유지**하며, 오히려 seq가 합의율에서
무너진다. 4축에서의 pool 우세(P2)가 고차원에서 뒤집히지 않고 **확대**됨을 확인했다.

### 남은 한계

- **품질 CI가 넓다**(짝 표본 축소 탓). 규모별로 시드를 늘리면 8축×5 외 규모도 유의성이 잡힐 수
  있다.
- **full 메모리 외삽은 근사**다(유효후보 비율이 region 수에 따라 변함). 다만 **시간 외삽(∝S)은
  정확**하고, 그것만으로도 full 실행 불가는 확정된다.
- seq 합의율은 **백트랙 상한(2회)에 민감**할 수 있다 — 상한을 늘리면 합의율이 오를지, 아니면
  시간만 늘고 여전히 결렬할지는 별도 측정 대상.

## 6. 완벽 정보 전제 재실행 (에이전트가 진짜 선호를 정확히 앎)

위 측정은 에이전트가 자기 선호를 대략만 아는 **부분 정보** 전제다(agent_view: 가중치 3단계
양자화 + 점수 30% 결측). 여기서는 그 노이즈를 0으로 두어(**뷰 = 진실**) 재실행했다 — 즉
"대리인이 위임자의 진짜 선호를 정확히 안다"는 전제. 재현: `run_oom_stress.py --seeds 20 --perfect`.
원자료: `oom_stress_perfect.jsonl`.

**① threshold 밑 수락이 전 규모에서 0이 됐다.** 완벽 정보에선 에이전트 효용 = 판정기 진짜
효용이라, threshold(0.4) 위에서 수락한 합의는 진짜로도 항상 threshold 위다. §2에서 본 오수락은
순전히 뷰-진실 간극이 원인이었음이 확인된다.

| 규모 | pool 밑수락 (노이즈 → 완벽) | seq 밑수락 (노이즈 → 완벽) |
|---|:--:|:--:|
| 6축×5 | 1 → **0** | 0 → 0 |
| 8축×5 | 1 → **0** | 2 → **0** |
| 10축×5 | 1 → **0** | 1 → **0** |
| 10축×8 | 5 → **0** | 1 → **0** |
| 10축×10 | 1 → **0** | 1 → **0** |

**② seq는 완벽 정보에서도 여전히 결렬한다 — 결렬은 구조적이다.** 노이즈가 걷혀 seq 합의율이
다소 올랐지만(예: 10축×5 65→80%, 10축×10 85→95%), **고차원에서 여전히 5~20% 결렬**한다.
결렬 원인이 뷰 노이즈가 아니라 **순차 분해 + 백트랙 2회 상한이라는 구조**임이 확정됐다.
pool은 완벽 정보에서도 전 규모 100%.

| 규모 | pool 합의율 (노이즈→완벽) | seq 합의율 (노이즈→완벽) |
|---|:--:|:--:|
| 6축×5 | 100 → 100% | 100 → 100% |
| 8축×5 | 100 → 100% | 80 → 90% |
| 10축×5 | 100 → 100% | 65 → 80% |
| 10축×8 | 100 → 100% | 65 → 80% |
| 10축×10 | 100 → 100% | 85 → 95% |

**③ pool의 품질 우위가 더 또렷해졌다.** 뷰 잡음이 사라지니 짝비교가 노이즈 땐 1개 규모만
유의했던 것이 **3개 규모에서 유의**해졌다.

| 규모 | pool 효용µ | seq 효용µ | pool−seq (95% CI) |
|---|--:|--:|--:|
| 6축×5 | 1.533 | 1.460 | **+0.073 [+0.002, +0.143]** ✓ |
| 8축×5 | 1.265 | 1.215 | +0.047 [−0.044, +0.138] |
| 10축×5 | 1.319 | 1.199 | **+0.139 [+0.033, +0.246]** ✓ |
| 10축×8 | 1.335 | 1.180 | **+0.177 [+0.088, +0.266]** ✓ |
| 10축×10 | 1.309 | 1.281 | +0.033 [−0.069, +0.136] |

**종합**: 완벽 정보 전제에서도(오히려 더 선명하게) pool이 **신뢰성(100% vs 80~95%)·품질(전
규모 pool≥seq, 3개 유의)** 양쪽에서 우세하고, seq의 고차원 결렬은 구조적이다. threshold 밑
수락 이슈는 완벽 정보로 소거된다 — 즉 §1~5의 핵심 결론(둘 다 OOM 규모에서 생존, 그 규모에서
pool 우세)은 정보 전제와 무관하게 유지된다.
