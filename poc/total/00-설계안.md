## 1. 목적

두 PoC가 **같은 QA를 서로 다른 방법으로 재고 있다.** FC와 의제 탄력성 c는 우연히 정합하지만, TB·RU·CF는 방식이 다르거나 한쪽에만 있다. 측정 코드를 하나로 모아 **같은 자로 재게** 하는 것이 목적이다.

**두 실험은 합치지 않는다.** `dp2-nparty`의 방안 1-A vs 방안 2 비교와 `dp-composite-agenda`의 1안 vs 2안 비교는 서로 다른 설계 문제이므로 **각각 독립 실행**한다. 공유하는 것은 **측정기와 결과 형식**뿐이다.

## 2. 다루는 QA

| QA | 정의 출처 | 판정 지표 |
|---|---|---|
| **Functional Correctness** | 24 §1 (dp2 정의) | Total Utility 달성률 → 개선 비율 s → 별점 |
| **Confidentiality** | 24 §7 (dp2 정의) | 1:1 대비 노출 배수 m → 별점 (노출률·집중도 병기) |
| **Time Behaviour** | 24 §6 (dp2 정의) | 합성 시간 T + 지배 항 |
| **Resource Utilization-메모리** | 24 §2 | **프로세스 tracemalloc 피크**와 **공통 기저**를 각각 보고 |
| **Scalability-의제** | 24 §4 | 조합-메모리 탄력성 c → 별점 (완결률 게이트) |

**제외**: Fault Tolerance · Recoverability (사용자 지시), Scalability-참여자 수 · Analysability · Adaptability (이번 범위 밖).

> 제외 사유를 코드에 남긴다 — 나중에 "왜 없지?"가 되지 않도록 `qa/__init__.py` docstring에 명시.

## 4. 공통 계약 (핵심 설계)

측정기가 실험 도메인을 모르게 하려면 계약이 먼저 있어야 한다. 두 PoC의 도메인은 이렇게 다르다:

| | dp2-nparty | dp-composite-agenda |
|---|---|---|
| 후보 | `Candidate` (단일 튜플) | `Scenario.axes` × 값의 곱집합 |
| 선호 | `Profile.utility(c)` | `TruthProfile` + soft/hard rules |
| 실행 결과 | `SessionResult` (phases·messages·bytes·eval_calls·n) | `RunResult` (phases·messages·peak_kib·wall_ms) |

### 4.1 계약 정의 (초안)

```python
# qa/contract.py
Outcome = Hashable                      # 후보 1건. dp2=튜플 / dpca=frozenset(축,값)

class Preference(Protocol):
    pid: str
    initial_threshold: float            # 바닥선 (FC의 유효 후보 판정)
    def utility(self, o: Outcome) -> float: ...

@dataclass(frozen=True)
class ObservationEvent:
    sweep: int
    round: int
    actor: str                          # 행위 주체 pid
    kind: str                           # "submit" | "vote" | "announce" | "notify"
    outcome: Outcome | None
    audience: tuple[str, ...]           # 이 이벤트를 정당하게 볼 수 있는 pid 목록

@dataclass
class SessionResult:
    plan: str
    participants: list[str]
    agreement: Outcome | None           # None = 결렬(NO_DEAL)
    rounds: int
    sweeps: int
    phases: int                         # 직렬 통신 단계 (편도)
    messages: int                       # 물리 전송 건수
    bytes: int                          # 페이로드 바이트
    eval_calls: int                     # 효용 평가 호출 수 (전 참여자 합)
    events: list[ObservationEvent]
    peak_bytes: int = 0                 # runner가 채움 (tracemalloc)
    base_bytes: int = 0                 # 공통 기저 (효용 테이블·순위표)
```

### 4.2 가시성을 이벤트에 선언한다 — 기존 대비 개선점

지금 dp2의 `cf_depth._visible_subs(session, observer, coordinator)`는 **방안별 가시 규칙을 측정기가 알고 있다.** 방안이 늘 때마다 측정기를 고쳐야 하고, dpca 도메인에는 아예 맞지 않는다.

**대신 `ObservationEvent.audience`에 가시성을 선언한다.** 프로토콜이 "이 메시지는 누가 보는가"를 알고 있으므로 그쪽이 채우는 것이 옳고, 측정기는 필터만 하면 된다:

```python
visible = [e for e in session.events if observer in e.audience]
```

이렇게 하면 CF 측정기가 방안·도메인과 완전히 분리된다. **이번 통합의 가장 중요한 구조 변경**이다.

### 4.3 실험이 제공해야 하는 것

```python
class Experiment(Protocol):
    name: str
    def dataset(self) -> Dataset: ...              # §6
    def plans(self) -> dict[str, PlanFactory]: ...
    def run(self, case, plan) -> SessionResult: ...
    def candidates(self, case) -> Iterable[Outcome]: ...   # x*·유효후보 열거 (generator 허용)
    def base_size(self, case) -> int: ...                  # 공통 기저 바이트
    def e2_anchor_plan(self) -> PlanFactory: ...           # CF의 e₂ 참조 프로토콜 (§5.2)
```

`candidates()`를 **generator 허용**으로 두는 것이 중요하다 — dpca는 곱집합이라 전수 리스트가 메모리에 안 들어갈 수 있다 (현행 `oracle.analyze`는 `enumeration_limit=200_000`).

## 5. QA별 명세

### 5.1 Functional Correctness — 24 §1

두 PoC가 이미 등가이므로 **dp2 `measures/fc.py`를 정본으로 이식**한다.

- 유효 후보 = 전원 utility ≥ initial_threshold. **결렬 후보(전원이 자기 바닥선을 얻음)는 항상 포함**
- `x*` = 유효 후보 중 total utility 최대
- 달성률 = `U(r) ÷ U(x*)`
- `R̄` = 유효 후보 달성률의 **산술 평균** (표본 추출이 아니라 기대값 정확 계산)
- 개선 비율 `s = (달성률 − R̄) ÷ (1 − R̄)`
- **집계는 표본 전체의 달성률 평균과 R̄ 평균을 먼저 구한 뒤 s로 한 번 환산**한다
  (24 §1.4 「집계 수준」). 세션별 s를 평균 내지 **않는다** — 개선 여지가 0에 가까운 쉬운
  세션의 s가 크게 튀어 대표값을 지배하기 때문이다. 이식 초판이 이걸 어겨 별점이 한 칸씩
  틀렸다 (§13-4)
- 별점: `s > 0.8→5 · >0.6→4 · >0.4→3 · >0.2→2 · >0→1 · else 0`
- **FR 위반은 점수와 분리해 플래그로 보고** (하드 제약 위반, 바닥선 밑 수락) — dpca `judge.py`의 좋은 점이라 가져온다

### 5.2 Confidentiality — 24 §7

**판정 지표: 1:1 대비 노출 배수 m** = `Σ(전 관찰자의 노출 깊이 e) ÷ e₂` (피해자 1인 기준, 낮을수록 좋음)

깊이 `e`는 성격이 다른 2축으로 각각 산출해 병기한다:

| 축 | 뜻 | 무엇의 책임 |
|---|---|---|
| **A — 순위표 노출 비율** | 관찰로 순위가 확정 귀속되는 항목 수 ÷ 유효 후보 수 | 구조 (공격자 무관, 정보론적 상한) |
| **B — 접두 복원 깊이** | 고정 공격자가 순서까지 복원한 최대 순위 ÷ 유효 후보 수 | 공격자 능력 (실제 성과) |

**별점** (24 §7.3 잠정 사다리, 3점 경계 = 1:1 등가): `m ≤ 0.25→5 · ≤0.5→4 · ≤1→3 · ≤2→2 · ≤4→1 · >4→0`

**병기**: ① 최대 단일 관찰자 깊이(노출 집중도) ② 정규화 노출률(1순위 기준, 하위 호환)
**관점 2개**: 일반 참여자 관찰자(**판정 기준**) / 담당자(병기)
**공격자**: frequency 상대 모델 — 24 §7.4의 고정 규칙 3개를 코드에 봉인. 변경 시 전 측정 재실행.

> **e₂ 앵커는 실험 도메인별로 따로 측정한다.** e₂는 참조 양자 프로토콜(N=2)에서 얻는 고정 분모인데, 후보 공간·유효 후보 수가 도메인마다 달라 dp2의 e₂를 dpca에 쓰면 분모가 맞지 않는다. 각 실험이 `e2_anchor_plan()`으로 자기 참조 프로토콜을 제공한다.
>
> 이로써 **2인 고정인 dpca에서도 m이 성립한다** — 분모가 측정 대상이 아니라 참조 프로토콜이므로, "이 설계가 평범한 양자 SAO보다 더 새는가"를 잰다.

### 5.3 Time Behaviour — 24 §6

> **T = phase 수 × t_phase + (효용 평가 호출 수 ÷ N) × t_eval + 총 전송 바이트 ÷ bw**

| 상수 | 값 | 출처 |
|---|---|---|
| `t_phase` | **75ms** (편도) | 24 §6.4-d — LTE 클라우드 릴레이 구간 분해 |
| `t_eval` | **3µs** | 24 §6.4-b — PoC 실측 1.394µs 기반 |
| `bw` | **2,500,000 B/s** (20 Mbps) | 24 §6.4-c — LTE |

- **phase는 편도**다 (구 이름 `t_rtt`는 오해를 낳아 개명됨). 라운드 수 비교는 24 §6.3이 금지한다
- 평가 항의 **÷N 병렬 보정** 적용 (24 §6.4-a)
- **지배 항(regime)을 함께 보고**한다 — 절대값보다 이쪽이 정보량이 크다
- **dpca의 `wall_ms` 실측은 판정에서 제외**한다 — 실행 머신 성능에 의존해 재현성이 없다. 참고 관측으로만 기록

> **dpca에는 바이트 계측이 없다** (`comms.py`는 건수·phase만). 전송 항을 계산하려면 어댑터가 페이로드를 직렬화해 바이트를 세야 한다 — dp2의 `payload_bytes`(JSON, `ensure_ascii=False`) 규약을 공유한다.

### 5.4 Resource Utilization-메모리 — 24 §2

**두 값을 각각 보고한다** (사용자 지시):

| 값 | 뜻 | 방안 의존 |
|---|---|---|
| **프로세스 피크** | 협상 실행 구간의 tracemalloc 피크 | 있음 |
| **공통 기저** | 각자의 효용 테이블·순위표·역인덱스 | **없음** — 조합 수에만 비례 |

**별점은 내지 않는다.** 24 §2.8이 명시하듯 PoC(ENV-A)의 논리 크기와 실기기 RSS는 단위가 달라 별점이 포화된다 — 한도 대비 r 판정은 ENV-B 소관이다. PoC에서는 **방안 간 상대 비교**만 한다.

다만 24 §2.8 단서에 따라 **"단말 총 점유 = 공통 기저 + 프로토콜 상태"** 를 함께 표시한다 — 공통 기저는 방안 선택으로 줄일 수 없는 하한이므로 조합 공간 규모 상한의 근거가 된다.

### 5.5 Scalability-의제 — 24 §4

- **c** = 조합 수 S에 대한 피크 메모리의 log-log 회귀 기울기, **95% CI·R² 병기**
- **별점**: 전체 열거(c=1)와 이론 이상(c=1/d) 사이 5등분 — `c ≤ 1/d+w→5 · … · >1.0→0` (w = (1−1/d)/5)
- **`d`는 데이터셋의 의제 수다 — 하드코딩 금지.** 24 §4.3: *"기준 시나리오의 의제 수 d가 바뀌면 하계 1/d와 구간 폭을 갱신한다"*. 현행 dp2 `stars_c(c, d=4)`의 기본값 4는 제거하고 데이터셋에서 받는다
- **완결률 게이트 (24 §4.4)**: 최소 S vs 최대 S의 정상 완결률이 유의하게 저하되면(비율 차 검정 95%) **c와 무관하게 0점 + 결함 보고**
- 회귀 구현은 dp2의 scipy `linregress` + t-구간을 쓴다 (dpca의 자체 OLS + `T_TABLE` 하드코딩은 폐기)

## 6. 데이터셋 변수화

**참여자 수·의제 수·후보 수는 코드에 없다. 데이터셋이 정한다.**

```python
@dataclass(frozen=True)
class Dataset:
    name: str
    n_participants: int      # dp2: 3~50 스윕 / dpca: 2
    n_issues: int            # = SC-의제 별점의 d
    issue_value_counts: list[int]
    n_candidates: int        # 조합 수 S = prod(issue_value_counts)
    seed: int
    cases: list[Case]
```

이에 따라 고쳐야 할 현행 하드코딩:

| 위치 | 현행 | 통합 후 |
|---|---|---|
| `dp2 scaling.stars_c(c, d=4)` | 기본값 4 | `dataset.n_issues` |
| `dpca comms.Comms(n_participants=2)` | 기본값 2 | `dataset.n_participants` |
| `dpca` 전반의 2인 전제 | 고정 | 데이터셋 값 |
| `tb.synth_time`의 `session.n` | 세션이 채움 | 유지 (이미 변수) |

## 7. 결과 형식 — 두 PoC의 장점 결합

```

  <experiment>/<run_id>/
    meta.json                       실행 메타 — seed·commit·negmas 버전·상수·데이터셋 (dp2)

    report.html                     대시보드 (dp2)
```

| 요소 | 출처 | 왜 |
|---|---|---|
| `<run_id>` 폴더 단위 + 실행 메타 | dp2 | 재현성 — seed·commit·negmas 버전이 있어야 결과를 신뢰할 수 있다 |
| `raw.json` + 자동 `report.md`/`.html` + `INDEX.md` | dp2 | 수기 md는 갱신 누락이 생긴다 |
| **`cases.jsonl`** | dpca | 케이스별 1행이라 필터·교차 집계가 쉽다. 지금 dp2는 집계값만 남아 개별 케이스 추적이 안 된다 |
| **이벤트 로그 + `explain_run`** | dpca | 추적성 — 로그만으로 협상 전개를 사람 말로 재구성 |

## 8. 24 핸드북 동기화

### 8.1 폐지된 문서 번호 참조

`dp-composite-agenda`는 **폐지된 문서 번호(25~29)** 를 정본으로 인용하고 있다 — `recovery.py`, `comms.py`, `run_c_sweep.py`, `run_benchmark.py`, `analyze_fc.py`, `run_rec.py`, `run_final_fc_rec.py`, README. `docs/changbae/`에 25~29는 없다(24로 통합·폐지).

통합 라이브러리는 **모든 측정기 docstring이 24의 절 번호를 인용**한다 (`[24 §1]`, `[24 §7.3]` 등).

### 8.2 dpca의 자체 별점 밴드가 24와 충돌한다 (2026-08-12 확인)

`results/최종-QA-비교.md` §0이 **24와 전혀 다른 자체 별점 밴드**를 정의해 쓰고 있다:

| QA | dpca `최종-QA-비교.md` §0 | **24 핸드북 (통합본이 따를 것)** |
|---|---|---|
| FC | 달성률 **직접** 밴드 (≥.95 / ≥.90 / ≥.85 / ≥.80 / ≥.70) | `s = (달성률 − R̄) ÷ (1 − R̄)` 5등분 — **무작위 베이스라인 정규화** |
| Scalability-의제 | **최대 축 수** (메모리 ≤100MB 조건) | **탄력성 c** (log-log 기울기) |
| RU-메모리 | 16축 피크 **절대 MB** 밴드 (≤1MB/≤10MB/…) | **별점을 내지 않는다** (§2.8 — ENV-B 소관) |
| 시간 | **wall time 절대 초** 밴드 (≤0.2s/≤1s/…) | **합성 시간 모델** (t_phase·t_eval·bw) |

**dpca 내부에서도 갈린다** — `P3-c-결과.md`는 탄력성 c로 별점을 냈는데(★5) `최종-QA-비교.md`는 최대 축 수로 낸다. 같은 QA에 척도가 두 개다.

통합본은 **현행 24를 따른다.** 따라서 dpca의 별점은 전부 바뀐다 — 이건 버그 수정이 아니라 **정의 교체**이므로 §9.2에 "재현 대상 아님"으로 명시한다.

### 8.3 24 통합 이후 개정 미반영

RU 판정(순간 피크·공통 기저 분리), CF 지표(노출 배수 m), TB 상수(t_phase 75ms·t_eval 3µs) 개정이 dpca에 반영되지 않았다. 통합본이 현행 24로 맞춘다.

## 10. 확정 사항 (사용자 답변, 2026-08-12)

**1. 기존 두 폴더 — 유지.** `dp2-nparty`·`dp-composite-agenda`를 그대로 둔다. `poc/total`은 신설이며 기존 폴더의 코드를 지우지 않는다.

**2. 바이트 계측 — "방식 차이"가 아니라 dpca에 없다 (신설 필요).** 전수 검색으로 확인:

| | 계측 방식 |
|---|---|
| dp2 | `blackboard.payload_bytes()` — `json.dumps(payload, ensure_ascii=False)`의 UTF-8 바이트 × 전송 건수 (규약 고정) |
| **dpca** | **없음.** `comms.py`는 `messages`(건수)·`phases`만 센다. 바이트 관련 코드 0건이고 `fc_benchmark.jsonl` 필드에도 없다 |

따라서 dpca 어댑터는 dp2와 **같은 규약**(`json.dumps(..., ensure_ascii=False)` UTF-8 길이)으로 페이로드를 직렬화해 바이트를 세야 한다. 프로토콜 구현에 손이 가는 유일한 항목이다.

**3. dpca의 관점 — 담당자 = 참여자.** dpca는 2인 교대 제안이라 상대방이 곧 담당자다. **관점 1개**로 보고한다.
계약상 실험이 관점 목록을 선언한다: dp2 = `["participant", "coordinator"]`, dpca = `["participant"]`.

**4. CF 별점 — 잠정 사다리 유지 + 객관 수치 병기.** 24 §7.3이 "잠정 — PL 조율 예정"이므로 그대로 쓰되, **별점 옆에 항상 원지표를 함께 보고**한다 — `m_A` · `m_B` · 최대 단일 관찰자 깊이 · 정규화 노출률. 별점만 남기지 않는다.

**5. 데이터셋 — 각자 원래 폴더에 있고, 복사하지 않는다.**

| 실험 | 데이터셋 위치 |
|---|---|
| dp2-nparty | [`data/benchmark/`](../dp2-nparty/data/benchmark) — `cases` · `fixtures` · `schema` |
| dp-composite-agenda | [`scenarios/*.yaml`](../dp-composite-agenda/scenarios) (12종) · [`fixtures/*.json`](../dp-composite-agenda/fixtures) (12종) |

`poc/total/datasets/`는 **데이터를 담지 않고 로더·메타(참여자 수·의제 수·d 등)만** 둔다. 원본은 기존 폴더가 단일 출처(single source of truth)로 유지된다.

## 11. 남은 검토 여지 (착수를 막지는 않음)

- **의제 조합 데이터셋의 정교함 차이.** dp2의 SC-의제는 24 §4가 *"벤치마크 보류 상태라 개발용 multi-issue 생성으로 대체 (잠정)"* 이라 적혀 있고, dpca의 `scenarios/*.yaml`은 축·값·의존성·충돌 라벨까지 정의돼 있다. 통합 후 dp2 쪽에도 쓸 수 있는지는 P3 단계에서 판단한다 — 지금 결정하지 않는다.

## 12. 구현하며 달라진 것 (2026-08-12)

설계안대로 되지 않았거나, 구현 중에야 드러난 것들을 남긴다.

### 12-1. 기존 폴더 유지 → **데이터셋은 이전** (사용자 결정)

원본 두 폴더는 더 이상 쓰지 않으므로 벤치마크 데이터를 `datasets/` 아래로 **복사**했다
(nparty 537건 · composite 25건). 원본 위치를 참조하지 않으므로 `poc/total`만으로 완결된다.

### 12-2. 프로토콜을 `_vendor/`로 이식 (재작성하지 않음)

계약만 새로 쓰고 프로토콜은 원본을 그대로 옮겼다. 검증 기준이 "기존 실행과 같은 수치"인데
재작성하면 차이의 원인을 가릴 수 없기 때문이다. 원본에서 손댄 곳:

| 파일 | 수정 |
|---|---|
| `nparty/_vendor/benchmark.py` | `DATA_DIR`를 `datasets/nparty`로 재지정 |
| `composite/_vendor/**` | `dpca.` 절대 임포트 → 패키지 경로 (9개 파일) |
| `composite/_vendor/harness/comms.py` | **바이트 계측·관찰 기록 신설** (원본에 없던 항목) |
| `composite/_vendor/strategies/*.py` | 위 계측을 위한 호출부 인자 추가 · `_pid` |
| `composite/_vendor/harness/runner.py` | `RunResult`에 `bytes`·`observations` 추가 |

### 12-3. FC·SC-의제를 **2지표 병행**으로 (사용자 결정)

- FC: 개선 비율 `s`(24 정본) + 달성률 절대 밴드
- SC-의제: 탄력성 `c`(24 §4.3) + 최대 의제 수

두 지표가 어긋날 수 있는 것이 정상이다 — 절대 수준과 증가 추세는 다른 질문이다.

### 12-4. RU 별점은 **단말 총 점유 ÷ 한도** (24 §2.8 단서)

한도 기본값은 ART 힙 상한 **256MB**. 24 §2.8의 15%p 등분을 그대로 쓰되 실험에서
override 가능하게 했다. 작은 규모에서 포화하는 한계는 그대로이므로 절대 MB를 병기한다.

### 12-5. 구현 중 드러난 것 — 설계안에 없던 문제 3가지

**(a) CF 깊이의 대조 대상이 틀리면 조용히 0이 된다.**
노출 깊이를 **전체 공간** 순위와 대조하면, 피해자가 애초에 제안하지 않을 후보(바닥선
미달·하드 제약 위반)가 순위표 앞자리를 차지해 첫 항목부터 어긋난다. 분모(d_v)와 대조
대상을 **유효·제안 가능 후보로 같이 맞춰야** 한다. 실제로 이 버그가 있었고 고쳤다.

**(b) 교환된 offer의 표현이 후보 공간과 다르면 매칭이 전부 실패한다.**
dpca의 offer는 축 순서 원시 튜플(`('sat','17:00',…)`)인데 후보 공간은 정규형이라,
변환하지 않으면 노출 깊이가 0이 된다. 이것도 실제 버그였다.

**(c) tracemalloc을 겹쳐 감싸면 피크가 0이 된다.**
dpca 러너는 내부에서 이미 tracemalloc을 쓴다. 밖에서 한 번 더 감싸면 내부 `stop()`이
추적을 꺼 버린다. composite 어댑터는 원본이 잰 값을 그대로 쓴다.

셋 다 **조용히 틀린 값을 내는** 종류라, 회귀 테스트가 없었으면 못 잡았을 것이다.

### 12-6. 남은 한계 — 해결하지 못하고 기록만 한 것

- **composite의 CF B축은 0이다.** dpca는 `agent_view`로 에이전트가 자기 선호를
  부분적으로만 안다(S01 `score_dropout: 0.3`). 관찰 순서로 **진실** 순위의 접두를
  복원하는 일이 거의 없다 — 도메인 속성이지 버그가 아니다. A축은 정상 변별한다.
  e₂ 앵커가 퇴화하면 `m_B`를 큰 수로 내지 않고 **`null` + 사유**로 비운다.
- **1안과 2안의 교환 granularity가 다르다** (축값 vs 전체 조합). 축 단위 노출을 재는
  별도 지표가 필요하며 이번 범위 밖이다.
- **SC-의제의 `d`가 스윕마다 애매하다.** 24 §4.3은 "기준 시나리오의 의제 수"라고 하나
  스윕이 여러 의제 수를 섞는다. 중앙값을 쓰고 실제 값을 `raw.sc_issue.d`에 기록했다.
- **FC 전수 열거 한도.** 조합이 20만을 넘는 시나리오(S11·S12)는 FC에서 제외된다.
  표본으로 바꾸면 달성률이 틀린 값이 되므로 **조용히 넘어가지 않고 거부**한다.

깊이를 각각 훼손했을 때 전부 실패했다.

### 13-2. 리뷰에서 고친 것

§12-5의 버그 3종에 더해:

1. **스윕이 거짓 데이터를 만들고 있었다.** S11의 축은 10개인데 12·14·16·18·20축을
   요구하면 `load_scenario`가 조용히 전체(10축)를 준다 — 다섯 수준이 같은 실행이 되어
   탄력성 c가 왜곡된다. 축 상한을 넘는 수준은 제외하고 그 사실을 출력하게 했다.
2. **`Dataset`이 정의만 되고 안 쓰였다.** "참여자·의제 수를 데이터셋이 정한다"가 명목에
   그쳤다 — 두 실험이 실제로 만들어 쓰고 `meta.json`에 기록하게 했다.
3. **리포트가 `None`을 `"None"`으로 찍었다.** "안 쟀다"와 "0이다"가 뒤섞인다.

### 13-4. 사후 리뷰에서 잡은 이식 회귀 — FC `s`의 집계 수준 (2026-08-13)

**증상.** `qa/fc.py:aggregate()`가 **세션별 s를 산술 평균**하고 있었다:

```python
mean_s = statistics.fmean(x.s for x in scores)   # ← 24 §1.4가 금지한 방식
```

**24 §1.4 「경계 사례와 집계 규칙」** 은 정반대를 규정한다:

> 대안 비교 캠페인에서 s는 세션별로 구해 평균 내는 것이 아니라, **표본 전체의 달성률
> 평균과 R̄ 평균을 먼저 구한 뒤 한 번 환산**한다 (§1.5 절차 6). 세션별 s는 개선
> 여지(분모)가 0에 가까운 쉬운 세션에서 크게 요동치므로, 평균 수준에서 환산해야 표본
> 전체의 개선 정도를 안정적으로 나타낸다.

**왜 값이 달라지나.** s의 분모 `1 − R̄`가 세션마다 다르다. 후보가 전부 고만고만한 쉬운
세션은 R̄가 1에 가까워 분모가 0에 수렴하고, 달성률이 조금만 흔들려도 s가 크게 튄다.
그런 세션의 s를 어려운 세션의 s와 동등한 무게로 평균 내면 **잡음이 대표값을 지배**한다.
규정대로 평균 수준에서 한 번 환산하면 분모가 표본 전체의 개선 여지 하나로 고정된다.

**영향.** 달성률 지표는 단순 평균이라 무관하고, **s만** 바뀐다:

| 실험 | 방안 | 달성률 | R̄ | 회귀분 s | **정정 s** |
|---|---|---|---|---|---|
| nparty | plan1a | 0.9142 | 0.8759 | 0.5262 (★3) | **0.3086 (★2)** |
| nparty | plan2 | 0.9679 | 0.8759 | 0.8440 (★5) | **0.7411 (★4)** |
| composite | seq2 | 0.7658 | 0.7396 | 0.0405 (★1) | **0.1005 (★1)** |
| composite | pool | 0.7706 | 0.7396 | 0.0454 (★1) | **0.1189 (★1)** |

nparty는 두 방안 모두 별점이 한 칸 내려가지만 **순위 결론(plan2 > plan1a)은 그대로이고
격차는 0.318 → 0.433으로 오히려 벌어진다.** composite는 별점이 유지되고 s 값만 커진다
(세션별 평균이 이쪽은 오히려 **과소** 평가하고 있었다 — 편향의 방향이 표본에 따라
달라진다는 점이 이 결함이 눈에 안 띈 이유다).

**이 결함은 이식 과정에서 새로 생긴 것이다.** 원본 dp2는 처음부터 규정대로 하고 있었다
(`campaign.py:73`, `full_campaign.py:349`). 위 「정정 s」 열은 우연의 일치가 아니라
**dp2 원본 `results/full-20260812T171034KST/raw.json`의 발표값과 소수 4자리까지 동일**하다.

**고친 것.**

1. 환산식을 `improvement_ratio(achieved, baseline)` 한 함수로 뽑고 `score()`와
   `aggregate()`가 **같은 함수**를 쓰게 했다 — 두 곳에 규칙이 복제돼 있던 것이 원인이다.
2. `aggregate()`가 `mean_baseline`(R̄)을 함께 낸다. 없으면 리포트에서 s를 재검산할 수
   없었다 — 실제로 이 결함의 영향을 계산할 때 원본 케이스 표를 다시 돌려야 했다.
   **추적성 결함이 검출을 늦춘 사례**다.
3. 리포트 FC 표에 R̄ 행과, "세션별 s의 평균이 아니다"라는 검산 안내를 넣었다.

**테스트.** 회귀분이 테스트를 통과했던 이유는 집계 테스트가 **달성률만** 검증했고
(`test_aggregate_means`), s 관련 테스트가 전부 **케이스 1건**짜리라 두 방식이 같은 값을
내는 구간에만 있었기 때문이다. 다음을 추가했다:

- `TestAggregateSRule` (11건) — 쉬운 세션(R̄=0.98)과 어려운 세션(R̄=0.50)을 섞은 픽스처로
  두 방식의 값이 갈리게 만들고, 규정 값과 일치·세션 평균과 불일치를 **양쪽 다** 단언한다.
  R̄=1 퇴화, 음수 s, 순서 무관, 1건일 때 일치도 함께 고정했다.
- `test_pooled_s_matches_dp2` — 통합본의 집계 결과를 dp2 발표값(0.3086/★2, 0.7411/★4)에
  직접 못박는다. §13-3과 같은 성격의 교차 검산이다.

**교훈 (§13-1의 뮤테이션 점검을 갱신).** 뮤테이션 점검에서 "`fc`의 s 정규화"를 훼손했을 때
테스트가 잡았지만, 그건 **`score()` 안의 환산**이었다. **집계 수준의 규칙은 훼손 대상에
넣지 않았다.** 뮤테이션 대상 선정 자체가 커버리지 사각이었던 셈이다.

집계 규칙을 대상으로 뮤테이션을 다시 돌려 **4/4 잡힘**을 확인했다:

| 훼손 | 잡은 테스트 |
|---|---|
| 집계를 세션별 s 평균으로 되돌림 | `test_stars_follow_the_pooled_s` · `test_pooled_s_matches_dp2` (2건) |
| 정규화 분모 `1−R̄` 제거 | `test_pooled_s_can_be_negative` · `test_pooled_s_matches_dp2` (2건) |
| R̄=1 퇴화에서 무조건 만점 반환 | `test_pooled_baseline_of_one_gives_zero_when_missed` |
| `mean_baseline`을 0으로 고정 | `test_pooled_s_can_be_negative` · `test_pooled_s_matches_dp2` (2건) |

dp2 발표값에 못박은 회귀 테스트가 4건 중 3건에서 잡아냈다 — **외부 기준값과 대조하는
테스트 1개가 자체 픽스처 여러 개보다 강하다**는 것이 이번 사례의 요지다.

> **기존 실행 결과의 처리.** 2026-08-12 실행분(`nparty-1a-vs-2-20260812T123001Z`,
> `composite-1-vs-2-20260812T121104Z`)의 FC `s`와 `s 별점`은 이 회귀를 포함한다.
> 실행 이력이므로 지우지 않고 남기되, **판정에는 2026-08-13 재실행분을 쓴다.**
> 재실행분은 `mean_baseline`이 함께 기록되므로 구분된다 (구 실행분에는 그 열이 없다).

### 13-5. 24 §1.4 개정 — R̄ = 1 규칙의 분리 (2026-08-13)

§13-4를 고치는 과정에서 `qa/fc.py`와 벤더링 `_vendor/measures/fc.py`가 **R̄ = 1 구간에서
다른 값**을 낸다는 것이 드러났다. 처음엔 제 구현의 이탈로 봤으나, 따져 보니 **24 쪽 규칙에
결함이 있었다.** 사용자 승인(2026-08-13)을 받아 24 §1.4를 개정했다.

**개정 전 규칙.** R̄ = 1이면(개선 여지 0) 도달 결과와 무관하게 `s = 1`. 근거는 "분모가 0이라
s가 정의되지 않으므로 관례가 필요하다"였고, 이상 여부는 병기되는 달성률로 확인하도록 했다.

**문제.** 그 규칙에서는 **"결렬이 정답인 시나리오에서 억지 합의를 만든" 프로토콜이 판정
지표에서 만점(★5)을 받는다.** 실측 예 `F-3p-005-no-deal-optimal` (바닥선 0.4/0.4/0.4,
후보 12개 중 유효 후보는 결렬뿐):

| 도달 결과 | 달성률 | R̄ | 개정 전 s | FR 위반 |
|---|---|---|---|---|
| 결렬 (정답) | 1.0000 | 1.0 | 1.0 (★5) | 0건 |
| **억지 합의** | **0.3753** | 1.0 | **1.0 (★5)** | **3건** |

달성률·FR 플래그로 잡으라는 단서가 있었지만, **s는 판정 지표이고 달성률은 병기 지표**다.
역할 분담으로 덮을 수 있는 문제가 아니다.

**개정의 근거는 취향이 아니라 극한이다.** R̄ = 1에는 성격이 다른 두 경우가 섞여 있다:

| 도달 결과 | 분자 (달성률 − R̄) | 분모 (1 − R̄) | 판정 |
|---|---|---|---|
| 유효 후보에 도달 (달성률 = 1) | 0 | 0 | **0/0 부정형** — 관례 필요 → `s = 1` |
| 유효 후보 밖 (달성률 < 1) | **음수 고정** | 0<sup>+</sup> | **부정형 아님** — 극한 −∞ 확정 → `s = 0점` |

R̄ ≤ 1이 항상 성립하므로(각 유효 후보 달성률 ≤ 1의 평균) 분모는 **양수 쪽에서** 0으로
수렴한다. 분자는 음수 고정. 둘째 줄은 관례를 끼워 넣을 자리가 없고, −∞는 24 밴드의
`s ≤ 0 → 0점`에 그대로 들어간다. **개정 전 규칙은 0/0 관례를 두 경우 모두에 적용한 것**이
결함이었다.

**핵심 인식**: R̄ = 1은 "잴 수 없다"가 아니라 **"무작위조차 만점"** 이다. 유효 후보가 결렬
하나뿐이어도 무작위 선택 전략은 멀쩡히 정의된다 — 결렬 후보는 24 §1.3에 따라 **항상**
후보 집합에 있고, 선택지가 1개라 무작위가 결정론이 될 뿐 반드시 달성률 1.0을 얻는다.
그 판에서 못 맞췄다면 무작위보다 나쁜 것이므로 0점이 §1.4의 0점 정의와 정확히 맞는다.

**반영 범위.**

| 대상 | 처리 |
|---|---|
| `docs/changbae/24-QA-측정-핸드북.md` §1.4 | 규칙을 두 줄로 분리 + 근거·개정 전 규칙·구현 상태 기록. §1 머리말에 개정 이력 |
| `qa/fc.py:improvement_ratio()` | 개정 규칙 (기존 동작 유지, 극한 논거를 docstring에 명시) |
| `_vendor/measures/fc.py` · `poc/dp2-nparty` | **개정 전 규칙 그대로 둔다** — 목적이 기존 발표 수치 재현이라 값을 바꾸면 그 목적이 깨진다 |
| `tests/test_fc_crosscheck.py` | `is_known_s_divergence()`로 이 분기만 이름 붙여 예외 처리 + `TestKnownSDivergence`가 차이를 값으로 못박음 |
| `qa/fc.py:aggregate()` · 리포트 | `degenerate_cases`(R̄=1 건수)·`degenerate_missed`(그중 유효 후보 밖) 병기. 24가 "달성률로 확인하라"고 한 구간이 몇 건인지 안 보이면 그 확인 자체가 불가능하다 |

**현재 벤치마크에서의 도달 가능성** (측정):

| | R̄=1 케이스 | 유효 후보 밖 합의 | 둘 다 |
|---|---|---|---|
| nparty (472건) | **33건** (`*-no-deal-optimal` 32 + conformance 1) | 0건 | **0건** |
| composite (20건) | 0건 | **4건** (바닥선 밑 수락) | **0건** |

두 조건이 각각 다른 도메인에 존재하고 교집합만 아직 비어 있다. **지금 발표 수치는 어느
규칙이든 동일**하지만, 프로토콜이 조금만 바뀌면 갈린다. 게다가 §13-4의 집계 수정으로
`mean_s`가 `mean_achieved`·`mean_baseline`만으로 계산되므로, 이 분기는 **케이스별 s 열과
교차검산에만** 영향을 준다.

### 13-6. QA 5종 × 2시나리오 정합성 감사 (2026-08-13)

`poc/total`의 목적은 **QA 5종을 두 시나리오에서 같은 자로 재는 것**이다. 두 실험의
`raw.json` 키가 모두 `['fc','tb','ru','cf','sc_issue']`인 것은 확인됐지만, **키가 같다고
방법이 같은 것은 아니다.** 측정기는 공유하되 그 입력을 만드는 어댑터가 갈라질 수 있어
항목별로 감사했다.

| QA | 측정기 | 입력 생성 방법 | 판정 |
|---|---|---|---|
| FC | 공통 | 동일. composite만 열거 한도로 12건 중 2건 제외 | 방법 동일 · 표본 결손 |
| CF | 공통 | 동일 (e₂ 앵커가 도메인별인 것은 의도된 설계) | ✅ |
| TB | 공통 | **`eval_calls` 산출이 달랐다** | ❌ → 수정 |

| SC-의제 | 공통 | **스윕의 `base_bytes` 취급이 다르다** | ⚠️ 정의 판단 필요 |

#### 고친 것 — TB `eval_calls`가 한쪽만 실측이었다

```python
# nparty  _vendor/protocol.py — 실측
self._eval_calls  = sum(len(a.ranked) for a in self.agents)   # 순위표 구축
self._eval_calls += len(candidates) * self.n                  # 방안 1-A의 라운드별 재평가

# composite  adapters/composite/__init__.py (수정 전) — 공식 추정
eval_calls = len(pids) * len(case._space_list())              # plan 인자가 없다
```

composite 쪽은 방안에 의존하지 않아 **eval 항이 방안을 구분할 능력이 원천적으로
없었다.** 실측이 증명한다 — seq2와 pool의 `median_eval_ms`가 똑같이 5.04ms였다.

`AgentBeliefs`에 계수기를 달아 실측으로 바꿨다. S01 기준:

| | 옛 공식 (방안 무관) | seq2 | pool | pool2 | full |
|---|---|---|---|---|---|
| `eval_calls` | 3,360 | **798** | **240** | **107** | **2,769** |

이제 "후보군을 압축하는 방안이 전수 열거보다 적게 평가한다"가 수치로 드러난다 —
설계 의도가 지표에 반영된다.

**계수 지점을 두 번 잡았다.** 처음에는 `AgentBeliefs.utility()` 호출만 셌는데 1안이
S01에서 **2회**로 나왔다. 1안(`sequential.py`)은 `utility()`를 거치지 않고
`weights`·`scores`를 직접 읽어 `_optimistic`·`_score`에서 효용을 만든다. 세 지점을 모두
`note_eval()`로 모았고, 우회가 다시 생기면 잡히도록 회귀 테스트를 붙였다.

> **알려진 보수성**: 1안의 축 단위 평가는 전체 조합 1건 평가보다 싸다. 합성 시간 모델은
> `t_eval` 상수 하나를 모든 호출에 곱하므로 1안의 eval 항은 **상한**으로 읽어야 한다
> (24 §6.4-a의 단일 상수 가정에서 오는 한계).

#### 오판 기록 — RU 측정 구간은 어긋나지 않았다

감사 중 "composite는 신념 구축을 피크 구간에서 제외했고 nparty는 포함한다,
`measure_peak`의 base 차감도 한쪽에만 있다"고 판단했으나 **둘 다 틀렸다.**

1. **base 차감은 no-op이다.** `tracemalloc.start()`는 시작 이후 할당만 추적하므로
   직후 current가 정확히 0이다 (실측 확인). 차감 여부의 상대 오차 0.0000%.
2. **구간 의미도 같다.** nparty도 `p.ranked()`를 `measure_peak` **밖에서** 먼저
   호출해 공통 기저를 구간에서 뺀다 (`adapters/nparty/__init__.py:163`). composite의
   `build_beliefs`와 같은 위치·같은 이유다. 둘 다 **기저는 밖, 프로토콜 생성+실행은 안**.

`p.ranked()` 호출을 못 보고 단정했다. 기록으로 남긴다 — **감사에서 "다르다"고 말하려면
양쪽 코드를 같은 깊이로 읽어야 한다.**

#### 남은 판단 — SC-의제의 `base_bytes`

`sc_issue.py`는 `c`(63행)와 `max_issues`(208행) 모두 `total_bytes = base + peak`를 쓰는데,
nparty 스윕은 실제 기저를 싣고 composite 스윕은 `base_bytes=0`을 싣는다. nparty에서
기저는 무시할 수준이 아니다 — 총점유의 **30%(plan1a) · 45%(plan2)**.

**그런데 composite에 기저를 실으면 그쪽이 더 틀린다.** composite의 `base_bytes()`는
`deep_size(후보 공간 전체)`인데 10축이면 조합이 970만 개다. **pool·seq는 그 공간을
애초에 만들지 않는 것이 설계의 요점**이므로, 만들지도 않는 공간을 기저로 물리면 방안의
장점을 지운다. `run_sweep_point()`가 열거를 피한 것도 같은 이유다(열거하면 프로세스가
죽는다).

즉 **"공통 기저"가 두 도메인에서 같은 뜻이 아니다** — nparty에서는 실체이고 composite에서는
가상의 상한이다. 선택지:

- **A.** SC-의제를 `peak_bytes`만으로 정의 — 즉시 정합하나 `max_issues`의 한도 판정이 낙관적
- **B.** `total_bytes` 유지하되 composite가 **실제로 물화한 후보 수**만 기저로 계상 — 정확하나 `_vendor/strategies/`에 계측 신설 필요
- **C.** `c`는 peak, `max_issues`는 total — 두 지표가 묻는 질문이 실제로 다르다는 점에 맞춤
  (`c`는 프로토콜의 성질, `max_issues`는 단말의 한계. 24 §2.8의 "단말 총 점유가 판정 기준"과 정합)

**미결.** 사용자 판단 대기 중.

### 13-7. 24 §7 개정 — CF 정의 일반화·B축 제거 (2026-08-13, PL 지시)

§5.2의 "깊이 2축" 설계는 이 개정으로 폐기됐다. 두 가지가 바뀌었다.

**① 정의 일반화.** 구 정의("N명이 협상해도 새는 총량이 1:1 한 번 만큼을 넘지 않는가")는
다자를 전제해 2인 고정인 composite에 어색하게 걸렸다. 신 정의는 **"제안한 설계가
일반적인 2인 협상보다 얼마나 더 내 선호를 노출하는가"** — 참여자 수 전제가 없어
두 실험을 같은 문장으로 덮고, 분모(e₂)가 참조 프로토콜이라는 사실이 정의에 드러난다.
측정 방법은 바뀌지 않았다 (이미 이렇게 재고 있었다 — 정의문이 구현을 따라온 것).

**② B축(접두 복원 깊이) 제거.** 근거 셋:

1. nparty에서는 "라운드 = 순위" 제출 규칙(51 §2)이 방안 전 계열 공통이라, 귀속 관찰이
   있으면 순서도 자동 노출된다 — **B가 A와 항상 일치**해 별도 정보가 없다.
2. composite에서는 `agent_view` 때문에 참조 프로토콜에서조차 순서 복원이 일어나지 않아
   **B의 분모가 퇴화**한다 (§12-6에 한계로 기록했던 그 현상).
3. 지표는 읽는 사람에게 직관적이어야 한다 — 두 도메인 모두에서 결론을 바꾸지 않는 축은
   설명 비용만 남긴다.

검토 과정에서 "양보 곡선 전략이 들어오면 A≠B가 생긴다"는 반론이 있었으나 기각됐다 —
제안 순서는 프로토콜이 못 박고, 양보 곡선(PolyAspiration)은 바퀴 사이 threshold 인하만
담당하므로(51 §6) 순서를 바꾸지 못한다.

**반영 범위**: 24 §7(정의·용어·지표·산출 절차) · `qa/cf.py`(`depth_b` 삭제, `depth` 단일화,
`m_A/m_B` → `m`) · `_vendor/measures/cf_depth.py`(동일 — "기존 발표 수치 재현" 목적은
이 개정으로 폐기, 지금은 24 정본이 유일 기준) · 리포트·실험 출력 · 테스트(B축 5건 삭제,
개정 기록·퇴화 앵커 2건 추가, 456건 전부 통과). **m 값 자체는 변하지 않는다** —
구 m_A가 그대로 m이 된다 (회귀 테스트의 기준값 0.677/1.184 유지로 확인).

### 13-8. 파이썬 버전 고정의 강제화 (2026-08-13, PL 승인)

README의 "3.14 고정"(팀원 명시, 1 ULP 사고 배경)이 **선언만 있고 강제가 없어**
실행 이력이 혼재됐다 — 8건 중 5건이 3.11.15, 3건이 3.14.x.

**버전이 실제로 바꾸는 것** (같은 nparty 별점 실험의 3.14.4/3.11.15 실행 직접 대조):

| 항목 | 결과 |
|---|---|
| FC 달성률·s·x\* 적중 · CF m · 메시지·phase | **소수 6자리까지 동일** — ULP 뒤집힘 미발현 |
| RU-메모리 (기저·피크·총점유) | **5~10% 차이** — tracemalloc이 재는 파이썬 객체 크기가 버전마다 다름 (본질적, 코드로 제거 불가) |
| SC-의제 c | 셋째 자리 차이 (위 메모리에서 회귀) |

즉 고정이 필요한 실질 이유는 ULP(FC)보다 **RU·c의 실행 간 비교 가능성**이다.
버전이 섞인 두 실행의 메모리를 한 표에 놓으면 방안 차이인지 인터프리터 차이인지
구분할 수 없다.

**조치**: `src/total/pyversion.py` — 실험 3종의 진입점이 3.14(패치 무관)를 검사하고
아니면 실행을 거부한다. 우회는 `--allow-python-mismatch`뿐이며 우회해도 경고가 남고
meta.json의 버전 기록으로 구분된다. 테스트(pytest)는 막지 않는다 — 테스트는 발표
수치가 아니고 어느 버전에서든 통과해야 정상이다.

### 13-9. 실험(DP)별 측정 범위 분리 (2026-08-13, PL 지시)

QA 5종을 두 실험에 획일 적용하던 것을 DP별 변별축으로 좁혔다 —
**nparty = FC·CF·TB / composite = FC·RU·TB** (`campaign.QA_NPARTY`·`QA_COMPOSITE`).

근거는 실측이다:

- **nparty의 RU**: 프로토콜 상태가 kB 수준이라 어느 방안이든 만점으로 포화 (§2.8이
  예고한 성질). 의제 조합 규모 문제는 composite DP의 소관이므로 SC-의제 스윕도 제거.
- **composite의 CF**: 잔여 비밀률의 분모가 전체 후보(1,680~28만)로 재개정되면서
  케이스 15건 전부 비밀률 0.98~1.00 → ★5로 퇴화 — 변별력 0 (`qa/cf.py` docstring이
  예고: "조합적으로 거대한 도메인에서는 깊이가 퇴화한다 — CF는 nparty 담당").
- **composite의 RU**: 조합 폭발이 DP의 본질이고, 실제로 S12(조합 28만)에서 두 방안
  모두 한도(128MB) 초과가 잡혔다 — 이 축이 판정을 가르는 실측 사례.

`measure()`에 `qa` 선택 인자를 추가해 실험이 자기 범위를 선언한다. 측정하지 않는
QA는 raw.json에서 섹션 자체가 빠진다 ("안 쟀다"와 "0이다"의 구분 원칙 그대로).

### 13-10. composite RU 기저 개정 — B안 채택 (2026-08-13, PL 확정)

§13-6의 미결 항목("SC-의제의 base_bytes — composite에 전체 공간을 기저로 물리면
방안의 장점을 지운다")이 RU 본 판정까지 같은 문제를 갖고 있음이 확인됐다:
run_session의 기저가 **전체 조합 공간 사본**(deep_size)이어서, S12에서 두 방안의
총점유가 135.27 vs 135.25MB — 기저 135.15MB에 파묻혀 **방안 간 변별이 구조적으로 0**
이었다. nparty는 전 참여자가 실제로 전 후보 효용표를 드는 도메인이라 그 기저가
맞지만, composite는 **전체 공간을 만들지 않는 것이 설계의 요점**이다 (34 문제 정의).

**B안 채택** (§13-6의 선택지 중): 방안이 실제로 물화한 후보 구조를 실측한다.

| 항 | 정의 | 구현 |
|---|---|---|
| 공통 기저 | 축 정의 + 자기 선호 표현 1인분 (방안 무관·소량) | 스윕 경로(`run_sweep_point`)와 같은 공식으로 통일 |
| 프로토콜 상태 | 협상 구간 피크 — **실물화 후보 구조 포함** (방안 의존) | 벤더 tracemalloc 그대로 (창 밖에서 기저 구축 → 이중 계상 없음) |
| 실물화 후보 구조 | full=전수 목록 · pool=압축 풀 · seq=축값 목록의 **보유 최대치** | `AgentBeliefs.note_materialized()` — `note_eval()`과 같은 계측 패턴, 최대 부하 단말 기준 |
| 오라클 공간 | FC 채점 인프라의 전체 공간 사본 — 단말 점유 아님 | `oracle_space_bytes()`로 개명, extra 참고 기록 |

24 §2.8에 composite 기저 정의 개정을 기록했다. 구 규칙("기저 = 공간 사본 +
순위표 1인분")은 폐지.
