# 슬라이드 1 — 배경

## 왼쪽 — 복합 의제 협상의 이해

정의 나열 대신 예시 한 장면에 용어를 라벨로 얹는다.

### 예시 — 친구 4명이 저녁 모임을 잡는 상황

```
정해야 할 항목(의제) 4개

  날짜      장소      시간      식당
  7개       5개       8개       6개
   │         │         │         │
   ▼         ▼         ▼         ▼
 금요일  ·  강남   ·  19시   ·  한식     ← 각 항목에서 하나씩
─────────────────────────────────────
              = 안(후보) 1개
```

- 가능한 안 전체 = 7 × 5 × 8 × 6 = **1,680개**
- 의제가 하나 늘 때마다, 전체 후보는 그 의제의 값 개수만큼 **배로** 늘어남
  (모임 4개 의제 1,680개 → 여행 6개 의제 161,280개)
- 협상 = 두 단말이 이 후보 중 하나를 제안↔수락 반복으로 골라 합의하는 것

### 진행 흐름

도식: [DP-01-배경-진행흐름.drawio](DP-01-배경-진행흐름.drawio)

```
사용자 요청 → Planner(LLM) 의제 목록 생성 → [후보군 구성]* → 협상 세션 ⇄ 상대 단말 → 합의
                                            * 본 DP의 결정 지점
```

## 오른쪽 — 문제 정의

### OOM이 나는 지점

- 협상 엔진은 매 턴 "지금 낼 최선의 제안"을 골라야 함
- 이를 위해 후보를 효용 순으로 정렬·탐색함 — 이 단계에서 후보들이 실제 메모리에 올라감
- 의제 수가 늘면 후보 수가 곱으로 늘어, 정렬·탐색 시점에 앱 메모리 한도를 초과함
- 결과: 협상을 시작하기도 전에 앱이 종료됨(OOM)
- 앱 힙 한도는 OS가 고정하며, 별도 프로세스로 우회하는 것은 정책상 불가

### 규모별 부하 (전수 열거 기준)

| 의제(축) 규모 | 조합 수 | 피크 메모리 / 시간 |
|---|--:|--:|
| 6축×5값 | 15,625 | `[실측]` |
| 8축×5값 | 390,625 | `[실측]` |
| 10축×5값 | 977만 | `[실측]` |
| 10축×10값 | 100억 | `[실측]` (외삽) |

### 왜 단순히 줄이면 안 되는가

- 메모리만 보면 후보를 잘라내면 됨 — 그러나 잘린 후보 안에 최선의 합의안이 있을 수 있음
- 이 시스템의 최우선 품질은 **합의 정확도**(최적 안 대비 품질)임
- 본 DP는 정확도를 올리는 결정이 아니라, **메모리 한도를 지키면서 정확도를 잃지 않는** 구조의 결정임
- 두 품질이 정면으로 상충함 — 후보를 줄일수록 메모리는 안전해지고 정확도는 위험해짐

### 차트 (하단 배치)

- [차트] 축 수별 피크 메모리 증가 — 전수 열거 기준, y 로그 스케일, 허용선 표기
- 수치 확정 후 `results/mem_scaling.svg` 계열로 교체

# 슬라이드 1 — 배경 (템플릿 적용안)

> 템플릿: 상단(제목+설명 2줄) / 왼쪽(제목+내용+UML) / 오른쪽(제목+내용+UML) / 하단(구조 필요 1줄)

## 상단

**복합 의제 협상의 후보군 구성**

- 여러 의제를 한 묶음으로 합의하는 협상에서, 협상에 올릴 후보군을 어떻게 만들지 결정이 필요
- 후보 수는 의제가 늘수록 배로 증가하나, 단말 메모리 한도와 합의 정확도 요구는 그대로임

## 왼쪽 — 복합 의제 협상이란

- 의제: 정해야 할 항목 하나 — 모임이라면 날짜·장소·시간·식당
- 각 의제에서 값을 하나씩 고른 것이 안(후보) 1개

```
  날짜      장소      시간      식당
  7개       5개       8개       6개
   │         │         │         │
   ▼         ▼         ▼         ▼
 금요일  ·  강남   ·  19시   ·  한식
─────────────────────────────────────
        = 후보 1개  ·  전체 1,680개
```

- 의제가 하나 늘 때마다 전체 후보는 그 의제의 값 개수만큼 배로 늘어남 (모임 4개 의제 1,680개, 여행 6개 의제 161,280개)
- 협상은 두 단말이 이 후보 중 하나를 제안과 수락·거절 반복으로 골라 합의하는 절차임

도식(UML): [DP-01-배경-진행흐름.drawio](DP-01-배경-진행흐름.drawio) — 사용자 요청부터 합의까지, 후보군 구성이 본 DP의 결정 지점

## 오른쪽 — 문제: 협상 시작 전에 메모리가 바닥남

- 협상 엔진은 매 턴 최선의 제안을 고르기 위해 후보를 효용 순으로 정렬·탐색하며, 이때 후보들이 실제 메모리에 올라감
- 의제 수가 늘면 후보 수가 배로 늘어, 정렬·탐색 시점에 앱 메모리 한도를 초과하고 협상 시작 전에 앱이 종료됨(OOM)
- 앱 힙 한도는 OS가 고정하며, 별도 프로세스로 우회하는 것은 정책상 불가함
- 후보를 잘라내면 메모리는 해결되나 잘린 후보 안에 최선의 합의안이 있을 수 있음 — 이 시스템의 최우선 품질은 합의 정확도임

OOM 발생 지점 흐름(UML 스케치 — 슬라이드 반영 시 drawio 작성):

```
후보군 생성(lazy, 가벼움)
   ↓
협상 시작 — 최선의 제안 선택
   ↓
효용 순 정렬·탐색 (후보 실체화)   ← 여기서 메모리 한도 초과
   ↓
OOM — 협상 시작 전 종료
```

- [차트] 의제(축) 수별 피크 메모리 증가 — 전수 열거 기준, 허용선 표기, 수치 `[실측]`

## 하단

**최선의 합의안을 놓치지 않으면서, 후보군을 전부 만들지 않는 구성 구조가 필요**

# 슬라이드 2 — 설계

제목(안): **두 후보안 비교 — 정확도 우선 전제에서 2안 채택**

## 1안 — 의제별 순차 협상 (Pipeline)

### 장점

- 의제를 1개씩 협상해 후보를 한 축 크기만 유지하므로, 의제 수가 늘어도 메모리 사용량이 거의 늘지 않음 `[실측]`
- 축마다 합의를 확정하고 넘어가므로, 중단되어도 앞 축 결과가 남아 재실행 비용이 낮음
- 세션이 작고 구조가 단순해 구현·검증 부담이 낮음

### 단점

- 앞 축을 먼저 확정하므로, 뒤 축과 맞물린 더 좋은 조합을 놓쳐 정확도가 낮음 `[실측]`
- 이른 확정이 뒤 축을 막으면 백트랙이 필요해, 의제가 많아질수록 합의가 결렬되는 비율이 늘어남 `[실측]`
- 잃은 정확도를 되돌릴 조절 수단이 없어, 메모리를 더 써도 품질이 회복되지 않음

## 2안 — 개인별 후보군 압축 협상 (Filter-then-Negotiate)

### 장점

- 조합(패키지) 단위로 제안·평가하므로, 의제가 맞물린 경우에도 좋은 조합을 유지해 정확도가 높음 `[실측]`
- 전 과정을 단일 세션으로 진행해 중간 결렬 없이 합의에 도달함 `[실측]`
- 유지 개수 W로 압축 정도를 조절할 수 있어, 메모리와 정확도를 상황에 맞게 교환함

### 단점

- 후보 조합을 실제로 만들어 평가하므로, 의제 수가 늘면 메모리·시간이 가파르게 증가함 `[실측]`
- 협상이 끝날 때까지 중간 확정이 없어, 중단 시 처음부터 다시 하며 복구 비용이 높음
- 압축에서 상위 W개 밖 후보를 버리므로, 최적 조합이 협상 전에 탈락할 수 있음

## 판정 — 2안 채택

- 두 안은 메모리와 정확도를 서로 반대 방향으로 가져감 — 1안은 메모리, 2안은 정확도에 유리함
- 최우선 품질이 합의 정확도이므로 2안을 채택함
- 1안의 정확도 손실은 구조에서 오는 것이라 되돌릴 수 없음 — 반면 2안의 메모리 부담은 W로 조절할 수 있음
- 즉 2안만이 "정확도를 지키면서 메모리를 관리하는" 방향의 조절 수단을 가짐

---

## 확인 필요

- `[실측]` 자리 수치 확정 — 측정 조건(전제·축 범위·시드)을 함께 각주로 표기할지
- 배경 우측 차트를 전수 열거 기준으로 할지, 1안·2안 비교로 할지
- 판정 근거에 2안 메모리 한계(고차원에서 실행 불가 구간 존재)를 명시할지, 운영 범위(의제 수 상한)로 처리할지
