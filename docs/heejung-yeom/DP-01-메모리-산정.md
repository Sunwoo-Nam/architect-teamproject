## 3. 왜 "예산이 고정"인가 — ADJ 제약의 실질적 효과

### 3.1 RAM 용량은 이 문제와 거의 무관하다

```
기기 RAM                    12~16 GB      넉넉함
    ↓ 그러나
앱 1개의 Java heap 상한        수백 MB       dalvik.vm.heapgrowthlimit 로 캡
    ↓ 그리고
별도 워커 프로세스로 우회        불가          ADJ ≤ 300 구간 추가 금지 제약
```

안드로이드는 앱 프로세스당 힙 상한(`dalvik.vm.heapgrowthlimit`)을 둔다. `android:largeHeap="true"`를 주면 `dalvik.vm.heapsize`까지 올라가지만, 어느 쪽이든 **기기 RAM과는 무관한 별도의 캡**이다.

### 3.2 ADJ 제약이 막는 것

안드로이드는 메모리 부족 시 죽일 프로세스 순위를 `oom_score_adj`(ADJ)로 매긴다. **값이 낮을수록 늦게 죽는다.**

| ADJ | 상태 |
|---|---|
| 0 | 포그라운드 앱 |
| 100 | 보이는 앱 |
| 200 / 250 | perceptible (음악 재생, 포그라운드 서비스) |
| 300 | 백업 |
| 400~700 | heavy weight · 서비스 · 홈 · 직전 앱 |
| 900~999 | 캐시된 앱 — 제일 먼저 죽음 |

> 정확한 상수는 안드로이드 버전·제조사에 따라 다르다. 인용 전 대상 버전에서 확인할 것.

`ADJ ≤ 300` 구간에 상주 프로세스를 새로 만들 수 없다는 제약은, 설계 관점에서 다음을 뜻한다.

- 협상 전용 데몬 프로세스 금지
- 포그라운드 서비스 상시 구동 금지
- **결과: 앱 자기 프로세스의 힙 안에서 후보군 생성을 끝내야 한다**

**이 제약의 실질적 효과는 "힙 상한을 우회할 탈출구를 막는 것"이다.** "무거운 조합 계산은 별도 워커 프로세스로" 같은 회피책이 봉쇄되므로, `heapgrowthlimit`이 그대로 하드 리밋이 된다.

→ 슬라이드의 *"온디바이스는 예산이 고정"* 주장에 대한 정확한 근거이며, **"RAM이 16GB인데 왜 문제냐"는 반박을 막는 유일한 논거**이기도 하다.

### 3.3 파생 이슈 — 메모리 밖의 문제

앱이 백그라운드로 내려가면 ADJ가 300을 넘어가고, 그때부터 **협상 도중 프로세스가 죽을 수 있다.** 이는 Resource Utilization이 아니라 Fault Tolerance / Recoverability 영역이다.

- 1안(의제별 순차)은 세션을 N번 돌아 총 노출 시간이 길다
- 2안은 압축 후 협상 1회라 노출 시간이 짧다

**현재 Trade-off 표에 없는 축이다.** 별도 검토가 필요하다.

## 4. 산정식

```
peak_bytes = (동시 존재 outcome 수) × (outcome 1개 바이트)
           + (효용함수 표 바이트)
           + (정렬·샘플링 임시 사본)
```

### 4.1 outcome 1개 바이트 — 추정

의제 6개(여행 시나리오) 기준, JVM 환경 가정.

| 구성 | 바이트 |
|---|---|
| 인덱스 배열 `int[6]` (객체 헤더 16 + 4×6) | 40 |
| 효용값 `double` | 8 |
| 정렬용 참조 · 컬렉션 노드 | 16 |
| **최소형 합계** | **~64B** |
| 객체 그래프 실사용 (Outcome 객체 · 박싱 · 컬렉션 오버헤드) | **200~350B** |

> **⚠ 위 값은 추정이다.** 이하 계산은 보수적으로 **200B/outcome**을 사용한다.

### 4.2 실행 환경이 먼저 정해져야 한다

**NegMAS는 Python 프레임워크다.** 안드로이드에서 Python 런타임(Chaquopy 등)으로 구동하면 튜플 1개가 100B를 넘고, 위 추정의 **2~3배**가 된다.

현재 문서상 `DP-01-enhanced-candidates.md`는 "Android 1차 운영 후보"를 언급하지만, **NegMAS를 안드로이드에서 어떻게 구동할지(Python 런타임 탑재 / JVM 재구현 / 서버 위임)에 대한 결정이 보이지 않는다.** 이 결정 없이는 바이트 산정이 확정되지 않는다.

200B/outcome 가정.

| 케이스 | 동시 outcome 수 | 추정 메모리 |
|---|---|---|

### 5.1 효용함수 표

`DP-01-복합의제-후보군구성-슬라이드-rev.md` §2의 저장 항목 수에 항목당 약 64B(HashMap 노드 + 박싱, **추정**)를 적용.

| 표현 | 항목 수 | 추정 메모리 |
|---|---|---|
| Mapping (전체 표) | 161,280 | **~10MB** |

**효용함수 표를 쌍별로 분해하는 것이 후보군 축소보다 절대 절감량이 크다.**

## 6. 발견 — `W`는 메모리 다이얼이 아니다

현재 슬라이드는 `W = 메모리↔정확성 다이얼`이라고 주장하지만, **바이트로 환산하면 성립하지 않는다.**

```
2안 피크 = W × |다음 의제| × 200B

W =   20  →     240 × 200B =   48 KB
W =  100  →   1,200 × 200B =  240 KB
W = 1000  →  12,000 × 200B =  2.4 MB   ← 300MB 예산의 0.8%
```

**W를 50배 올려도 예산의 1% 미만이다.** W의 상한을 정하는 것은 메모리가 아니라 **부분 평가 연산량(CPU · 지연)** 이다.

### 6.1 따라서 수정이 필요한 주장 두 가지

| 현재 슬라이드 | 문제 | 수정 방향 |
|---|---|---|
| Trade-off 표의 *"피크 메모리 14 vs 240"* | 실제로는 2.8KB vs 48KB — **의미 있는 차이가 아니다.** 이 축으로 1안이 유리하다고 주장하면 반박당한다 | 두 후보안을 가르는 축에서 메모리를 제외 |
| *"2안의 다이얼 = W (메모리↔정확성)"* | W의 실제 제약은 CPU·지연 | 다이얼의 대가를 "연산량"으로 재기술 |

### 6.2 그러면 DP-01의 메모리 논거는 어디서 성립하는가

**"1안 vs 2안"이 아니라 "축소 vs 무축소"에서만 성립한다.**

```
무축소   32~64MB  +  효용표 10MB
축소       48KB   +  효용표 70KB
```

이것이 DP-01이 아키텍처 결정인 이유의 정량적 근거다. 두 후보안 사이의 선택은 **Functional Correctness(상호작용 보존)** 로 판정하는 것이 정직하다.

## 7. 측정 지표 정의 (제안)

### M01-2 `outcome_space_cardinality` — 1차 지표

| 항목 | 정의 |
|---|---|
| 측정 대상 | 협상 세션에 넘기는 OutcomeSpace의 동시 존재 후보 수의 피크 |
| 측정 방법 | 후보군 생성 로직 계측 (카운터) |
| 임계값 | 시나리오별 무축소 cardinality 대비 **감소율**로 판정 |
| 채택 이유 | 런타임·표현 방식에 흔들리지 않고, 설계가 직접 결정하는 값 |

### M01-1 `peak_negotiator_state_bytes` — 검증 지표

| 항목 | 정의 |
|---|---|
| 측정 대상 | 협상 시작 직전 baseline 대비 **앱 프로세스 Java heap 증가분의 피크** |
| 측정 방법 | 강제 GC 후 baseline 확보 → 협상 구간 10ms 간격 샘플링 → `Runtime.totalMemory() − freeMemory()` |
| **임계값 제안** | **≤ 20MB** |
| 임계값 근거 | NFR-MAF-09의 *참여자 1인당 20MB*와 정렬. 후보군은 자기 단말에 1벌이므로 "1인분 이내"면 확장성 모델과 모순되지 않는다 |

**이 선을 그으면 무축소(32~64MB)는 명확히 실패하고 두 후보안은 통과한다.** DP-01이 왜 아키텍처 결정인지가 숫자로 증명된다.

> 전체 프로세스 RSS가 아니라 **delta**로 측정하는 이유: 300MB는 MAF 전체 예산이고, DP-01은 그중 후보군 몫만 책임지기 때문이다.

## 9. 상위 문서(05-NFR.md)에 제기할 사항

### 9.1 LLM 메모리 귀속 전제가 명시되어야 한다

NFR-MAF-06은 `Memory 300MB (온디바이스 LLM 로딩 포함)`으로 되어 있다.

**이 전제가 성립하려면 LLM 가중치가 앱 힙이 아니라 시스템 공유 런타임에 mmap되어 있어야 한다.** 4-bit 양자화된 1~3B 모델도 가중치만 0.5~2GB이므로, 앱 프로세스 RSS로 집계되면 300MB는 물리적으로 불가능하다.

→ 근거란에 **"LLM 가중치는 시스템 공유 런타임에 상주하며 앱 프로세스 힙에 집계되지 않는다"** 는 전제를 명시할 것을 제안한다.

### 9.2 동기화 대상
