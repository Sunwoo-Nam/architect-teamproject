# Topic Planning — 입출력 계약

> **목적**: 이 레이어를 다른 담당 범위와 **분리해서 설계·구현·검증할 수 있도록**, 레이어의 경계를 데이터 계약으로 고정한다.
> **전제 결정**: 분해 입도는 시스템이 결정한다 · 분해는 발의자가 확정한다 · 병렬 실행은 미결(§5)
> **모듈 정의**: [`00-모듈-구조.md`](00-모듈-구조.md)

---

## 1. 경계는 넷이다

```
                          IDS
                           │  ① NegotiationRequest
                           ▼
      ┌────────────────────────────────────────┐
      │        Topic Planning Layer            │ ──④──▶ IDS · 사용자
      └────────────────────────────────────────┘        ProgressSnapshot
              │  ②                    │  ③              DecisionRequest
              ▼                       ▼                 ConfirmedPlan
      TopicSessionSpec        DecompositionAnnouncement
      TopicSessionResult      ACK / REJECT
              │                       │
      하위 협상 세션            상대 단말 PPA
```

이 넷을 고정하면, 하위 협상 세션의 내부 구현(축별 순차 · 후보군 압축 · 다자 프로토콜 종류)이 무엇이든 이 레이어는 영향을 받지 않는다.

---

## 2. 경계 ① — IDS → 이 레이어 : `NegotiationRequest`

| 필드 | 내용 |
|---|---|
| `request_id` | 요청 식별자 |
| `subject_text` | 자연어 주제 원문. 예: "6박 7일 쿄토 근교 여행 일정 논의" |
| `extracted_frame` | IDS가 뽑을 수 있는 만큼의 구조화 결과(기간 · 지역 · 목적 범주). **best-effort이며 누락을 허용한다** |
| `participants[]` | `{user_id, endpoint_hint, role}`. `role`은 `발의자` 또는 `참여자` |
| `deadline` | 협상 결론 기한 |
| `delegation_scope` | 위임 범위(FR-MAF-10). 사용자 승인 없이 확정할 수 있는 한계 |
| `hard_constraints[]` | 사용자가 명시한 절대 조건. 예산 상한, 필수 포함 · 제외 항목 |
| `preference_ref` | 선호 데이터에 대한 **핸들**. 값 자체가 아니다 |
| `context_ref` | 기존 협상 세션의 연속인지 여부(FR-IDS-04) |

**`preference_ref`를 값이 아닌 참조로 두는 이유.** 이 레이어가 Private Knowledge를 보유하면 유출 표면이 그만큼 넓어진다. 실제 값 접근은 하위 세션의 효용 계산 시점에만 일어나야 한다.

**`extracted_frame`을 best-effort로 두는 이유.** IDS가 어디까지 구조화할지는 IDS 쪽 결정이다. 이 레이어가 그 결과에 의존하면 두 레이어가 다시 묶인다. `extracted_frame`이 비어 있어도 `subject_text`만으로 동작해야 한다.

---

## 3. 경계 ② — 이 레이어 → 하위 협상 세션

**분리의 핵심은 이 경계다.** 복합 의제 협상과 다자 합의 프로토콜의 담당 범위와 맞닿는다.

### 3.1 나가는 것 — `TopicSessionSpec`

| 필드 | 내용 |
|---|---|
| `topic_id` | 토픽 식별자 |
| `issues[]` | `{name, value_domain[], 의제 간 제약}`. 값 도메인은 **이미 채워진 상태**로 넘긴다 |
| `bound_values` | 앞 토픽에서 확정되어 이번 세션에서 고정된 값 |
| `resource_budget` | 이 토픽에 배정된 예산 · 시간 상한 |
| `participants[]` | 이 토픽의 참여자. 토픽마다 N이 다를 수 있다 |
| `deadline` · `max_rounds` | 세션 종료 조건 |

### 3.2 돌아오는 것 — `TopicSessionResult`

| 필드 | 내용 |
|---|---|
| `status` | `AGREED` / `NO_DEAL`(합의 실패) / `INFEASIBLE`(실행 가능한 값 자체가 없음) |
| `agreed_outcome` | `{issue: value}` |
| `resource_consumed` | 실제 소모한 예산 · 시간 |
| `blocking_cause` | 실패 시, **어느 `bound_values` 때문에 막혔는가** |
| `max_candidates` | 이 세션이 수용 가능한 후보 수 상한 |

**`blocking_cause`가 필요한 이유.** 이것이 없으면 Backtrack Controller가 동작하지 않는다. "실패했다"는 정보만으로는 어느 토픽으로 되돌아갈지 고를 수 없고, 결국 직전 토픽으로만 되돌리는 맹목적 백트랙이 된다.

**`max_candidates`가 필요한 이유.** 분해 입도를 시스템이 결정하기로 했으므로, 시스템에는 입도 판단 기준이 있어야 한다. 가장 근거 있는 기준은 **하위 세션의 수용 한계**다 — 한 토픽의 의제 조합 수가 세션의 후보 상한 안에 들어오도록 나눈다. 따라서 하위 계층은 자기 한계를 상위에 노출해야 하고, Topic Decomposer는 그 값을 입도 결정의 입력으로 쓴다.

## 4. 경계 ③ — 이 레이어 → 상대 단말 : `DecompositionAnnouncement`

분해는 발의자가 확정하므로, 협상이 아니라 **통보와 응답**이다.

### 4.1 나가는 것

| 필드 | 내용 |
|---|---|
| `plan_id` | 계획 식별자 |
| `topics[]` | `{topic_id, 제목, issues[] 이름 목록}` |
| `dependency_edges[]` | 토픽 간 선후 · 제약 관계 |
| `execution_order[]` | 토픽 실행 순서 |
| `topic_participants[]` | 토픽별 참여자 집합 |

### 4.2 돌아오는 것

`ACK` 또는 `REJECT{reason}`. `reason`은 `해석_불가` / `참여_불가` / `제약_충돌`.

**역제안 없이도 거부는 남겨야 하는 이유.** 발의자 확정이라도 상대가 분해안을 받아들일 수 없는 경우가 있다(스키마를 해석하지 못함, 특정 토픽에 참여할 수 없음, 자기 하드 제약과 충돌). 거부 경로가 없으면 **결렬이 정의되지 않는다.** 거부를 받으면 발의자는 입도를 바꿔 재분해하고 다시 통보한다.

---

## 5. 경계 ④ — 이 레이어 → IDS · 사용자

| 산출물 | 시점 | 내용 |
|---|---|---|
| `ProgressSnapshot` | 진행 중 (FR-MAF-07) | 전체 토픽 수, 토픽별 상태(대기 · 진행 · 잠정합의 · 결렬), 되돌림 횟수, 잔여 자원 |
| `DecisionRequest` | 되돌림 상한 초과 · 위임 범위 초과 (FR-MAF-08) | 사용자에게 결정을 요청한다 |
| `ConfirmedPlan` | 종료 | `{status, topics[]의 확정값, 전역 정합성 검증 결과, execution_items[], event_log_ref}` |

`execution_items[]`는 Tool Calling(FR-MAF-09)이 그대로 실행할 수 있는 액션 목록이다. 이 레이어가 여기까지 만들어야 Tool Calling이 계획 구조를 몰라도 된다.

## 6. 병렬 실행이 이 계약에 미치는 영향 (미결)

의존 관계가 없는 토픽을 병렬로 진행할 것인지는 아직 결정하지 않았다. 이 결정은 성능 옵션이 아니라 **전역 자원 배분 방식을 바꾸는 결정**이다.

| | 순차만 허용 | 병렬 허용 |
|---|---|---|
| 자원 배분 | 잔여를 그대로 흘려보낸다. `resource_budget = 남은 전체` | **사전 배분(예약)이 필수**다. 동시 실행 토픽이 같은 예산을 놓고 경합한다 |
| 배분 실패 시 | 발생하지 않는다 | 한쪽은 남기고 한쪽은 모자란다. 사후 재분배하려면 이미 잠정 합의된 것을 깨야 한다 |
| `TopicSessionResult` 수신 | 동기적 | 비동기. 도착 순서와 백트랙 판정이 얽힌다 |

검토할 때는 이 축을 기준으로 판단한다.

---

## 7. 이 계약이 고정하는 것

- 하위 협상 세션의 내부 구현이 무엇이든(축별 순차 · 후보군 압축 · 다자 프로토콜 종류) 이 레이어는 영향을 받지 않는다. 접점은 `TopicSessionSpec` / `TopicSessionResult` 둘뿐이다.
- IDS가 자연어를 어디까지 구조화하든 이 레이어는 동작한다. `extracted_frame`은 있으면 쓰고 없으면 `subject_text`로 대체한다.
- 이 레이어는 Private Knowledge의 실제 값을 보유하지 않는다. `preference_ref`만 들고 다닌다.
