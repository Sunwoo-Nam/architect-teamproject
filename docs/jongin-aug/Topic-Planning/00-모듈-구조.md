# Topic Planning — 모듈 구조

> **범위**: IDS로부터 협상 의도를 받은 시점부터, 그것을 여러 개의 "토픽"으로 나누고, 각 토픽의 협상 세션을 실행·조립해 최종 확정에 이르기까지.
> **문서 성격**: 설계 대안을 비교하는 DP 문서가 아니라, **실제로 무엇을 개발해야 하는가**를 모듈 단위로 나열한 구조 초안이다.
> **입출력 계약**: [`01-입출력-계약.md`](01-입출력-계약.md)
> **도식**: [`02-모듈-관계도.drawio`](02-모듈-관계도.drawio) · [`03-런타임-흐름.drawio`](03-런타임-흐름.drawio)

---

## 1. 이 레이어가 무엇인가

하나의 **토픽**은 복합 의제(multi-issue)를 담은 협상 세션 하나에 대응한다. 즉 토픽은 협상 세션의 단위이고, 의제는 그 세션 안에서 결정할 축이다.

예: "6박 7일 쿄토 근교 여행 일정 논의"

```
협상 의도 (IDS)
  └ 토픽 1  1일차 오전·점심   → 의제: 출발시각 · 이동수단 · 점심 장소 · 예산
    토픽 2  1일차 오후·저녁   → 의제: 관광지 · 저녁 식당 · 숙소
    토픽 3  2일차 …
                                  └ 이 안쪽이 복합 의제 협상 세션
```

토픽 안쪽(의제 조합 폭발·후보군 구성)은 [`../../07-DP후보안/sunwoo/DP-복합의제-협상방식.md`](../../07-DP후보안/sunwoo/DP-복합의제-협상방식.md)가, 세션 안의 다자 진행은 [`../../changbae/51-설계후보1-다자-합의-프로토콜.md`](../../changbae/51-설계후보1-다자-합의-프로토콜.md)가 다룬다. **본 문서는 그 위, 토픽을 만들고 배열하고 조립하는 층을 다룬다.**

## 2. 현재 상태 — 이 층은 비어 있다

- [`../../09-Design-Overview/C-MAF-내부.drawio`](../../09-Design-Overview/C-MAF-내부.drawio)에는 `IDS(복합 Intent → Task)` → `Orchestrator(Planning)` 화살표만 있고, 그 안에서 무슨 일이 일어나는지는 정의되어 있지 않다.
- [`../../04-FR.md`](../../04-FR.md)의 FR-IDS-03은 "IDS 자체 처리인가 MAF 태스크인가"의 분류까지만 규정하고, **MAF에 무엇을 넘기는지의 페이로드는 정의하지 않는다.**
- [`../../../poc/co-planning/00-구현-계획.md`](../../../poc/co-planning/00-구현-계획.md)의 "단계 분리 + 잠정 합의 + backtracking"이 구조적으로 가장 가깝지만, 그 단계는 **의제(축) 단위**이지 토픽 단위가 아니다.

## 3. 설계 대상 모듈 (11개)

모듈은 투입할 설계 노력에 따라 A · B · C 세 등급으로 나눈다. **Negotiation Request Schema는 이 목록에 없다** — 입출력 계약을 정의한 시점에 그것은 우리가 설계하는 컴포넌트가 아니라 IDS 담당과 합의해야 할 **경계 데이터**가 되었다(§4).

### 3.1 A등급 — 진짜 설계 문제 (3개)

| 모듈 | 하는 일 | 어려운 지점 |
|---|---|---|
| **Topic Decomposer** | 주제를 토픽 목록으로 나눈다. 분해 축(시간 · 장소 · 기능)을 고르고 입도를 정한다. | 비결정적 LLM 출력으로 결정론적 계약(`topics[]`)을 만들어야 한다. 입도 기준을 `max_candidates`로 잡았으므로 조합 수 검증과 재분해까지 이 모듈의 책임이다(§5). |
| **Global Budget Allocator** | 총예산 · 총이동시간처럼 여러 토픽을 가로지르는 전역 자원을 배분한다. 1일차에 예산을 다 쓰는 것을 막는 유일한 장치다. | 병렬 실행 허용 여부가 설계를 가른다. 순차면 잔여 소모, 병렬이면 사전 배분(예약)이 필수다. 미결 결정이 설계를 좌우한다(§8). |
| **Backtrack Target Selector** | 세션 실패 시 `blocking_cause`와 의존 그래프를 보고 되돌아갈 토픽을 고른다. | 하위 계층에 대응물이 없다. 하위 계층은 축 순서가 선형이라 "가장 가까운 앞 축"으로 되돌리면 되지만, 토픽의 의존 그래프는 선형이 아니고 원인 토픽이 직전이 아닐 수 있다. |

### 3.2 B등급 — 구현 대상, 설계 결정은 적음 (6개)

| 모듈 | 하는 일 |
|---|---|
| **Topic → Issue Builder** | 토픽 하나당 의제 집합을 만든다. 협상 세션의 입력(`issues[]`)을 생성하는 어댑터다. |
| **Value Domain Resolver** | 각 의제의 실제 값 후보를 Sub-Agent · Tool 조회로 채운다(그날 상영작, 영업 중인 식당). LLM이 값을 지어내면 협상은 성립해도 후속 실행(FR-MAF-09)이 실패한다. 외부 도구 의존이라 실패 · 지연 처리가 붙지만 구조 결정은 아니다. |
| **Topic Dependency Graph** | 토픽 사이의 선후 · 제약 관계를 표현한다(1일차 숙소 → 2일차 출발지). 실행 순서와 제약 전파 경로를 여기서 결정한다. |
| **Topic Participant Resolver** | 토픽마다 참여자 집합이 달라질 수 있다(1일 점심은 2명, 저녁은 4명). 토픽별 N이 달라지므로 다자 합의 프로토콜의 파라미터가 세션마다 바뀐다. |
| **Decomposition Announcer** | 확정된 분해안을 상대에게 통보하고 ACK · REJECT를 수신한다. 발의자 확정 결정으로 협상이 사라져 통보만 남았다. |
| **Plan Assembler** | 전 토픽의 잠정 합의를 조립하고 전역 정합성(예산 총합, 이동 연속성)을 검증한 뒤, 일괄 commit 하여 Tool Calling(FR-MAF-09)으로 넘긴다. |

### 3.3 C등급 — 하위 계층 구현의 레벨 확장 (2개)

복합 의제 협상 1안(축별 순차 좁힘 + 앞 축 합의를 뒤 축 제약으로 전파)과 **구조가 같고 적용 단위만 한 단계 위**다. 재귀 관계이므로 1안 구현을 레벨 파라미터화하면 그대로 쓴다.

| 모듈 | 하는 일 |
|---|---|
| **Topic Session Orchestrator** | 다음 토픽을 선택하고 세션을 개시하며, 앞 토픽의 합의값을 뒤 토픽의 제약으로 전파한다. |
| **Plan State Store** | 토픽별 합의를 **잠정(tentative)** 상태로 보관하고, 전체 계획이 확정되기 전에는 어떤 토픽도 외부 commit 하지 않는다. |

> **되돌림 횟수 상한 관리와 사용자 요청(FR-MAF-08)** 도 C등급 재사용 범위다. 되돌림 **대상 선정**만 A등급으로 분리했다(3.1).

## 4. 설계 대상에서 빠진 것 — Negotiation Request Schema

IDS가 MAF에 넘기는 페이로드는 [`01-입출력-계약.md`](01-입출력-계약.md) §2에 `NegotiationRequest`로 정의했다. 이것은 **우리가 설계하는 모듈이 아니라 IDS 담당과 합의해야 할 경계 데이터**다. 설계 항목이 아니라 협의 항목으로 관리한다.

## 5. 계약을 쓰고 나서 드러난 문제 — 준비 구간이 직선이 아니다

입도 기준을 `max_candidates`로 잡은 순간, **조합 수는 값 도메인이 채워져야 계산된다**는 사실이 준비 구간의 구조를 건드린다. 분해 시점에는 아직 조합 수를 모른다.

```
Topic Decomposer  →  Topic → Issue Builder  →  Value Domain Resolver  →  조합 수
        ?                                                                    ?
        └──────────  초과를 알았을 때 어디로 되돌아가는가  ───────────────────┘
```

**이 절은 문제 인식까지만이다.** 준비 구간을 어떤 순서와 반복 구조로 구성할지는 결정 사항이며 §8에 검토 항목으로 남긴다. 현재 도식 [`03-런타임-흐름.drawio`](03-런타임-흐름.drawio)의 준비 구간은 직선으로 그려져 있고, 이는 **아직 결정되지 않은 구조를 그린 잠정 상태**다.

결정해야 할 축은 셋이다.

- **재분해 루프를 두는가.** 초과 시 자동으로 입도를 낮춰 다시 분해할지, 아니면 초과를 실패로 보고 사용자에게 넘길지.
- **통보 시점을 검증 앞에 둘 것인가 뒤에 둘 것인가.** 뒤에 두면 확정된 분해안만 나가지만 준비 구간이 길어진다. 앞에 두면 통보가 빠르지만 초과 판명 시 이미 ACK 받은 분해안을 갱신 통보해야 한다.
- **조합 수를 어떻게 알아내는가.** 값 도메인 전체를 조회할지, 개수(cardinality)만 얻는 경로를 별도로 둘지, LLM 추정치를 쓸지. 도구 호출 비용이 재분해마다 반복되므로 이 선택이 준비 구간의 지연을 좌우한다.

## 6. 진행 순서 — 결정 단위

모듈 단위가 아니라 **문제·의사결정 단위**로 진행한다. 하나의 결정이 여러 모듈을 동시에 움직이기 때문이다.

| # | 결정 단위 | 무엇을 정하는가 | 연동 모듈 | 선행 |
|---|---|---|---|---|
| **D0** | `NegotiationRequest` 합의 | IDS가 넘기는 페이로드. 설계가 아니라 **협의**다 | (경계 데이터) | — |
| **D1** | **토픽 실행을 순차로만 할 것인가, 병렬을 허용할 것인가** | 전역 자원 배분 방식, 상태 저장 구조, 결과 수신 모델, 백트랙 판정 | Global Budget Allocator · Topic Session Orchestrator · Plan State Store · Backtrack Target Selector · Topic Dependency Graph | — |
| **D2** | 입도 기준을 무엇으로 삼는가 | `max_candidates` 단독인지, 의미적 응집도를 함께 보는지 | Topic Decomposer · (하위 계층의 `max_candidates` 노출) | — |
| **D3** | 준비 구간의 구성 (§5) | 재분해 루프 유무 · 통보 시점 · 조합 수 확인 방법 | Topic Decomposer · Topic → Issue Builder · Value Domain Resolver · Decomposition Announcer | D2 |
| **D4** | 실패 시 되돌림 대상 선정 규칙 | 세션 실패와 전역 조립 실패 각각의 되돌림 대상 | Backtrack Target Selector · Topic Dependency Graph · Plan State Store · (하위 계층의 `blocking_cause` 계약) | D1 |

**D1이 keystone이다.** 병렬을 허용하면 Topic Session Orchestrator와 Plan State Store가 더 이상 하위 계층 구조의 단순 레벨 확장이 아니게 된다 — 즉 **D1이 §3.3 C등급 재사용의 전제 자체를 좌우한다.** 그래서 등급 분류보다 먼저 결정되어야 한다.

D0는 다른 결정과 독립이므로 IDS 담당과 병행해서 진행할 수 있다.

## 7. 결정된 것

| 항목 | 결정 | 부수 결과 |
|---|---|---|
| **분해 입도의 결정 주체** | 시스템이 결정한다. 사용자는 진행 중 개입으로만 관여한다(FR-MAF-07·08). | 시스템에 입도 판단 기준이 있어야 한다. 기준은 **하위 세션의 후보 수용 한계** — 한 토픽의 의제 조합이 그 상한 안에 들어오도록 나눈다. 따라서 하위 계층이 자기 한계(`max_candidates`)를 상위에 노출해야 한다. |
| **분해의 확정 주체** | 발의자가 확정한다. 상대는 역제안하지 않는다. | 상대와 분해를 맞추는 모듈이 협상 프로토콜에서 **통보 + ACK/REJECT**로 축소된다. 이에 따라 모듈명을 `Decomposition Announcer`로 정한다. 다만 거부 경로는 남겨야 한다 — 없으면 결렬이 정의되지 않는다. 거부 시 발의자가 입도를 바꿔 재분해한다. |
| **IDS 인계 페이로드** | `NegotiationRequest`로 정의했다. 선호 데이터는 값이 아닌 참조(`preference_ref`)로 받는다. | 상세는 [`01-입출력-계약.md`](01-입출력-계약.md) §2. |

## 8. 아직 정해지지 않은 것

§6의 결정 단위와 대응한다.

- **(D1) 의존 관계가 없는 토픽의 병렬 실행 여부.** 성능 옵션이 아니라 **전역 자원 배분 방식을 바꾸는 결정**이다. 순차만 허용하면 잔여를 흘려보내면 되지만, 병렬을 허용하면 동시 실행 토픽이 같은 예산을 놓고 경합하므로 사전 배분(예약)이 필수가 된다. 나아가 C등급 재사용 전제까지 무너뜨린다. 판단 축은 [`01-입출력-계약.md`](01-입출력-계약.md) §6.
- **(D2) 입도 기준.** `max_candidates` 하나로 잡을지, 의미적 응집도(한 토픽이 사용자에게 하나의 결정으로 읽히는가)를 함께 볼지.
- **(D3) 준비 구간의 구성.** 재분해 루프 유무 · 통보 시점 · 조합 수 확인 방법. 세 축의 상세는 §5. 현재 도식 [`03-런타임-흐름.drawio`](03-런타임-흐름.drawio)의 준비 구간은 이 결정 이전의 **잠정 배치**다.
- **(D4) 되돌림 대상 선정 규칙.** 토픽 루프 안의 백트랙은 직전 토픽이라는 국소 판단이지만, Plan Assembler의 전역 정합성 검증 실패는 전역 판단이라 선정 규칙이 다르다. 두 경우를 함께 정해야 한다.
