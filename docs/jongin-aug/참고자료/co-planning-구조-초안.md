# co-planning 구현 구조 초안

> **작성 목적:** [raw.md](raw.md)의 co-planning 확장 요구(선행 협상 결과가 후행 협상의 입력이 되는 복합 계획 수립)를
> 어떤 구조로 구현할지에 대한 초안이다.
> **전제:** NegMAS가 무엇을 제공하고 무엇을 제공하지 않는지는 [NegMAS-파악-및-요구사항-격차.md](NegMAS-파악-및-요구사항-격차.md)에 정리되어 있다.
> 본 문서는 그 격차(G1~G5)를 메우는 구조를 다룬다.
> **성격:** 확정안이 아니라 논의용 초안이다. §7의 결정점은 아직 열려 있다.

📐 **구조도:** [co-planning-구조.drawio](co-planning-구조.drawio)

---

## 1. 구조 개요 — 4계층

| 계층 | 이름 | 구현 주체 | 책임 |
|---|---|---|---|
| L1 | 계획 그래프 (Plan Graph) | 우리 | co-planning 과제를 협상 노드의 방향 그래프로 표현 |
| L2 | 세션 컴파일러 (Session Compiler) | 우리 | 노드 1건을 NegMAS 협상 시나리오로 변환. **자원 상한 강제 지점** |
| L3 | 세션 런타임 (Session Runtime) | NegMAS 중심 | 1건의 협상을 실제로 수행 |
| L4 | 전역 효용·확정 (Global Utility & Commitment) | 우리 | 계획 전체 효용 유지, 노드 확정·보류·철회 |

NegMAS는 **L3만** 담당한다. L1·L2·L4는 NegMAS에 대응 구조가 없으며, 이것이 raw.md 11행
("NegMAS가 커버하지 못하는 부분이 많을 것임")의 구체적 내용이다.

## 2. L1 — 계획 그래프

### 2.1 구성 요소

**노드(Node)** — 계획을 구성하는 결정 단위 1건. 세 종류를 둔다.

| 노드 종류 | 설명 |
|---|---|
| 협상 노드 | 상대 PPA와 합의가 필요한 결정. L3에서 NegMAS 세션 1건으로 실행된다 |
| 로컬 결정 노드 | 협상 없이 자기 기기에서 결정 가능한 항목 (예: 이동 수단 선택) |
| 승인 게이트 | 사용자 확인이 필요한 지점. 통과 전에는 후행 노드가 활성화되지 않는다 |

**간선(Edge)** — 노드 간 의존 관계. 간선은 방향과 함께 **바인딩(binding)** 을 가진다.

**바인딩** — 상위 노드의 합의 결과가 하위 노드의 의제를 어떻게 제약하는지를 규정하는 데이터.
raw.md 9~10행의 "영화 협상 결과를 바탕으로 식사를 예매", "오전 방문지 결과를 참고해 다음 스케줄 협상"이
정확히 이 바인딩이다.

예시 (영화 → 식사):

| 상위 합의 항목 | 하위 의제 항목 | 바인딩 규칙 |
|---|---|---|
| 영화.종료시각 | 식사.slot | 종료시각 이후 슬롯만 유효 (하한 제약) |
| 영화.상영관 | 식사.area | 상영관 인근 지역만 후보 (집합 축소) |
| — | 식사.cuisine, 식사.price | 제약 없음 (자유) |

### 2.2 그래프인 이유

직렬 목록이 아니라 방향 그래프로 두는 근거는 다음과 같다.

- 여행 계획의 "오전 → 오후 → 저녁"은 직렬이지만, "숙소"와 "이동수단"처럼 서로 독립적이면서
  같은 상위 노드에 종속되는 병렬 분기가 존재한다.
- 그래프 구조가 있어야 "어느 노드까지 확정되었고 어느 노드가 철회 대상인지"를 표현할 수 있다(L4).

### 2.3 확장성 확보 방식

raw.md 12행의 "다양한 co-planning 시나리오 확장성"에 대한 답이다.

> **co-planning 시나리오는 코드가 아니라 데이터로 추가한다.**

플랜 템플릿(선언적 스펙)이 담는 것: 노드 목록과 종류, 각 노드의 issue 목록,
issue별 허용 값 어휘, 간선과 바인딩 규칙.

새 시나리오(회식, 스터디, 동반 출장) 추가 = **템플릿 1건 + 어휘 등록**이며,
Negotiator 클래스 추가나 협상 전략 코드 변경이 아니다. L1·L2가 이 스펙을 해석하는 구조여야
이 성질이 성립한다.

## 3. L2 — 세션 컴파일러

### 3.1 입출력

| 구분 | 항목 |
|---|---|
| 입력 | 노드 의제(issue 목록), 상위 세션의 확정 결과, 로컬 사용자 컨텍스트, issue 어휘 카탈로그 |
| 출력 | NegMAS `OutcomeSpace`, 로컬 `ufun`, mechanism 파라미터(`n_steps`, `time_limit` 등) |

### 3.2 자원 상한 강제 지점

NegMAS는 `to_discrete(levels, max_cardinality)`, `limit_cardinality`, `sample` 같은 **도구**는 제공하지만,
"이 협상의 공간은 N개를 넘지 않는다"를 **강제하는 지점**은 제공하지 않는다.
그 지점을 여기에 둔다.

컴파일러가 수행하는 축소 수단:

- **상위 바인딩 적용** — 상위 합의로 이미 결정된 축은 값이 고정되거나 후보가 줄어든다
- **로컬 컨텍스트 적용** — 사용자 캘린더·위치·예산으로 애초에 불가능한 값을 제외한다
- **어휘 이산화 수준 결정** — 시간 슬롯을 30분/1시간/2시간 중 무엇으로 자를지 결정한다
- **상한 초과 시 처리** — 위 세 가지로도 상한을 못 맞추면, 노드를 더 작은 노드로 분할하거나
  이산화 수준을 낮춘다

**중요:** 이 축소는 outcome space가 **실체화되기 전에** 일어나야 한다.
곱집합을 만든 뒤 필터링하면 이미 메모리를 쓴 뒤다.

### 3.3 프라이버시 경계

컴파일러는 원본 사용자 데이터에서 두 갈래를 만든다.

- **ufun** — 선호 강도, 유보값, 불가능한 이유. 로컬에만 존재하며 전송되지 않는다.
- **issue 값 어휘** — 상대에게 보낼 수 있는 단어의 전체 집합. 여기 없는 값은 보낼 수 없다.

즉 **보낼 수 있는 어휘의 상한도 컴파일러가 정한다.**

## 4. L3 — 세션 런타임

### 4.1 NegMAS 매핑

| 필요 기능 | NegMAS 대응 |
|---|---|
| 다자 협상 | `SAOMechanism(max_n_agents=…)` |
| 도중 참여·이탈 | `dynamic_entry=True`, `ResponseType.LEAVE` |
| 종료 조건 | `n_steps`, `time_limit` |
| Offer + 부가 데이터 | `ExtendedOutcome(outcome, data={...})` |
| 유효성 강제 | `check_offers`, `enforce_issue_types` |
| 후보 탐색 | `SamplingInverseUtilityFunction` (전량 정렬형 대신 샘플링형 사용) |

### 4.2 constraint hint 처리

raw.md 15행의 의미론을 그대로 구현한다.

| 방향 | 동작 |
|---|---|
| 발신 | Offer에 issue별 `fixed` / `relaxable` 표시를 붙여 보낸다 |
| 수신 | `fixed` 표시된 issue는 그 Offer의 값을 고정 조건으로 해석하고, **후보 집합에서 해당 값을 만족하지 않는 outcome을 제외**한다 |
| counter-offer | fixed 값은 유지하고 `relaxable` issue만 변경한다 |
| 만족 불가 | 해당 Offer 또는 계획 분기를 거절한다 |

**분리해 둘 것:** 힌트는 **제안 후보 공간**을 줄인다. **수락·거절 판단은 자기 ufun과 내부 제약이 결정한다.**
두 층위를 섞으면 상대가 보낸 표시가 자기 유보값을 무력화한다.

**메모리 효과:** 힌트를 정렬 가중치로 반영하면 후보 집합 크기가 줄지 않아 OOM 대책이 되지 않는다.
후보 집합 자체를 잘라야 raw.md 13~14행의 목적(OOM 완화)이 달성된다.

### 4.3 미정의 항목

raw.md가 규정하지 않아 별도 결정이 필요하다. 상세는 격차 문서 §5.2 참조.

- 힌트가 해당 세션에만 유효한가, 후속 노드까지 승계되는가
- 발신자가 이전 `fixed`를 철회하는 절차가 있는가
- N자 협상에서 참여자들이 같은 issue에 서로 다른 `fixed` 값을 보냈을 때의 처리
- 힌트 적용 결과 자기 후보 집합이 비었을 때, 세션 결렬인가 계획 분기 거절인가

## 5. L4 — 전역 효용·확정

### 5.1 왜 필요한가

NegMAS의 ufun은 **하나의 OutcomeSpace 위**에 정의된다. 세션이 여러 개면 세션마다 별개 ufun이고,
각 세션이 자기 공간 안에서 최적을 찾아도 **계획 전체가 최적이라는 보장이 없다.**

예: 영화 세션에서 양측 효용이 가장 높은 상영을 확정했는데, 그 시간대 그 지역에는
양측이 모두 받아들일 식당이 없어 식사 세션이 결렬되는 상황.

### 5.2 책임

- **전역 효용 유지** — 계획 전체(확정 노드 + 미확정 노드의 기대치)에 대한 사용자 효용을 관리한다
- **확정·보류·철회** — 노드 합의를 확정할지, 후행 결과를 볼 때까지 보류할지, 철회하고 재협상할지 결정한다
- **후행 노드 활성화** — 확정 결과를 바인딩에 실어 L2로 넘긴다

### 5.3 최적성 평가의 위치

계획 최적성 지표(파레토·Nash 근접도)는 **모든 참여자 ufun + outcome 전량 열거**를 요구하므로
온디바이스 런타임에서 계산할 수 없다(격차 문서 G5). 따라서 L4는 **확정 합의를 기록만** 하고,
평가는 오프라인 벤치마크에서 수행한다.

측정할 두 지표:

- **세션 최적성** — 각 세션의 파레토/Nash 최적성 (해당 세션 공간 기준)
- **계획 최적성** — 계획 전체를 하나의 결합 결과로 보고, 결합 공간의 파레토 프론티어 기준으로 계산

## 6. 실행 흐름 (영화 → 식사 예시)

1. IDS가 Intent를 감지하고 플랜 템플릿을 선택 → L1이 계획 그래프를 만든다 (영화 노드 → 식사 노드 → 승인 게이트)
2. L2가 **영화 노드**를 컴파일한다. 로컬 컨텍스트로 어휘를 줄이고 공간 상한을 적용해 OutcomeSpace와 ufun을 만든다
3. L3가 `SAOMechanism` 세션을 실행한다. Offer에 constraint hint를 실어 양측이 서로의 공간을 줄인다
4. 합의가 나오면 L4가 이를 받아 전역 효용을 갱신하고 확정 여부를 결정한다
5. 확정되면 간선의 바인딩(영화.종료시각 → 식사.slot 하한 / 영화.상영관 → 식사.area 후보)을 적용해
   **식사 노드**를 L2로 넘긴다
6. 2~5를 반복한다
7. 모든 노드가 확정되면 승인 게이트에서 사용자 확인을 받고 Sub-Agent가 실행한다

## 7. 열린 결정점

본 초안은 아래 세 항목에 대해 **결론을 내리지 않았다.** 각각 실무적으로 성립하는 두 안이 있고,
품질 특성 간 트레이드오프가 뚜렷하다.

### D1. 계획 그래프 실행 방식 — 순차 확정형 vs 결합 협상형

- **순차 확정형:** 상위 노드를 확정한 뒤 그 결과를 하위 의제에 주입해 순차 실행.
  세션당 공간이 작아 메모리에 유리하나, 지역 최적에 갇히고 철회·재협상 메커니즘이 필요하다.
  총 소요가 노드 수만큼 누적되어 계획의 실효 기한을 넘길 위험이 있다.
- **결합 협상형:** 의존 노드들의 의제를 하나의 결합 공간으로 묶어 동시 협상.
  계획 최적성에 유리하나, 공간이 노드 수에 대해 곱셈으로 증가한다(격차 문서 §4 산정).

**긴장:** 결과 최적성(raw.md가 지목한 핵심 QA) ↔ 자원 사용량(OOM).

### D2. outcome space 축소 책임 — 사전 컴파일 축소 vs 힌트 기반 런타임 축소

- **사전 컴파일 축소:** L2가 협상 시작 전에 어휘를 잘라 공간 상한을 결정론적으로 보장한다.
  상대 제약을 모르는 상태에서 자르므로 합의 가능 영역을 미리 제거할 위험이 있다.
- **힌트 기반 런타임 축소:** 넓게 시작해 수신 힌트마다 공간을 잘라 나간다.
  합의 영역 보존에 유리하나 최악 메모리가 시작 시점에 발생하고 상한 보장이 없다.

**긴장:** 합의 가능성·최적성 ↔ 메모리 상한 보장.

### D3. 시나리오 확장 방식 — 선언적 템플릿 카탈로그 vs LLM 동적 플랜 생성

- **선언적 템플릿:** 도메인별 템플릿과 어휘를 사전 정의. 공간 상한과 어휘 민감도를 검증할 수 있으나
  커버리지가 카탈로그에 묶인다.
- **LLM 동적 생성:** Orchestrator가 IDS intent에서 계획 그래프와 어휘를 생성. 커버리지가 열리고
  과제의 "동적 Agent/Tool 생성" 가설과 정합하나, 생성된 어휘의 크기와 민감도가 통제되지 않는다.

**긴장:** 기능 확장성 ↔ 자원 예측가능성 + 기밀성.
