# 37. 설계 문제 — 합의 확정 구조 (Agreement Commit)

> 문제 정의·의존: [`30`](30-설계-문제-총괄.md) §30.1 · 평가 축: [`20`](20-핵심-QA-확정.md)의 확정 QA 10개
> 관련 CFR: F1 합의 확정 전파·인계 · D1 승인 수집 · 관련 계층: 합의 종결 정합(L4, [`09`](09-Functional-Correctness-정의.md))

---

## 1. 문제 정의

협상이 타결되어 완결 규칙이 충족된 순간, **확정 당사자 전원이 동일한 합의 레코드를 빠짐없이 갖게 만들어야 한다.** 한 명이라도 다른 내용을 갖거나 못 받으면, 이후 각자의 실행(캘린더 등록 — 실행 자체는 과제 범위 밖)이 실세계에서 충돌한다.

이것이 라운드 중의 제안 전파([`31`](31-제안-토폴로지.md))와 다른 문제인 이유: 제안은 **자주 보내고 일부가 유실되어도 다음 라운드에서 복구**되지만, 확정은 **단 한 번이고 반쯤 전달된 상태가 있어서는 안 된다** — "일부만 확정을 아는" 상태가 곧 결함이다. 요구 품질이 다르므로 구조 대안도 따로 비교한다.

## 2. 전제와 제약 (모든 대안에 공통)

- 확정 대상과 당사자 범위는 완결 규칙([`32`](32-완결-규칙-실행-구조.md))의 판정 결과로 이미 정해져 있다 — 본 문제는 그 결과를 **전파·확정 짓는 구조**만 다룬다.
- 승인하지 않은 참여자에게는 확정 효력이 미치지 않는다 (절대 제약).
- 확정 레코드는 서명 가능한 형식이며, 확정 후 외부 실행 계층으로 인계된다 (인계 이후는 범위 밖).

## 3. 대안

### 대안 A — 2단계 확정형 (Two-phase Commit)

**도식**: [`drawio/37-A-2단계-확정형.drawio`](drawio/37-A-2단계-확정형.drawio)

**구조.** **Commit Coordinator**가 확정안을 전 당사자에게 배포하고(1단계 — prepare), 전원의 ACK가 모이면 commit을 선언·기록하고 통지한다(2단계). ACK가 하나라도 빠지면 확정은 성립하지 않고 재시도하거나 이상 처리로 넘어간다.

| Component | 위치 | 역할 |
|---|---|---|
| Commit Coordinator | 확정 단말 | 확정안 배포, commit/abort 결정 |
| Ack Collector | 확정 단말 | 당사자들의 ACK를 수집하고 시한을 관리한다 |
| Durable Commit Log | 확정 단말 | commit 결정을 내구성 있게 기록한다 |
| Ack Responder | 각 당사자 단말 | 확정안을 검증하고 ACK를 보낸다. commit 선언을 받으면 로컬에 확정 기록 |

**정상 동작:** prepare 배포 → 전원 ACK → commit 선언·기록 → 전원 통지. **오류 상황:** Coordinator가 commit 선언 직전에 죽으면 "확정인지 아닌지"가 잠시 불명해진다 — 복구 시 Commit Log를 기준으로 판정한다.

### 대안 B — 서명 순환형 (Signature Chain)

**도식**: [`drawio/37-B-서명-순환형.drawio`](drawio/37-B-서명-순환형.drawio)

**구조.** 확정 문서가 당사자들을 정해진 순서로 순회하며 각자 검증 후 **서명을 첨부**한다. **마지막 서명이 붙는 순간 문서 자체가 확정의 증명**이 되고, 완성본이 전원에게 배포된다. 별도의 선언자가 없다.

| Component | 위치 | 역할 |
|---|---|---|
| Signing Relay | 각 당사자 단말 | 문서를 검증하고 서명을 첨부해 다음 순번에 전달한다 |
| Chain Validator | 각 당사자 단말 | 앞 서명들의 유효성을 검증한다 — 위조·누락 서명 검출 |

**정상 동작:** 문서 순환 → 서명 누적 → 전원 서명 완료 = 확정 → 완성본 배포. **오류 상황:** 순환 중 한 명이 무응답이면 확정이 그 자리에서 멈춘다 — 시한 후 이상 처리(확정 실패 선언)로 넘어간다. 부분 서명 문서는 정의상 "미확정"이라 애매한 상태가 없다.

### 대안 C — 공증 로그형 (Replicated Commit Ledger)

**도식**: [`drawio/37-C-공증-로그형.drawio`](drawio/37-C-공증-로그형.drawio)

**구조.** 당사자 전원이 **append-only 확정 로그의 사본**을 유지한다. 확정 레코드는 로그 복제 프로토콜로 전 사본에 동일하게 기록되며, 전 사본 합치가 확인된 시점이 확정이다.

| Component | 위치 | 역할 |
|---|---|---|
| Replicated Commit Ledger | 각 당사자 단말 | 확정 로그의 사본을 유지한다 |
| Log Sync | 각 당사자 단말 | 레코드를 복제하고 사본 간 합치를 확인한다 |

**정상 동작:** 레코드 제안 → 복제·합치 확인 → 전 사본 동일 기록 = 확정. **오류 상황:** 어느 단말이 죽어도 남은 사본에 기록이 있어 복귀 시 따라잡으면 된다 — 대신 합치 확인의 왕복이 매번 든다.

## 4. QA Trade-off 평가표

(SC-의제·Confidentiality 축은 세 대안 모두 (0) — 확정 구조는 의제 조합과 무관하고, 확정 레코드는 이미 전원이 합의한 내용이라 새로운 노출이 없다.)

| QA | A. 2단계 확정형 | B. 서명 순환형 | C. 공증 로그형 |
|---|---|---|---|
| Functional Correctness | (0)<br>정상 경로에서는 전원 동일 확정이 보장되나, commit 선언 직전 Coordinator 사망 시 "일부만 확정 인지" 창이 구조적으로 존재한다 (Commit Log 복구로 닫음) | (+)<br>부분 확정 상태가 정의상 존재할 수 없다 — 서명이 다 붙었거나(확정) 아니거나(미확정) 둘뿐이며, 문서 스스로 증명한다 | (+)<br>전 사본 합치 후에만 확정 — 사본 대조로 불일치가 즉시 검출된다 |
| Fault Tolerance | (−)<br>Coordinator가 확정 절차의 단일 실패점이다 | (−)<br>순환 중 한 명의 무응답이 확정 절차 전체를 세운다 | (+)<br>어느 단말이 죽어도 남은 사본으로 절차가 이어지고, 복귀자는 따라잡으면 된다 |
| Analysability | (+)<br>확정 이력이 Commit Log 한 곳에 시간 순으로 남는다 | (+)<br>서명 체인 자체가 "누가 언제 확인했나"의 증적이다 | (0)<br>기록은 완전하나 사본 여러 개를 대조해 읽는 절차가 붙는다 |
| Scalability (참여자 수) | (+)<br>배포·ACK의 2왕복 — 왕복 수가 인원과 무관하게 고정이다 | (−)<br>서명이 순차라 확정 시간이 인원수에 정비례한다 | (−)<br>복제·합치 확인 메시지가 인원에 따라 늘어난다 |
| Scalability (의제 조합) | (0)<br>무관 | (0)<br>무관 | (0)<br>무관 |
| Time Behaviour | (+)<br>2왕복으로 끝나 확정이 가장 빠르다 | (−)<br>순차 순환이라 확정이 가장 느리다 | (0)<br>복제는 병렬이지만 합치 확인 왕복이 추가된다 — 중간 |
| Recoverability | (−)<br>Coordinator가 죽으면 확정 여부 판정을 위해 Commit Log 복구부터 해야 한다 | (0)<br>복원할 것이 "문서 + 어느 순번까지 서명됐나"로 단순하다 | (+)<br>기록이 전원 사본으로 남아 있어 무엇이 죽어도 확정 이력이 유실되지 않는다 |
| Resource Utilization | (+)<br>부담이 확정 단말에 잠깐 집중될 뿐 총량이 가장 작다 | (0)<br>한 번에 한 단말만 서명 작업 — 총량은 작으나 시간이 길다 | (−)<br>전원이 로그 사본을 유지·동기화하는 상시 비용을 진다 |
| Confidentiality | (0)<br>무관 | (0)<br>무관 | (0)<br>무관 |
| Adaptability | (0)<br>확정 절차 변경이 확정 단말 한 곳의 일이다 | (0)<br>문서 규칙 변경으로 대응 — 순환 순서는 구성 항목 | (−)<br>복제 프로토콜의 변경은 전 단말 동시 교체라 가장 무겁다 |

## 5. 배타성 확인

세 대안은 "무엇이 확정의 증거인가"가 다르다 — Coordinator의 commit 선언(A) / 전원 서명이 붙은 문서(B) / 전 사본의 합치된 로그(C). 확정의 증거는 하나여야 한다: 둘 이상을 두면 두 증거가 어긋났을 때(선언은 됐는데 서명이 미완) 어느 쪽이 참인지 정할 상위 기준이 또 필요해지고, 그 순간 "단일한 확정"이라는 문제의 목적 자체가 깨진다. component도 대체 관계다(Commit Log vs 서명 문서 vs 복제 로그는 같은 역할의 다른 구현).

## 6. 비지배 확인

- A는 FC·FT·Rec에서 진다 (우위: SC-참여자·TB·RU) ✓
- B는 FT(C 대비)·SC-참여자·TB에서 진다 (우위: FC·Analy·Rec(A 대비)) ✓
- C는 SC-참여자·RU·AD·Analy(A·B 대비)에서 진다 (우위: FT·Rec) ✓

## 7. 다른 문제와의 결정 의존

- **[`31`](31-제안-토폴로지.md)**: A는 31-A(star)의 Coordinator를 재사용하면 배포 경로가 공짜다. B는 31-C(ring)의 순환 경로와 결이 같다. 31-B(mesh)에서는 C의 복제 경로가 기존 연결을 재사용한다.
- **[`32`](32-완결-규칙-실행-구조.md)**: 32-C(서명 누적형)를 골랐다면 본 문제의 B(서명 순환형)와 문서·서명 체계를 공유해 성립 판정과 확정을 한 절차로 합칠 수 있다 — 이 결합 이득은 32와 37을 함께 결정할 때 고려한다.
- **[`35`](35-이탈-무응답-처리-구조.md)**: 확정 절차 중의 이탈은 일반 라운드보다 민감하다 — 확정 중 이탈자를 당사자에서 제외할지(완결 규칙 재적용) 확정을 중단할지의 정책 연결이 필요하다.
