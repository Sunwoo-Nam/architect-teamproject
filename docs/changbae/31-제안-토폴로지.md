# 31. 설계 문제 — 제안 토폴로지 (Proposal Topology)

> 문제 출처: [`08`](08-핵심-QA-중요도-난이도-평가.md) §8.4 질문 1 · 채택 결정: [`30`](30-설계-문제-총괄.md) §30.1
> 평가 축: [`20`](20-핵심-QA-확정.md)의 확정 QA 10개
> 관련 CFR: B1 세션 구성 · B2 라운드 실행 · B3 메시지 전파

---

## 1. 문제 정의

다자 협상에서는 라운드마다 이런 일이 반복된다: 각 참여자의 Agent가 자기 제안을 만들고, 그 제안이 다른 참여자들에게 전달되고, 각자가 받은 제안을 평가해서 수락/거절/역제안을 내고, 그 결과가 다시 모두에게 알려져야 다음 라운드로 넘어간다.

여기서 정해야 하는 것은 **"제안과 응답이 어떤 경로로 오가는가"** 이다. 즉:

- 제안을 **누가 모으는가** — 한 단말이 모으는가, 아무도 모으지 않고 각자 주고받는가
- 모은 제안을 **누가 누구에게 전달하는가** — 한 곳에서 일괄 배포하는가, 전원이 전원에게 직접 보내는가, 순서대로 넘기는가
- "지금 라운드가 어디까지 진행됐는가"라는 **라운드 상태를 누가 알고 있는가**

이 선택을 잘못하면 생기는 일: 참여자마다 서로 다른 협상 상태를 보게 되어 잘못된 판정이 나오거나(정확성 훼손), 참여자가 늘 때 메시지가 폭증하거나(확장성 훼손), 한 단말의 고장이 협상 전체를 멈추거나(감내성 훼손), 모든 참여자에게 모든 제안이 노출되어 선호가 유추된다(기밀성 훼손). **어떤 경로 구조를 골라도 이 네 가지를 동시에 다 잘할 수는 없다** — 그래서 이것은 trade-off 결정이다.

## 2. 전제와 제약 (모든 대안에 공통)

- 협상 알고리즘은 NegMAS 기반이다: 각 Agent는 자기 옵션을 효용(Ufun)으로 점수화해 최고점 후보를 제안하고, 받은 제안은 자기 threshold와 비교해 수락/거절을 판정한다. **이 알고리즘 부분은 모든 대안에서 동일하며, 대안이 바꾸는 것은 제안이 오가는 경로뿐이다.**
- 모든 Agent는 사용자 개인 단말(Android)에서 온디바이스로 실행된다. 서버를 경유하는 중계는 본 문제의 대안에 포함하지 않는다 (온디바이스 중심 원칙, 02 §2.5.2).
- 메시지는 A2A 프로토콜 형식을 따르고, 전 구간 암호화된다.
- 위임 범위 검사(운용 제약)와 최종 사용자 승인은 어느 대안에서든 동일하게 수행된다 — 20 §20.3의 절대 제약.

## 3. 대안

### 대안 A — Coordinator 집계형 (Star)

**도식**: [`drawio/31-A-Coordinator-집계형.drawio`](drawio/31-A-Coordinator-집계형.drawio)

**구조.** 협상을 시작한 개시자의 단말이 **Session Coordinator** 역할을 맡는다. 모든 참여자 단말은 Coordinator와만 통신하고, 참여자끼리는 직접 통신하지 않는다. 별 모양(star)의 연결이다.

**Component 목록과 역할:**

| Component | 위치 | 역할 |
|---|---|---|
| Round Controller | 개시자 단말 | 라운드의 시작·마감을 선언한다. 마감 시한(timeout)을 관리하고, 응답이 다 모이면 다음 라운드로 넘긴다 |
| Proposal Aggregator | 개시자 단말 | 참여자들이 제출한 제안·응답을 모아서 하나의 "라운드 결과"로 정리한다 |
| Round Result Distributor | 개시자 단말 | 정리된 라운드 결과를 전 참여자에게 일괄 배포한다 |
| Session State Store | 개시자 단말 | 협상의 기준 상태(현재 라운드, 살아있는 후보, 참여자별 응답 현황)를 보관한다 — **세션의 진실(source of truth)은 여기 하나다** |
| Negotiation Agent | 각 참여자 단말 | NegMAS 기반 제안 생성·평가 (모든 대안 공통) |
| Coordinator Link | 각 참여자 단말 | Coordinator와의 단일 연결로 제안을 제출하고 라운드 결과를 수신한다 |

**정상 동작 (라운드 1회):** ① Round Controller가 "라운드 k 시작"을 배포한다 → ② 각 참여자의 Negotiation Agent가 제안(또는 수락/거절)을 만들어 Coordinator Link로 제출한다 → ③ Proposal Aggregator가 전원 응답을 모으고(시한 내 미응답은 Round Controller가 처리) 라운드 결과를 만든다 → ④ Distributor가 결과를 전원에게 배포한다 → ⑤ 전원이 동일한 결과를 받은 상태에서 다음 라운드가 시작된다.

**오류 상황:** 참여자 1명의 메시지가 유실되면 Coordinator가 재요청한다 — 나머지 참여자는 영향을 모른다. 그러나 **Coordinator 단말 자체가 꺼지면 모든 경로가 끊겨 협상 전체가 멈춘다.** 이 경우 세션은 Recoverability 절차(Coordinator 복구 또는 역할 이관)로 넘어간다.

### 대안 B — 전원 브로드캐스트형 (Full Mesh)

**도식**: [`drawio/31-B-전원-브로드캐스트형.drawio`](drawio/31-B-전원-브로드캐스트형.drawio)

**구조.** 모으는 사람이 없다. 모든 참여자 단말이 서로 직접 연결되어, 각자 자기 제안·응답을 **나머지 전원에게 직접 보낸다**. 그물 모양(full mesh)의 연결이다. 세션의 기준 상태를 보관하는 단일 장소가 없고, **각 단말이 자기 로컬 뷰를 유지**한다.

**Component 목록과 역할:**

| Component | 위치 | 역할 |
|---|---|---|
| Broadcast Messenger | 각 참여자 단말 | 자기 제안·응답을 나머지 N−1명 전원에게 직접 전송하고, N−1명으로부터 수신한다 |
| Local Round Tracker | 각 참여자 단말 | 수신한 메시지들로 "지금 라운드가 어디까지 왔는가"를 스스로 계산한다 — 기준 상태가 없으므로 각자 추적한다 |
| State Convergence Checker | 각 참여자 단말 | 메시지 도착 순서가 단말마다 다를 수 있으므로, 라운드 경계마다 참여자들의 뷰가 일치하는지 서로 요약값(hash)을 교환해 확인하고, 어긋나면 재정렬한다 — **이 대안에만 필요한 추가 component** |
| Negotiation Agent | 각 참여자 단말 | (공통) |

**정상 동작:** ① 각자가 제안을 만들어 전원에게 브로드캐스트한다 → ② 각 단말의 Local Round Tracker가 "전원 것이 도착했다"를 확인하면 평가·응답을 다시 브로드캐스트한다 → ③ 라운드 경계에서 Convergence Checker가 뷰 일치를 확인하고 다음 라운드로 넘어간다.

**오류 상황:** 참여자 1명이 꺼져도 나머지끼리의 연결은 살아 있어 통신은 지속된다 — 단일 실패점이 없다. 대신 메시지 도착 순서 차이로 **단말마다 다른 상태를 보게 되는 위험**이 상존하고, Convergence Checker가 이를 잡아내 재동기화해야 한다.

### 대안 C — 순차 릴레이형 (Ring)

**도식**: [`drawio/31-C-순차-릴레이형.drawio`](drawio/31-C-순차-릴레이형.drawio)

**구조.** 참여자를 고정된 순서(예: 개시자 → 참여자1 → 참여자2 → … → 개시자)로 고리(ring) 모양으로 잇는다. **"협상 문서(Negotiation Baton)" 하나**가 이 고리를 따라 돈다 — 문서에는 현재까지의 제안·평가·응답이 전부 담겨 있다. 문서를 받은 단말만 그 시점에 활동하고, 자기 제안·평가를 문서에 덧붙여 다음 순번에게 넘긴다.

**Component 목록과 역할:**

| Component | 위치 | 역할 |
|---|---|---|
| Relay Handler | 각 참여자 단말 | 앞 순번에게서 협상 문서를 수신하고, 처리 후 다음 순번에게 전달한다. 다음 순번이 응답 없으면 시한 후 그 다음 순번으로 건너뛴다 |
| Baton Processor | 각 참여자 단말 | 받은 문서 안의 최신 제안들을 평가하고, 자기 제안·응답을 문서에 첨부한다 |
| Ring Order Registry | 전 단말 (세션 시작 시 배포) | 고리의 순서 정의 — 누가 다음 순번인지 |
| Negotiation Agent | 각 참여자 단말 | (공통) |

**정상 동작:** ① 개시자가 협상 문서를 만들어 첫 제안을 담고 다음 순번에게 보낸다 → ② 받은 사람이 문서 속 제안들을 평가하고 자기 응답·제안을 첨부해 다음으로 넘긴다 → ③ 문서가 고리를 한 바퀴 돌면 라운드 1회가 끝난 것이고, 문서에는 전원의 제안·응답이 순서대로 누적되어 있다.

**오류 상황:** 문서를 쥔 단말이 응답 없으면 앞 순번이 시한 후 건너뛰어 다음 순번에게 직접 보낸다 — 다만 **그 시한만큼 협상 전체가 기다린다** (한 번에 한 단말만 진행하는 구조라, 어느 한 곳의 지연이 곧 전체의 지연이다). 문서가 유실되면 마지막으로 문서를 보유했던 단말의 사본에서 복원한다.

## 4. QA Trade-off 평가표

각 셀: **판정(+/0/−)** 과 그 이유. (SC-의제 축은 세 대안 모두 0 — 의제 조합의 처리는 각 단말 내부의 옵션 생성·가지치기 문제여서 통신 경로 선택과 무관하다.)

| QA ([`20`](20-핵심-QA-확정.md)) | A. Coordinator 집계형 | B. 전원 브로드캐스트형 | C. 순차 릴레이형 |
|---|---|---|---|
| Functional Correctness | **+** 라운드 결과를 한 곳에서 만들어 일괄 배포하므로 전원이 항상 동일한 상태를 보고 판정한다 — 상태 불일치로 인한 오판정이 구조적으로 차단됨 | **−** 도착 순서 차이로 단말마다 다른 뷰를 볼 수 있고, Convergence Checker가 놓치면 서로 다른 상태에서 수락/거절을 판정할 위험 | **+** 항상 단 하나의 협상 문서가 돌므로 전원이 같은 문서 이력을 본다 — 동시 수정 충돌이 구조적으로 없음 |
| Fault Tolerance | **−** Coordinator 단말이 단일 실패점 — 이 단말이 꺼지면 협상 전체가 멈춘다 (참여자 1명의 오류는 잘 흡수) | **+** 단일 실패점 없음 — 1명이 꺼져도 나머지끼리 통신이 유지되어 협상을 이어갈 수 있다 | **−** 문서를 쥔 단말이 곧 그 순간의 단일 실패점 — 지연·무응답이 즉시 전체 대기로 이어진다 |
| Analysability | **+** 모든 메시지가 Coordinator 한 점을 지나므로 협상 전체 이력이 한 곳에 모인다 — 재구성이 가장 쉽다 | **−** 메시지가 N² 경로로 흩어져 완전한 이력이 어느 단말에도 없다 — N개의 로그를 수집해 상관 분석해야 재구성 가능 | **+** 처리 순서가 항상 결정적(고리 순서)이고 문서에 이력이 누적되므로 재구성이 단순하다 |
| Scalability (참여자 수) | **0** 메시지 수는 참여자당 제출 1 + 배포 1로 선형 — 기준 충족. 단 Coordinator 한 단말의 처리·연결 부하가 N에 비례해 집중된다 | **−** 라운드당 메시지가 N×(N−1)로 **제곱** 증가 — 참여자 2배에 메시지 4배로, 20의 선형 기준을 위반할 위험이 가장 크다 | **−** 메시지 수는 선형이지만 **시간이 직렬** — 한 번에 한 단말만 진행하므로 라운드 시간이 N에 정비례해 늘어난다 |
| Scalability (의제 조합) | **0** (경로 선택과 무관) | **0** (동일) | **0** (동일) |
| Time Behaviour | **0** 라운드당 2단계(제출→배포) — 수집은 병렬이라 빠른 편이나 B보다 한 단계 많다 | **+** 1단계 직접 전달 — 라운드 왕복이 가장 짧다 | **−** 라운드 1회에 N단계 직렬 — 셋 중 가장 느리고, N이 늘수록 더 느려진다 |
| Recoverability | **0** 기준 상태가 한 곳에 있어 참여자 단말의 복구는 쉽다(그 상태를 받아오면 끝). 반면 Coordinator 자신이 죽으면 세션 전체의 복구·역할 이관이 필요해 가장 무거운 복구가 된다 — 상쇄 | **−** 복구의 기준이 되는 상태가 없다 — N개의 로컬 뷰를 모아 맞춰보고 재동기화해야 하므로 복구 절차가 가장 복잡하다 | **+** 복원할 것이 "협상 문서 + 고리의 현재 위치" 하나뿐 — 복구가 가장 단순하다 |
| Resource Utilization | **−** 자원 부담이 개시자 한 사람의 단말에 쏠린다 — 그 사용자의 배터리·메모리 희생이 크고, 온디바이스 전제에서 형평 문제도 생긴다 | **−** 전 단말이 N−1개 연결을 유지하고 N−1건씩 수신 처리 — 모든 단말의 부담이 커진다 | **+** 어느 시점이든 활동 중인 단말이 1대뿐이고 나머지는 대기 — 전체 자원 소모가 가장 적다 |
| Confidentiality | **+** 참여자의 원 제안이 Coordinator에게만 가고, Coordinator가 집계·요약된 결과만 배포하도록 구성할 수 있어 **참여자 간 상호 노출을 구조적으로 줄일 수 있다** (단, 전원의 정보가 Coordinator 한 단말에 집중되는 위험은 [`34`](34-정보-공개-구조.md)에서 별도로 다룬다) | **−** 모든 제안·수락이 전 참여자에게 원문 그대로 보인다 — 역추론에 쓸 재료가 가장 많이 노출된다 | **0** 제안은 다음 순번에게만 직접 가지만, 문서에 누적된 앞 순번들의 제안·응답 이력이 뒤 순번에게 보인다 — 중간 수준 |
| Adaptability | **+** 라운드 규칙·순서 변경이 Coordinator 한 곳의 변경으로 끝난다 — 새 시나리오 수용 시 바꿀 곳이 하나다 | **−** 규칙 변경 시 전 참여자 단말의 로직이 동시에 같은 버전이어야 한다 — 배포·버전 불일치 문제가 시나리오 확장을 어렵게 한다 | **0** 규칙 정의를 문서에 실어 보낼 수 있어 변경 전파는 쉬우나, "순서대로 한 명씩"이라는 진행 방식 자체가 구조에 박혀 있어 동시 제안형 시나리오는 표현할 수 없다 |

## 5. 배타성 확인

하나의 협상 세션에서 메시지가 오가는 위상(topology)은 하나만 성립한다 — 같은 라운드에서 "Coordinator가 모아서 배포하면서 동시에 전원이 서로 직접 브로드캐스트하고 동시에 문서가 고리를 도는" 구조는 정의상 불가능하다. 세 대안은 연결의 모양 자체(별/그물/고리)가 다르고, 그에 따라 필요한 component(Aggregator vs Convergence Checker vs Relay Handler)가 서로 대체 관계다. 상황에 따라 위상을 바꾸는 혼합형(예: 평시 star, Coordinator 장애 시 mesh 전환)은 논리적으로 가능하나 두 구조의 component를 모두 구현·검증해야 하므로 별개의 제4안이며, 복잡도 대비 이득이 불명확해 본 문서에서는 채택하지 않았다.

## 6. 비지배 확인

- A는 FT·RU·TB에서 진다 (B가 FT·TB 우위, C가 RU·Rec 우위) → A가 전부 이기지 않음
- B는 FC·Analy·SC-참여자·Rec·RU·Conf·AD에서 진다 → B가 전부 이기지 않음 (B의 우위는 FT·TB)
- C는 FT·SC-참여자·TB에서 진다 → C가 전부 이기지 않음 (C의 우위는 Rec·RU)

어느 대안도 10개 축 전부에서 다른 대안과 같거나 우수하지 않다 ✓.

## 7. 다른 문제와의 결정 의존

- **[`33`](33-이탈-무응답-처리-구조.md) 이탈·무응답 처리**: 이탈을 "누가 감지하는가"가 본 결정에 의존한다 — A면 Coordinator가 자연스러운 감지 주체가 되고, B면 분산 감지가 필요하며, C면 앞 순번의 시한 관리가 감지를 겸한다.
- **[`36`](36-합의-확정-구조.md) 합의 확정 구조**: 확정 레코드를 제안 채널로 전파할지, 별도의 확정 전용 절차를 둘지가 본 결정의 영향을 받는다.
- **[`35`](35-개입-시점-모델.md) 개입 시점 모델**: checkpoint의 자연스러운 경계인 "라운드"의 정의가 대안마다 다르다 — A·B는 전원 응답 수집 완료 시점, C는 문서가 한 바퀴 돈 시점.
