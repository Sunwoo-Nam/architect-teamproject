# 53. FR 재도출 — 협상 범위 한정, VoC 매핑

> **배경**: [`52`](52-Stakeholder-재편-VoC.md)의 재편 Stakeholder·VoC로부터 FR을 재도출한다 (사용자 지시, 2026-08-13).
> **작성 원칙**:
> ① **협상 내용과 관련된 기능만** 포함한다 (과제 관리·개발 지원·학습 루프는 52 §52.3 보류).
> ② **해법 중립** — "설계를 다르게 골랐다면 무효가 되는 문장"은 FR이 아니다. 요구는 결과(무엇이 보장되어야 하는가)로 쓰고, 방법(어떻게)은 DP로 내려보낸다. 이 원칙으로 배제·재작성한 내역은 §53.2.
> ③ 각 FR은 근거 VoC 인덱스를 표기한다 (1:1일 필요 없음).
> **기존 문서와의 관계**: [`../04-FR.md`](../04-FR.md)(FR-IDS/FR-MAF 체계)·[`02`](02-Stakeholder별-FR-도출.md)(구 Stakeholder 100건)와 별개의 신규 도출이다. 정제 완료 후 정본 관계를 정리한다.

## 53.1 FR 목록 — 25건 (협상 라이프사이클 순)

| ID | 단계 | Functional Requirement | VoC 매핑 |
|---|---|---|---|
| FR-01 | 개시 | 시스템은 명시 지시 또는 대화 맥락 감지로 다자 협상을 개시하고 참여자를 초대하는 기능을 제공해야 한다 | EU-V1 |
| FR-02 | 개시 | 시스템은 초대를 수신하고 참여를 수락·거절하는 기능을 제공해야 한다 | EU-V2, EU-V4 |
| FR-03 | 개시 | 시스템은 위임 범위·수락 바닥선·정보 공개 범위를 사전 설정하는 기능을 제공해야 한다 | EU-V2, EU-V3, SP-V1 |
| FR-04 | 선호 | 시스템은 사용자 선호·제약을 수집해 협상에 반영하는 기능을 제공해야 한다 | PD-V2 |
| FR-05 | 선호 | 시스템은 추론한 선호를 사용자가 확인·교정할 수 있게 해야 하며, 불확실한 선호를 임의 확정하지 않아야 한다 | PD-V5, PD-V2 |
| FR-06 | 선호 | 시스템은 사용자가 자신의 선호 데이터를 열람·수정·삭제하는 기능을 제공해야 한다 | PD-V3, EU-V2 |
| FR-07 | 수행 | 시스템은 참여자 전원의 선호·제약을 반영하여 전원이 수용 가능한 안을 자율적으로 탐색·도출해야 한다 *(탐색 방식 — 제안 교환·순위 수집 등 — 은 설계에 위임)* | EU-V1 |
| FR-08 | 수행 | 시스템은 사용자가 정한 수락 바닥선 미만의 안을 자동 수락하지 않아야 한다 | EU-V2, SP-V1 |
| FR-09 | 수행 | 시스템은 실현 불가능한 안(일정 충돌·예약 마감 등)을 합의안으로 제시·수락하지 않아야 한다 | SA-V1 |
| FR-10 | 수행 | 시스템은 의제 도메인에 필요한 조회·실행 능력을 동적으로 구성하는 기능을 제공해야 한다 *(동적 Agent·Tool 생성 — 과제 제약·검증 가설 연계, [`../02-과제-개요.md`](../02-과제-개요.md) §2.7)* | SA-V2 |
| FR-11 | 수행 | 시스템은 시나리오별 완결 규칙(전원 동의·다수결·부분 완결)에 따라 합의 성립/결렬을 판정하고 종결해야 한다 *(완결 규칙 다양성은 PL 지시 ④)* | EU-V6, SD-V4 |
| FR-12 | 관찰·개입 | 시스템은 진행 상태·경과를 조회하는 기능을 제공해야 한다 | EU-V5, EU-V7, OP-V3 |
| FR-13 | 관찰·개입 | 시스템은 진행 중 사용자 개입(중단·조건 변경·거절)을 즉시 반영해야 한다 | EU-V2, EU-V4 |
| FR-14 | 종결 | 시스템은 최종 합의안을 제시하고 승인·거절·수정을 받는 기능을 제공해야 한다 | EU-V2 |
| FR-15 | 종결 | 합의 확정은 확정 당사자 전원이 동일한 내용을 확인한 뒤에만 효력을 가져야 한다 | EU-V6, SD-V3 |
| FR-16 | 종결 | 시스템은 완료된 협상의 이력과 판단 근거를 사후 조회하는 기능을 제공해야 한다 | EU-V5, SP-V3 |
| FR-17 | 신뢰·안전 | 이상 상황(무응답·교착·폭주·외부 확인 실패)에서도 협상은 불확정 상태 없이 정의된 결말(성공·실패·사용자 이관)로 완결되어야 한다 | SD-V1, SD-V4, SA-V3 |
| FR-18 | 신뢰·안전 | 시스템은 중단·장애 후 협상을 유효한 상태에서 재개할 수 있어야 한다 | OP-V1, HW-V1 |
| FR-19 | 신뢰·안전 | 시스템은 그룹에 공개되는 정보를 정책에 따라 최소화(필터링·요약·PII 제거)해야 한다 | EU-V3, SP-V4, PD-V4 |
| FR-20 | 신뢰·안전 | 구성 요소는 선언된 권한 범위 밖의 데이터·기능에 접근할 수 없어야 한다 | SA-V4, SP-V1 |
| FR-21 | 신뢰·안전 | 시스템은 참여자 간 상호 인증과 암호화 통신을 수립하고 변조를 감지해야 한다 | SP-V2 |
| FR-22 | 신뢰·안전 | 시스템은 협상 과정을 추적 가능한 privacy-safe 기록과 감사 증빙을 남겨야 한다 | SD-V2, SP-V3, OP-V4 |
| FR-23 | 검증 | 시스템은 실기기·실서비스 없이 협상 전체를 재현하는 기능을 제공해야 한다 | QA-V2, SA-V5 |
| FR-24 | 검증 | 시스템은 실패 상황(이탈·단절·타임아웃)을 임의 주입하는 기능을 제공해야 한다 | QA-V3 |
| FR-25 | 검증 | 시스템은 협상 지표(성공률·소요 시간·승인율 등)를 자동 측정·기록하는 기능을 제공해야 한다 | QA-V1 |

## 53.2 해법 중립 원칙의 적용 내역

요구가 설계 후보를 죽이는 사고를 막기 위해 배제·재작성한 내역. 판정 기준: **"설계를 다르게 골랐다면 이 문장이 무효가 되는가."**

| 항목 | 처리 | 사유 |
|---|---|---|
| "제안 생성→수락/거절→역제안" (교대 제안 사이클) | FR-07로 재작성 | 교대 제안은 특정 프로토콜. dp2-nparty 실측에서 FC 최고(★5)인 방안 3-A(일괄 순위·중앙 선별)는 역제안 사이클이 없다 — 원안대로면 최고 성능 설계가 요구 위반이 됨 |
| "라운드 경과에 따른 양보 전략 실행" | FR-08로 대체 | 양보 곡선은 수렴 메커니즘(설계). 요구의 본질은 "바닥선 미만 자동 수락 금지" |
| "전 참여자 협상 상태 동기화" | 삭제 (FR-15·FR-18·QAS-02로 커버) | 상시 동기화는 수단. 보장할 결과는 종결 시 전원 동일 + 중단 후 유효 재개 |
| "모델 출력 검증 후 반영" | 삭제 → [`54`](54-QAS-재도출.md) QAS-14로 이동 | "검증 계층"은 해법. 요구의 본질은 "모델 오류가 정확성을 훼손하지 않는다"는 품질 요구 |
| "Ufun 입력으로 정규화·공급" 등 해법 어휘 | FR-04·07·08에서 중립 표현으로 재작성 | Ufun·threshold는 NegMAS(선택한 해법)의 내부 개념 — 설계 문서·DP에서 등장할 어휘 |
| Sub-Agent 계층·동적 생성·A2A·서버 Orchestrator | FR에서 지우지 않고 제약으로 연결 | 우리가 고른 설계가 아니라 **과제 설명서가 부여한 제약** ([`../02-과제-개요.md`](../02-과제-개요.md) §2.3·§2.7) — [`../06-Constraints.md`](../06-Constraints.md) 소관 |
