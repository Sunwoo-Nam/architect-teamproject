# 36. 설계 문제 — 개입 시점 모델 (User Intervention Model)

> 문제 정의·의존: [`30`](30-설계-문제-총괄.md) §30.1 · 평가 축: [`20`](20-핵심-QA-확정.md)의 확정 QA 10개
> 관련 CFR: D3 즉시 개입 · D1 승인 수집

---

## 1. 문제 정의

협상은 백그라운드에서 자율로 진행되지만, 사용자는 언제든 끼어들 수 있어야 한다 — "잠깐 멈춰", "예산을 낮춰", "그 안은 싫어". 여기서 정해야 하는 것은 세 가지다: 협상의 **진행 상태를 어떤 단위로 관리**하는가(예: checkpoint처럼 저장 지점을 두는 방식 — 하나의 예시일 뿐 전제는 아니다), 사용자의 입력을 **어떤 component가 받아서 어디에 보관**하는가, 그리고 보관된 입력을 **어느 시점에 어떤 형태로 협상에 적용**하는가.

이것을 잘못 설계하면: 개입이 어중간한 시점에 반영되어 참여자마다 다른 조건으로 협상하게 되거나(정확성 훼손), 개입 반영을 위해 협상 전체가 자주 멈추거나(시간 훼손), 반영 절차 자체가 오류의 온상이 된다(감내성 훼손).

## 2. 전제와 제약 (모든 대안에 공통)

- 사용자 승인 없이 확정되는 실세계 효력은 없다 — 최종 승인 절차(CFR-D1)는 어느 대안에서든 동일하다 (절대 제약).
- 개입 입력의 UI(버튼·음성)는 본 문제의 범위가 아니다 — 입력이 도착한 이후의 **보관·적용 구조**만 다룬다.
- 개입이 반영되면 반영 사실이 전 참여자에게 전파된다 — 전파 경로는 [`31`](31-제안-토폴로지.md)의 결정을 따른다.

## 3. 대안

### 대안 A — 경계 적용형 (Boundary Gate)

**도식**: [`drawio/36-A-경계-적용형.drawio`](drawio/36-A-경계-적용형.drawio)

**구조.** 협상 상태를 **라운드 경계마다 확정 스냅샷**으로 저장한다. 사용자 입력은 도착 즉시 **Intervention Queue**에 보관되고, 진행 중인 라운드는 건드리지 않는다. 다음 라운드 경계에 도달하면 **Boundary Gate**가 Queue의 입력을 일괄 반영한 뒤 새 라운드를 시작한다.

| Component | 위치 | 역할 |
|---|---|---|
| Intervention Queue | 각 참여자 단말 | 사용자 입력을 도착 순서로 보관한다 |
| Boundary Gate | 각 참여자 단말 | 라운드 경계에서만 Queue를 꺼내 협상 조건에 반영한다 |
| Snapshot Store | 각 참여자 단말 | 라운드 경계마다 확정 상태를 저장한다 |

**정상 동작:** 입력 → Queue 보관 → 경계 도달 → 일괄 반영 → 다음 라운드. **오류 상황:** 반영 시점이 경계뿐이라 반영 절차가 단순하고 실패 여지가 작다 — 대신 개입이 최대 1라운드 늦게 반영된다.

### 대안 B — 즉시 중단·재개형 (Interrupt & Rollback)

**도식**: [`drawio/36-B-즉시-중단-재개형.drawio`](drawio/36-B-즉시-중단-재개형.drawio)

**구조.** 개입이 오면 **Interrupt Controller**가 즉시 전원에게 중단 신호를 보내 협상을 세우고, **Rollback Manager**가 진행 중이던 라운드의 잠정 상태를 undo log로 무효화한 뒤, 입력을 반영하고 **Resume Coordinator**가 전원 재시작을 맞춘다.

| Component | 위치 | 역할 |
|---|---|---|
| Interrupt Controller | 각 참여자 단말 | 개입 즉시 전원에 중단 신호를 전파한다 |
| Rollback Manager | 각 참여자 단말 | undo log로 진행 중 라운드의 잠정 상태를 되돌린다 |
| Resume Coordinator | 각 참여자 단말 | 입력 반영 후 전원이 같은 지점에서 재개하도록 맞춘다 |

**정상 동작:** 입력 → 즉시 중단 → 라운드 되돌림 → 반영 → 재개. **오류 상황:** 중단·되돌림·재개 각각이 전원 동기화를 요구해, 그 절차 중의 단절이 새로운 오류가 될 수 있다.

### 대안 C — 이중 트랙형 (Shadow Apply)

**도식**: [`drawio/36-C-이중-트랙형.drawio`](drawio/36-C-이중-트랙형.drawio)

**구조.** 협상은 **한 순간도 멈추지 않는다**. 개입은 본 트랙의 복사본인 **그림자 상태(shadow state)** 에 먼저 반영되고, **Diff Validator**가 그림자와 본 트랙의 차이를 검증한 뒤, **Swap Controller**가 안전한 시점(진행 중 메시지가 없는 순간)에 두 상태를 교체한다.

| Component | 위치 | 역할 |
|---|---|---|
| Shadow State Manager | 각 참여자 단말 | 개입이 반영된 가상 상태를 본 트랙과 병행 유지한다 |
| Diff Validator | 각 참여자 단말 | 그림자 상태가 본 트랙과 모순 없이 이어지는지 검증한다 |
| Swap Controller | 각 참여자 단말 | 안전 시점에 본 트랙을 그림자 상태로 교체한다 |

**정상 동작:** 입력 → 그림자 반영 → 검증 → 안전 시점 교체. **오류 상황:** 교체 순간의 원자성이 깨지면 참여자 간 상태가 갈릴 수 있어 교체 절차에 확인 왕복이 필요하다.

## 4. QA Trade-off 평가표

(SC-의제·Confidentiality 축은 세 대안 모두 (0) — 개입 처리 방식은 의제 조합·정보 노출과 직교한다.)

| QA | A. 경계 적용형 | B. 즉시 중단·재개형 | C. 이중 트랙형 |
|---|---|---|---|
| Functional Correctness | (0)<br>반영은 정확하고 전원 동시이나, 개입 도착 후 진행 중이던 라운드 하나는 옛 조건으로 마저 진행된다 | (+)<br>사용자가 거부한 방향으로 단 한 라운드도 더 가지 않는다 — 사용자 의사의 반영 충실도가 가장 높다 | (−)<br>교체 전까지 본 트랙이 옛 조건으로 계속 진행된다 — 이미 오간 제안과 새 조건 사이의 불일치 구간이 생긴다 |
| Fault Tolerance | (+)<br>진행 중 라운드를 건드리지 않아 반영 절차가 단순하다 — 새로운 실패 지점이 거의 없다 | (−)<br>중단·되돌림·재개의 매 단계가 전원 동기화를 요구한다 — 절차 중 단절이 새로운 오류가 된다 | (0)<br>본 트랙은 무중단이지만 교체 순간의 원자성이 새 실패 지점이다 |
| Analysability | (+)<br>개입이 경계에만 기록되어 이력이 결정적이다 — "몇 라운드부터 새 조건"이 명확하다 | (0)<br>중단·롤백 지점은 명확하나 무효화된 라운드의 흔적 관리가 더해진다 | (−)<br>본 트랙과 그림자 트랙의 이력이 병존해 재구성이 가장 복잡하다 |
| Scalability (참여자 수) | (0)<br>경계 반영은 원래 있던 라운드 경계 동기화에 얹힌다 — 추가 왕복 없음 | (−)<br>중단·재개 합의가 전원 왕복이라 인원이 늘수록 개입 한 번이 무거워진다 | (0)<br>그림자 유지는 단말 내부 일이라 인원과 무관하다 |
| Scalability (의제 조합) | (0)<br>무관 | (0)<br>무관 | (0)<br>무관 |
| Time Behaviour | (0)<br>협상 자체는 멈추지 않아 총 시간 영향이 작다 (개입 반영만 최대 1라운드 지연) | (−)<br>중단·되돌림·재개 동안 협상이 서고, 무효화된 라운드를 다시 진행한다 — 합의 시간이 늘어난다 | (+)<br>협상이 한 순간도 멈추지 않는다 — 총 시간 영향이 가장 작다 |
| Recoverability | (+)<br>라운드 경계 스냅샷이 곧 복구 지점이 된다 — 복구 구조와 시너지 | (0)<br>undo log가 복구에도 쓰이나, 중단 절차 도중에 죽으면 상태 판정이 애매해진다 | (−)<br>본 트랙과 그림자 두 상태를 함께 복원해야 한다 |
| Resource Utilization | (+)<br>Queue와 경계 스냅샷뿐 — 추가 비용이 가장 작다 | (0)<br>undo log 유지 비용이 있으나 개입 시에만 커진다 | (−)<br>상태를 두 벌 유지한다 — 메모리 부담이 상시로 늘어난다 |
| Confidentiality | (0)<br>무관 | (0)<br>무관 | (0)<br>무관 |
| Adaptability | (0)<br>시나리오마다 "경계"의 정의가 다르면 Gate의 경계 인식을 맞춰야 한다 | (0)<br>중단·재개는 시나리오와 무관한 보편 절차다 | (−)<br>그림자 검증 규칙이 시나리오 형태마다 달라져 유지 부담이 있다 |

## 5. 배타성 확인

세 대안은 "개입이 도착했을 때 진행 중인 라운드를 어떻게 하는가"에 대한 답이 상호 배타적이다 — 끝까지 두고 경계에서 반영(A) / 즉시 세우고 되돌림(B) / 세우지 않고 병행 반영 후 교체(C). 하나의 개입 이벤트에 이 셋 중 두 가지를 동시에 적용할 수 없다(두다가 세울 수 없고, 세우면서 병행할 수 없다). component도 대체 관계다: Queue+Gate, Interrupt+Rollback, Shadow+Swap은 같은 사건을 다르게 처리하는 장치들이라 공존하면 어느 경로로 처리할지의 상위 결정이 다시 필요해진다.

## 6. 비지배 확인

- A는 FC(B 대비)·TB(C 대비)에서 진다 (우위: FT·Analy·Rec·RU) ✓
- B는 FT·SC-참여자·TB·Analy(A 대비)에서 진다 (우위: FC) ✓
- C는 FC·Analy·Rec·RU·AD에서 진다 (우위: TB) ✓

## 7. 다른 문제와의 결정 의존

- **[`31`](31-제안-토폴로지.md)**: A의 "경계"는 토폴로지가 정의한다 — 31-A·B는 전원 응답 수집 완료, 31-C는 문서 한 바퀴. 31-C(ring)에서는 라운드가 길어 A의 반영 지연이 커진다는 점을 함께 고려해야 한다.
- **[`34`](34-의제-분해-어젠다-구조.md)**: 세션이 여러 개인 구조(34-B·C)에서는 개입을 어느 세션에 반영할지의 라우팅이 추가된다.
- **[`35`](35-이탈-무응답-처리-구조.md)**: 이탈자의 복귀·재확인 입력은 본 문제의 입력 경로를 재사용할 수 있다.
