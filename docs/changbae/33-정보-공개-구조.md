# 33. 설계 문제 — 정보 공개 구조 (역추론 방지)

> 문제 정의·의존: [`30`](30-설계-문제-총괄.md) §30.1 · 평가 축: [`20`](20-핵심-QA-확정.md)의 확정 QA 10개
> 관련 CFR: G3 차등 필터링 · G5 역추론 완화

---

## 1. 문제 정의

협상에서는 메시지를 주고받는 행위 자체가 정보를 흘린다. 내가 어떤 후보를 제안했는지, 무엇을 수락하고 무엇을 거절했는지를 다른 참여자가 몇 라운드만 관찰하면, 내 선호 순위 — 어떤 날을 좋아하고 얼마까지 쓸 수 있는지 — 를 상당히 정확하게 유추할 수 있다.

이 문제는 "정보를 얼마나 공개할지"의 **정책 문제가 아니다**. 정책을 아무리 좁게 잡아도 제안·수락의 **패턴**은 남기 때문이다. 풀어야 하는 것은 **유추(역추론) 자체를 어렵게 만드는 SW component를 어디에 도입할 것인가**이다. 이것을 풀지 못하면: 참여자들이 자기 선호가 노출될까 봐 시스템에 위임 자체를 꺼리게 된다 — 프라이버시가 위임의 전제라는 과제의 출발점이 무너진다.

## 2. 전제와 제약 (모든 대안에 공통)

- 지정된 비공개 정보가 원문 그대로 노출되지 않는 것(QA-CF-1)은 모든 대안이 지키는 절대 제약이다 — 본 문제의 평가 축은 그 위의 **역추론 내성(QA-CF-2)** 이다.
- 협상이 성립하려면 어떤 형태로든 제안 정보는 오가야 한다 — "아무것도 안 보내기"는 대안이 아니다. 문제는 **무엇을 어떤 형태로 누구를 거쳐** 보내느냐다.
- 어느 대안이든 NegMAS의 제안·평가 알고리즘 자체는 바꾸지 않는다.

## 3. 대안

### 대안 A — Disclosure Gate형 (송신 관문)

**도식**: [`drawio/33-A-Disclosure-Gate형.drawio`](drawio/33-A-Disclosure-Gate형.drawio)

**구조.** 각 단말의 **송신 직전 경로에 관문(Gate)** 을 둔다. Gate는 나가는 제안·응답을 그대로 보내지 않고 일반화한다 — 정확한 선호값 대신 **수락 가능 구간**("6시~8시 사이면 가능")으로 바꾸고, 라운드가 거듭될수록 누적 노출량이 한도를 넘지 않게 **노출 예산**을 관리한다. 중앙 장치가 없고 전적으로 각 단말 안에서 동작한다.

| Component | 위치 | 역할 |
|---|---|---|
| Disclosure Gate | 각 참여자 단말 | 송신 직전에 제안을 일반화·구간화하고, 누적 노출 예산을 관리해 한도 초과 시 표현을 더 뭉갠다 |

**정상 동작:** 제안 생성 → Gate 통과(일반화) → 송신. **오류 상황:** Gate는 상태가 거의 없어 실패 시 재시작하면 된다 — 다만 예산 기록을 잃으면 보수적으로(더 뭉개는 쪽으로) 재시작한다.

### 대안 B — Blind Aggregator형 (중립 집계)

**도식**: [`drawio/33-B-Blind-Aggregator형.drawio`](drawio/33-B-Blind-Aggregator형.drawio)

**구조.** 참여자끼리는 서로의 제안을 아예 보지 못하게 한다. 각자는 **집계 단말의 Blind Aggregator에게만** 원문 제안을 보내고(개별 비공개 채널), Aggregator가 전체를 모아 **누가 냈는지 지운 익명·집계 결과**("6시 가능 2명, 7시 가능 3명")만 배포한다.

| Component | 위치 | 역할 |
|---|---|---|
| Blind Aggregator | 집계 단말 | 원문 제안을 수신해 출처를 지우고 집계·익명화한 결과만 만든다 |
| Raw Proposal Sender | 각 참여자 단말 | 원문 제안을 집계 단말에만 보낸다 |

**정상 동작:** 원문 제출(비공개) → 익명 집계 → 집계 결과만 배포. **오류 상황:** 집계 단말이 죽으면 정보 흐름 전체가 멈춘다. 그리고 전원의 원문이 한 단말에 모이므로 그 단말의 신뢰가 전제된다.

### 대안 C — 익명 셔플 릴레이형 (출처 불명화)

**도식**: [`drawio/33-C-익명-셔플-릴레이형.drawio`](drawio/33-C-익명-셔플-릴레이형.drawio)

**구조.** 제안의 **내용은 그대로 두고 출처를 끊는다**. 제안들이 참여자 단말들을 체인처럼 거치면서 각 단말의 Shuffle Relay가 묶음의 순서를 섞고 발신자 표시를 익명 ID로 바꾼다 — 체인을 다 지나고 나면 "이 제안 묶음 중 어느 것이 누구 것인지"를 아무도(중간 단말 포함) 연결할 수 없다.

| Component | 위치 | 역할 |
|---|---|---|
| Shuffle Relay | 각 참여자 단말 | 수신한 제안 묶음의 순서를 섞고 출처 표시를 익명 ID로 치환해 다음으로 넘긴다 |

**정상 동작:** 제안 묶음 → 셔플 체인 통과 → 익명화된 묶음 배포. **오류 상황:** 체인의 한 홉이 멈추면 그 라운드의 제안 전달이 멈춘다. 익명 ID와 실제 참여자의 매핑은 각자 자기 것만 알고 있다.

## 5. 배타성 확인

세 대안은 "노출을 줄이는 지점"이 다르다 — A는 **내용을 뭉개고**(출처는 공개), B는 **출처와 내용을 집계자 뒤에 숨기고**, C는 **출처만 끊는다**(내용은 공개). 이 중 둘을 겹치면 hybrid가 아니라 다른 문제가 생긴다: A+B는 뭉개진 정보를 다시 집계하는 것이라 집계의 정확성 이점이 사라져 B의 존재 이유가 없어지고, B+C는 익명화를 두 번 하는 중복이며, A+C는 내용도 출처도 없는 메시지가 되어 협상 매칭 자체가 불가능해진다. 즉 결합형은 더 강한 대안이 아니라 자기 부정이 된다.

## 6. 비지배 확인

- A는 FC·Conf(B·C 대비)·Analy(B 대비)에서 진다 (우위: FT·SC-참여자·Rec·RU·AD) ✓
- B는 FT·SC-참여자·Rec·RU·AD에서 진다 (우위: FC·Analy·Conf) ✓
- C는 FC·Analy·SC-참여자·TB·Rec·AD에서 진다 (우위: Conf, B 대비 RU) ✓

## 7. 다른 문제와의 결정 의존

- **[`31`](31-제안-토폴로지.md)**: B는 31-A(Coordinator 집계형)와 결이 같다 — Coordinator가 Blind Aggregator를 겸하면 홉 추가가 없다. 31-B(mesh)를 고르면 B를 위해 집계 단말을 따로 선출해야 해 비용이 커진다. C는 31-C(ring)의 순환 경로를 셔플 체인으로 겸용할 수 있다. A는 어떤 토폴로지와도 무관하게 동작한다.
