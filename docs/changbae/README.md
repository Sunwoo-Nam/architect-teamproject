# Stakeholder 기반 QA·FR 도출 분석 — 다자간 협상 범위

> 작성일: 2026-08-04 · 작성 브랜치: `changbae`
> 본 폴더는 On-Device Agentic Platform 과제의 범위를 **다자간 협상(N-party Negotiation)** 으로 한정하고,
> 그 범위에서 Quality Attributes와 Functional Requirements를 **Stakeholder 관점에서 도출**한 산출물이다.
> 기존 `docs/` 파일은 수정하지 않는다.

---

## 1. 분석 조건 (사용자 지시, 2026-08-04)

1. **범위: 다자간 협상** — 3인 이상의 사용자가 각자의 PPA를 투입해 공동 합의에 도달하는 시나리오(상호작용 시나리오 2)가 중심. 협상 알고리즘은 **NegMAS 기반**: 각 참여자가 자기 옵션 공간(OutcomeSpace)을 효용 함수(Ufun)로 점수화 → 최고점 후보 제안 → 수신자는 자기 효용이 threshold 이상이면 수락, 미만이면 거절 후 역제안. **이 2자 교대 제안 프로토콜의 N-party 확장을 설계**한다. 그룹 합의 후 예약(시나리오 6)은 확장 단계, 그 외(B2C 1:1·가전 중재·원격 케어)는 범위 외.
2. **독립 도출 원칙** — 기존 요구사항·QA 문서(`docs/04-FR.md`, `docs/05-NFR.md`, `docs/07-QAS.md`)를 도출 근거로 사용하지 않는다. 근거는 과제 설명(01·02)·Stakeholder VOC(03·annex 원본표)·상호작용 시나리오(annex)로 한정한다.
3. **기술 형식 구분** — FR은 *"…하는 기능을 제공해야 한다"*, QA는 *"…을 최대화/최소화해야 한다 (측정 지표)"* 형태로 기술한다.
4. **PL 지정 ①** — Functional Correctness가 최우선 QA이며 그 정의 자체를 함께 수립한다 (09 문서).
5. **PL 지정 ②** — 다중 의제 약속(예: 영화 — 날짜×영화×영화관×시간)에서 후보 조합의 전체 열거는 메모리 폭발을 일으키며, 현실적으로는 한 의제를 정하면 다른 의제의 후보 폭이 좁아진다. **이 탐색 공간 통제를 다루는 것이 중요 관심사** (구두 시나리오, 2026-08-04 — CFR-B5·B12와 설계 질문 8번으로 반영). *표기: PL 원 표현은 조합 크기 "K×L×M×N"이나, 참여자 수 N과의 혼동을 피하기 위해 본 문서군에서는 **K×L×M×P**로 표기한다 (원문 인용 제외).*
6. **PL 지정 ③** — **Ufun(효용 함수)은 잘 만들어져 있다고 가정한다** (2026-08-05: "이런 알고리즘은 우리가 만드는 것이 아님"). 이에 따라 Ufun 구성(CFR-E2)은 기제공 통합 항목으로 분류하고, 기능 정확성의 선호 정합(L3) 판정은 수용성(무수정 승인율) 중심으로 정의한다 (09 §9.3).
7. **PL 지정 ④** — **완결 규칙과 협상 시나리오는 다양하다** (2026-08-05): 다수결·전원 승인·승인자만 추려 완결하는 시나리오가 모두 존재하고, 아직 정의되지 않은 새 시나리오(의제 순서·라운드별 주제·승인 지점이 다른)도 수용해야 한다. 완결 규칙 구성화(CFR-B9·D1)와 협상 프로세스 템플릿(CFR-I3), 설계 질문 2·9번으로 반영한다.
8. **PL 지정 ⑤** — **합의의 실행(외부 앱 연동)은 과제 범위 밖** (2026-08-05). 기능 정확성의 L4는 "모두가 동일한 결과로 협상이 종료되었는가"의 **합의 종결 정합(Agreement Closure Consistency)** 으로 재정의하고, 시스템 책임은 확정 레코드의 전파·확인·실행 계층 인계까지로 한다 (09 L4, CFR-F1).
9. **PL 지정 ⑥** — **모든 QA는 ISO/IEC 25010 QA로 매핑한다. 비표준 QA를 임의로 신설하지 않는다** (2026-08-05). 같은 하위특성이라도 별개 QA ID 배정은 가능 — 이에 따라 공정성(효용 분배 균형)은 **Functional Correctness에 매핑하되 별개 QA ID(QA-FC-2)** 로 관리한다 (개인 관점 정확성은 QA-FC-1, 09 §9.2·§9.4).

## 3. 핵심 결론 (요약)

- **최우선 FR 9건** (04 §4.5): 빈도(역할 합의 폭) × (H,H) 교집합 6건 — **라운드 실행(B2) · 즉시 개입(D3) · 차등 필터링(G3) · 교착 감지(I7) · 세션 복구(I8) · Mock 시뮬레이션(J2)** — 에 포커스 알고리즘의 신규 설계 3건 — **양보 전략(B8) · 합의 완결 규칙(B9) · 탐색 공간 축소(B12)** — 를 더한 9건이 설계 대안 도출(ADR)의 1차 대상.
- **최우선 QA** (08 §8.3): 빈도 상위 12종 ∩ (H,H) 11종 = 교집합 9종 — 기능 정확성·결함 감내·확장성·시간 효율성·복구 가능성·시험 용이성·자원 효율성·기밀성·운용 제약 준수 — 에 (H,H) 단독 2종(공존성·운용성/사용자 통제)과 **PL 지정 1종(적응성 — 새 협상 시나리오 수용)** 을 더한 하위특성 12종이 아키텍처 결정의 1차 드라이버. 측정·관리 단위로는 **QA ID 기준 15개 항목** — 자극·판정 유형이 다른 결함 감내(QA-FT-1·2), 확장성(QA-SC-1·2), 기밀성(QA-CF-1·2)은 각 2개 항목으로 분리.
- **Functional Correctness 결론** (09 §9.6): 1차 정의(각 참여자 관점의 의도 정확성∧제약 준수∧선호 정합∧합의 종결 정합)로 확정하고, 2차(N명 간 분배)는 **별개 QA 항목 QA-FC-2 "효용 분배 균형"으로 분리**. 합의의 실행은 범위 밖 — L4는 "전원 동일 결과로 종결"까지.
- **측정 체계** (10): QA ID 15개 항목 + QA-FC-2 + 기반 2개 항목 각각에 지표·목표 수준(절대 기준 vs 파일럿 목표)·테스트 환경(Mock 시뮬레이션 / 실기기 / 사용자 평가)·방법을 정의 — 하나의 QA 항목은 하나의 자극 부류·하나의 판정 유형만 가지며, 같은 지표를 두 항목에 이중 계상하지 않는다. QAS 작성의 원천. **확정 핵심 QA 10개의 판정은 21이 정본** — QA당 연속 지표 1개와 근거 있는 목표 수준으로 정의하고, 0건·100% 류 on/off 조건은 QA가 아니라 FR 합격 조건으로 분리(21 §21.4).
- **FR-QA 매핑** (11): 최우선 FR 9건과 핵심 QA의 실현·평가 관계를 매트릭스로 정리. 최대 결합점은 완결 규칙(B9 — 3개 QA 주 실현), Mock 시뮬레이션(J2)은 전 QA 측정의 전제. 커버리지 공백 분석에 따라 **실질 ADR 대상은 최우선 9건 + 목록 외 (H,H) 6건(B11·I10·G5·I14·I16·J8) = 15건**.
- **다음 단계 입력**: 다자 프로토콜이 답해야 할 설계 질문 9가지 (08 §8.4) — 제안 토폴로지 / 완결 규칙 / 양보 전략 / 이탈 처리 / 정보 공개 / 개입 시점 / 합의 커밋 / 의제 분해·어젠다 / 시나리오 가변성(프로세스 템플릿).

## 6. 표기 원칙

- 원본 자료에 있는 근거는 출처를 표기하고, 원본에 없는 판단(순위·등급·다자 확장 해석·카테고리 체계)은 **"분석자 판단/추론/확장"** 으로 명시한다. 원본 VOC는 1:1 협상 어휘이므로 다자 적용은 대부분 분석자 확장에 해당한다.
- ISO/IEC 25010:2023 개정 반영: Usability → **Interaction Capability**, Portability → **Flexibility**, **Safety** 신설, Maturity → **Faultlessness**, Security에 **Resistance** 추가.
