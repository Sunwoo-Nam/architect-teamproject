# 다자 합의 구조도 기반 동작 설명

> 기준: 현재 PPT 구조도의 모듈 구성과 [`51-설계후보1-다자-합의-프로토콜.md`](../51-설계후보1-다자-합의-프로토콜.md) §3-1·§4·§6
>
> 전제: P0는 **조정자(Coordinator)**이자 자신의 선호를 가진 **합의 참여자**다.

## 1. 각 안의 제목

### 권장안

| 구분 | 제목 | 보조 설명 |
|---|---|---|
| 왼쪽 | **다중 SAO 세션 조정형**<br>Multi-session SAO Coordination | 익명 후보 배포 + O/X 전원동의 |
| 오른쪽 | **누적 공통제안 합의형**<br>Cumulative Common-Proposal Consensus | 참여자별 제안 누적 + 전원 교집합 |

위 조합은 제목에서 **구조적 특징**을, 보조 설명에서 **합의 판정 규칙**을 보여준다.

### 대안

| 관점 | 왼쪽 | 오른쪽 |
|---|---|---|
| 원 설계 명칭 중심 | 순차 SAO 투표형 | 누적 공통제안형 |
| 판정 방식 중심 | 익명 후보 전원동의형 | 누적 제안 교집합형 |
| 구현 구조 중심 | 다중 SAO 세션 동기화형 | 참여자별 누적 상태 관리형 |

## 2. 공통 모듈과 전제

- **`Negotiation Lifecycle Manager`**: 참여자·후보 공간·정책을 준비하고 협상을 시작한다. 합의 성립, 취소, timeout, 최대 바퀴 소진 시 전체 실행을 종료한다.
- **`OutcomeSpace`**: 모든 참여자가 같은 식별자로 해석해야 할 협상 후보의 공간을 정의한다.
- **`Utility Function`**: 후보를 해당 참여자의 효용 점수로 변환한다. 그림의 UFun은 전체의 공용 함수가 아니라 **P0의 개인 UFun**으로 읽어야 하며, 다른 참여자도 각자의 비공개 UFun을 가진다.
- **`Negotiator`**: 자신의 UFun과 revised threshold를 사용해 다음 후보를 고르고, 수신한 후보를 평가하는 참여자 대리 객체다.

## 3. 다중 SAO 세션 조정형의 동작

1. **실행 초기화**<br>
   `Negotiation Lifecycle Manager`가 P0와 일반 참여자를 등록하고 `OutcomeSpace`, 개인별 `Utility Function`, revised threshold, 최대 바퀴 수를 준비한다.

2. **양자 SAO 실행 구성**<br>
   P0는 일반 참여자별로 P0 측 `SAO Negotiator`를 하나씩 두고, 상대 측 `Negotiator`와 `N-1`개의 양자 SAO 세션을 구성한다. `Multi-session Coordinator`는 이 세션들이 같은 바퀴·라운드로 진행되도록 시작과 마감을 맞춘다.

3. **첫 제안 수집**<br>
   바퀴가 시작되면 각 참여자 `Negotiator`가 현재 threshold 이상의 다음 순위 후보 하나를 제안한다. P0는 자신의 후보를 로컬에서 추가한다.

4. **익명 후보 배치 생성**<br>
   `Batch-offer Aggregator`가 모든 제안을 모아 중복을 제거하고 제안자 귀속을 제거한다. 생성된 익명 후보 목록을 현재 라운드의 batch offer로 만든다.

5. **동일한 batch offer 배포**<br>
   `Multi-session Coordinator`가 동일한 batch offer를 모든 양자 세션으로 보낸다. 일반 참여자는 후보의 제안자와 다른 참여자의 응답을 보지 못한다.

6. **후보별 O/X 평가와 다음 제안**<br>
   각 `Negotiator`가 자신의 `Utility Function`으로 batch의 모든 후보를 평가한다. `utility ≥ revised threshold`면 O, 그렇지 않으면 X로 표시하고, **O/X 묶음과 자신의 다음 순위 후보**를 하나의 회신으로 보낸다.

7. **동기 마감과 전원동의 판정**<br>
   `Multi-session Coordinator`가 모든 세션의 회신을 마감한 뒤, 현재 batch에서 전원이 O를 준 후보를 찾는다. PPT 사례의 Round #3에서는 `C·G·D·A` 중 `A`만 전원 O이므로 `A`가 합의 후보가 된다.

8. **반복 또는 종료**<br>
   성립 후보가 없으면 직전 회신에 결합된 다음 제안들로 새 batch를 만들어 4–7단계를 반복한다. 성립 시 `Negotiation Lifecycle Manager`가 모든 세션을 같은 합의 결과로 종료하고, 바퀴 상한까지 성립하지 않으면 `NO_DEAL`로 종료한다.

## 4. 누적 공통제안 합의형의 동작

1. **실행 초기화**<br>
   `Negotiation Lifecycle Manager`가 참여자와 `OutcomeSpace`, 개인별 `Utility Function`, revised threshold, 라운드·바퀴 상한을 준비한다. `Cumulative State Manager`는 참여자별 빈 누적 제안 집합을 준비한다.

2. **라운드 제안 선택**<br>
   라운드 `k`에서 각 참여자 `Negotiator`가 자신의 `Utility Function`으로 정한 `k`번째 선호 후보 하나를 선택한다. revised threshold 미만인 후보는 제출하지 않는다.

3. **P0로 제안 제출**<br>
   일반 참여자는 선택한 후보만 P0에게 제출하고, P0의 자신의 제안은 로컬에서 같은 입력으로 처리한다. 다른 참여자에게는 중간 제안을 배포하지 않는다.

4. **누적 상태 갱신**<br>
   `Cumulative State Manager`가 수신 마감, 현재 라운드, 제출 여부를 관리한다. `Cumulative Proposal Store`는 제안을 해당 참여자의 누적 집합에 추가하고, 제출 라운드를 그 참여자의 후보 순위로 기록한다.

5. **전원 교집합 판정**<br>
   중앙 합의 로직이 모든 참여자의 누적 집합 `Sᵢ(k)`를 교차한다. `G(k) = S₀(k) ∩ S₁(k) ∩ … ∩ Sₙ₋₁(k)`가 빈 집합이면 다음 라운드로 가고, 비어 있지 않으면 전원이 직접 제안한 공통 후보가 생긴 것으로 판정한다.

6. **합의 후보 선택**<br>
   교집합 후보가 하나면 즉시 확정한다. 둘 이상이면 `순위 합 최소 → 순위 표준편차 최소 → 결선투표`의 정책순으로 하나를 선택한다.

7. **반복 또는 종료**<br>
   공통 후보가 없으면 라운드를 올리고 각 `Negotiator`가 다음 순위 후보를 낸다. 기존 제안은 `Cumulative Proposal Store`에 계속 남는다. 합의 성립 시 `Negotiation Lifecycle Manager`가 종료를 통지하고, 최대 바퀴까지 교집합이 없으면 `NO_DEAL`로 종료한다.

### PPT 사례의 해석과 정합성 확인

- 의도한 사례는 P0·P1·P2·P3가 `H`를 각각 R5·R1·R4·R3에 제출하여 R5에 처음 공통 후보 `H`가 완성되는 흐름으로 읽힌다.
- 다만 현재 화면의 **상단 제안 이력표 `R5–P2`는 `A`**, 하단 선호순위표의 **P2 5순위는 `C`**로 서로 다르다. `라운드 번호 = 순위 번호`를 유지하고 R5의 단일 공통 후보를 `H`로 만들려면 **`R5–P2`를 `C`로 수정**해야 한다.

## 5. 현재 구조도에서 빠지거나 암묵적인 모듈

### 5.1. 다중 SAO 세션 조정형

| 중요도 | 빠진 모듈·책임 | 검토 의견 |
|---|---|---|
| **필수** | **양자 `SAOMechanism` 세션 `N-1`개** | 현재는 양쪽 `Negotiator`만 있고 두 객체의 offer·response·step·timeout을 실행하는 세션이 표시되지 않았다. 화살표에 `SAO Session #i`라고 적어도 충분하다. |
| **필수 책임** | **O/X 응답 집계·전원동의 판정** | 별도 박스를 추가하지 않으려면 `Multi-session Coordinator`의 부제로 `Session sync · O/X unanimity`를 표시하는 것이 좋다. |
| **필수 책임** | **P0의 자체 제안·O/X 평가** | P0도 합의 참여자이므로 P0의 제안과 O/X가 판정에 포함되어야 한다. 박스보다 `P0 participation is handled locally`라는 주석이 간결하다. |
| 선택 | **현재 라운드 상태** | 현재 batch, O/X, 다음 제안, 세션 마감 여부는 필요하지만 단기 상태이다. 비교 그림에서는 `Multi-session Coordinator`의 내부 상태로 암묵 처리해도 된다. |

### 5.2. 누적 공통제안 합의형

| 중요도 | 빠진 모듈·책임 | 검토 의견 |
|---|---|---|
| **필수 책임** | **교집합 계산·합의 선택** | 현재 `Consensus Negotiator`가 이 역할을 한다고 추론할 수는 있지만 명칭으로는 불분명하다. 참여자를 대리하는 Negotiator가 아니므로 **`Cumulative Consensus Engine`** 또는 **`Consensus Coordinator`**로 바꾸고 `Accumulate · intersect · select`를 적는 것을 권장한다. |
| **필수 책임** | **P0의 자체 제안 생성** | P0 역시 순위에 따라 제안해야 한다. `P0 participation is handled locally`로 주석 처리하거나 P0의 로컬 `Negotiator`를 표시한다. |
| 선택 | **제안 수신·검증** | 참여자 ID, 라운드, 중복 제출, `OutcomeSpace` 소속 여부를 확인해야 한다. 구조도를 간결히 유지하려면 별도 `Proposal Receiver`를 두지 않고 중앙 합의 엔진의 책임으로 포함해도 된다. |

### 5.3. 두 안에 공통으로 빠진 책임

| 중요도 | 빠진 모듈·책임 | 검토 의견 |
|---|---|---|
| **필수** | **참여자별 Private UFun과 threshold** | 현재 그림만 보면 P0에만 UFun이 있는 것처럼 보일 수 있다. 각 참여자의 `Negotiator`에 `owns Private UFun · Threshold`라고 적는 것을 권장한다. |
| **필수** | **`Negotiation Policy`** | revised threshold 갱신, 동률 해소, 최대 바퀴·timeout은 원 설계에서 tactic 계층으로 분리된다. `Threshold Strategy + TieBreaker + Stop Conditions`를 하나의 공통 정책 박스로 모으면 과도한 세분화를 피할 수 있다. |
| 선택 | **통신·재시도 어댑터** | 각 참여자가 별도 단말·프로세스에 배치된다면 실제 transport, 인증, timeout, 재전송이 필요하다. 현재 그림이 논리 구조도라면 화살표와 주석으로만 남겨도 된다. |
| 선택 | **결과 통지** | 합의·`NO_DEAL`을 전원에게 전파해야 한다. 별도 모듈을 추가하기보다 `Negotiation Lifecycle Manager`의 종료 책임으로 두는 것이 적절하다. |

## 6. 구조도에 반영할 최소 수정안

구조도를 더 복잡하게 만들지 않으면서 책임 공백을 줄이려면 다음 정도면 충분하다.

1. 왼쪽 화살표에 `Bilateral SAO Session #i`를 표시한다.
2. 왼쪽 `Multi-session Coordinator`에 `Session sync · O/X unanimity`를 부제로 추가한다.
3. 오른쪽 `Consensus Negotiator`를 `Cumulative Consensus Engine`으로 바꾸고 `Accumulate · intersect · select`를 부제로 추가한다.
4. 두 그림 모두에 `P0 participation is handled locally`라는 주석을 두고, 참여자 `Negotiator`에 `Private UFun · Threshold`를 표시한다.
5. 정책을 표시할 여유가 있다면 공통 박스 `Negotiation Policy` 하나만 추가한다.
