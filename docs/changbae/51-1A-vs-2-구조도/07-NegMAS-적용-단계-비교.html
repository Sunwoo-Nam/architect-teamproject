방안 1-A vs 방안 2 — NegMAS 적용 단계 비교

기준: NegMAS 0.15.7

붉은 글씨는 NegMAS의 API·자료형·실행 기능을 그대로 재사용하는 부분이다. 방안별 동기화·상태 관리·합의 판정 로직은 새로 구현하므로 기본 글씨로 표시한다.

설계 전제

  • 방안 1-A: P0가 N-1개의 양자 SAO 세션을 동기화한다. 표준 SAO는 후보 하나에 대한 응답만 표현하므로, 익명 후보 목록과 후보별 O/X를 주고받는 응답 어댑터를 둔다.
  • 방안 2: SAO를 사용하지 않고 NegMAS Mechanism을 확장한 CumulativeConsensusMechanism을 구현한다. 이 메커니즘이 동시 제출·누적 상태·전원 교집합 판정을 담당한다.
  • P0는 두 방안 모두에서 프로토콜 담당자이자 자신의 UFun을 가진 참여자 1인이다.

단계별 비교

  1. OutcomeSpace / Outcome으로 협상 후보를 정의한다.
  2. 각 참여자의 BaseUtilityFunction을 준비한다.
  3. P0가 일반 참여자별로 SAOMechanism 양자 세션 N-1개를 생성한다.
  4. Plan1aCoordinator가 SAOSyncController를 기반으로 세션의 라운드를 맞춘다. 익명화·전원 O 판정은 새로 구현한다.
  5. 각 참여자는 SAONegotiator를 확장한 Plan1aNegotiator로 참여한다.
 1. 협상 구조 초기화
  1. OutcomeSpace / Outcome으로 협상 후보를 정의한다.
  2. 각 참여자의 BaseUtilityFunction을 준비한다.
  3. CumulativeConsensusMechanism을 Mechanism 기반으로 생성한다.
  4. 각 참여자는 Negotiator를 확장한 CumulativeNegotiator로 등록한다.
  5. P0 내부에 참여자별 누적 제안 집합 Si를 초기화한다.
2. 선호 순위·threshold 준비
  1. 각 Negotiator가 BaseUtilityFunction으로 후보 utility를 계산하고 내림차순 순위를 만든다.
  2. PolyAspiration으로 현재 바퀴의 revised threshold를 계산한다.
  3. 바퀴가 시작되면 각 참여자의 순위 포인터를 처음으로 돌린다. P0는 현재 라운드 후보만 유지한다.
 2. 선호 순위·threshold 준비
  1. 각 Negotiator가 BaseUtilityFunction으로 후보 utility를 계산하고 내림차순 순위를 만든다.
  2. PolyAspiration으로 현재 바퀴의 revised threshold를 계산한다.
  3. 바퀴가 시작되면 순위 포인터는 처음으로 돌리지만, P0의 누적 제안 집합 Si는 유지한다.
3. 바퀴의 첫 후보 수집
  1. 각 Plan1aNegotiator는 SAO propose()를 통해 threshold 이상의 현재 순위 후보 1개를 제안한다.
  2. P0 Coordinator가 양자 세션들의 첫 proposal을 모으고 P0 자신의 후보를 로컬로 추가한다.
  3. 제안 메시지가 정상 도착한 경우에만 해당 Negotiator의 순위 포인터를 전진시킨다.
 3. 라운드 후보 제출
  1. CumulativeConsensusMechanism이 MechanismState.step을 기준으로 라운드를 시작한다.
  2. 각 CumulativeNegotiator는 threshold 이상의 현재 순위 후보 1개를 전용 ProposalAction으로 P0에 제출한다.
  3. ProposalAction에는 참여자 ID·바퀴·순위 번호·Outcome을 담는다.
4. 익명 후보 목록 배포 — SAO offer
  1. P0 Coordinator가 수집한 후보의 제안자 귀속을 제거하고 중복 후보를 하나로 합친다.
  2. 익명 후보 목록을 전용 BatchOffer Outcome으로 표현한다.
  3. SAOMechanism이 각 양자 세션에 동일한 offer를 전달한다.
 4. 제출 수신·누적 상태 갱신
  1. P0는 수신한 Outcome이 협상 OutcomeSpace에 속하는지 확인한다.
  2. 정상 제출을 해당 참여자의 누적 집합에 추가한다: Si(k) = Si(k-1) ∪ {proposal}.
  3. 제출 라운드를 해당 참여자의 후보 순위로 기록한다.
  4. 다른 일반 참여자에게는 후보나 중간 판정 결과를 배포하지 않는다.
5. 후보 평가·SAO response + counter-offer
  1. 각 Negotiator가 목록의 모든 후보를 BaseUtilityFunction으로 평가한다.
  2. utility ≥ revised threshold면 O, 아니면 X로 판정해 votes 묶음을 만든다.
  3. SAOResponse의 data["votes"]에 O/X 묶음을 담고, outcome에 자기 다음 순위 후보(counter-offer)를 담아 회신한다.
  4. ResponseType은 SAO 응답 상태를 표현하고, 후보별 O/X 의미는 어댑터가 해석한다.
 5. 누적 상태 완성
  1. P0가 해당 라운드의 제출 수신을 마감한다.
  2. 제출한 참여자의 순위 포인터를 전진시킨다. 유실된 제출은 포인터를 전진시키지 않아 다음 시도에서 같은 후보를 다시 낸다.
  3. 방안 2는 다른 사람의 후보를 평가하거나 O/X를 회신하는 단계가 없다.
6. 합의 성립 판정
  1. P0 Coordinator가 모든 양자 세션의 O/X 묶음을 수집한다.
  2. 현재 익명 후보 집합 Ck에서 ∃c ∈ Ck : 전원 O인 후보를 찾는다.
  3. 응답 하나라도 없거나 X면 해당 후보는 성립하지 않는다. 만장일치 판정은 새로 구현한다.
 6. 합의 성립 판정
  1. P0가 모든 참여자의 누적 집합을 교차한다: G(k) = S1(k) ∩ … ∩ SN(k).
  2. G(k) = ∅이면 다음 라운드로 진행한다.
  3. G(k) ≠ ∅이면 전원이 직접 제안한 공통 후보가 생겼으므로 합의 성립 단계로 이동한다. 교집합 판정은 새로 구현한다.
7. 동률 후보 해소
  1. 전원 O 후보가 하나면 그대로 확정한다.
  2. 여러 개면 동률 후보만 다시 공지하고 각 Negotiator가 BaseUtilityFunction으로 최선안을 골라 1표를 준다.
  3. 최다 득표 후보를 선택하고, 득표까지 같으면 후보의 결정론적 순서로 확정한다.
 7. 동률 후보 해소
  1. 공통 후보가 하나면 그대로 확정한다.
  2. 여러 개면 P0가 제출 라운드로 복원한 전원 순위의 합이 가장 작은 후보를 선택한다.
  3. 그래도 같으면 순위 표준편차가 가장 작은 후보를 선택한다.
  4. 마지막까지 같으면 각 Negotiator가 BaseUtilityFunction으로 결선투표한다.
8. 미성립 시 다음 라운드
  1. 합의가 없으면 P0가 직전 SAOResponse.outcome들의 counter-offer를 다음 후보 집합으로 삼는다.
  2. 제안자 귀속을 제거한 다음 BatchOffer를 SAOMechanism으로 전달한다.
  3. 별도 미성립 공지는 없으며, 다음 offer가 직전 라운드의 미성립 신호가 된다.
 8. 미성립 시 다음 라운드
  1. CumulativeConsensusMechanism이 MechanismState.step을 증가시킨다.
  2. 각 Negotiator가 다음 순위 후보를 제출하고, P0는 기존 Si에 추가한다.
  3. 과거 제안은 제거하지 않으며 라운드가 지나도 계속 판정 근거로 사용한다.
  4. 일반 참여자에게 다른 사람의 제안이나 미성립 교집합을 공지하지 않는다.
9. 바퀴 전환·threshold 인하
  1. 모든 Negotiator가 현재 threshold 이상 후보를 소진하면 현재 바퀴를 마친다.
  2. 합의가 없으면 PolyAspiration의 다음 시점으로 threshold를 낮춘다.
  3. 참여자의 순위 포인터를 처음으로 돌리고 바퀴의 첫 proposal 수집부터 다시 시작한다.
 9. 바퀴 전환·threshold 인하
  1. 모든 Negotiator가 현재 threshold 이상 후보를 소진하면 현재 바퀴를 마친다.
  2. 합의가 없으면 PolyAspiration의 다음 시점으로 threshold를 낮춘다.
  3. 순위 포인터를 처음으로 돌리되, P0의 누적 제안 집합 Si는 그대로 유지한다.
10. 합의·결렬 종료
  1. 합의 후보가 결정되면 P0가 전체 양자 세션에 동일한 최종 Outcome을 설정한다.
  2. NegMAS Mechanism 종료 상태·callback을 통해 각 Negotiator에게 종료를 알린다. 여러 SAO 세션을 동일 결과로 닫는 작업은 P0 Coordinator가 담당한다.
  3. 최대 5바퀴까지 합의가 없으면 전 세션을 NO_DEAL로 종료한다.
 10. 합의·결렬 종료
  1. 합의 후보가 결정되면 MechanismStepResult.agreement에 최종 Outcome을 설정한다.
  2. NegMAS Mechanism 종료 상태·callback을 통해 모든 Negotiator에게 종료를 알린다.
  3. 최대 5바퀴까지 교집합이 없으면 agreement 없이 종료하고 시스템 결과를 NO_DEAL로 매핑한다.
NegMAS 활용 범위
  • OutcomeSpace / Outcome: 협상 후보 공간과 개별 후보를 표현한다.
  • BaseUtilityFunction: utility 계산, O/X 판정, 결선투표의 최선안 선택에 사용한다.
  • PolyAspiration: 바퀴별 revised threshold를 계산한다.
  • SAOMechanism: P0와 각 일반 참여자 사이의 offer·response·counter-offer 세션을 실행한다.
  • SAONegotiator: 제안·응답 callback과 참여자 생명주기를 제공한다.
  • SAOResponse / ResponseType: 응답 상태, 다음 후보, 확장 데이터를 담는 표준 응답 용기를 제공한다.
  • SAOSyncController: 여러 양자 SAO 세션의 제안·응답 시점을 동기화하는 기반을 제공한다.
  • Mechanism 종료·시간 제한·callback: 세션 실행 제어와 종료 통지를 제공한다.
 NegMAS 활용 범위
  • OutcomeSpace / Outcome: 협상 후보 공간과 개별 후보를 표현한다.
  • BaseUtilityFunction: 개인별 utility 계산, 순위 생성, 결선투표의 최선안 선택에 사용한다.
  • PolyAspiration: 바퀴별 revised threshold를 계산한다.
  • Mechanism: 방안 2 전용 메커니즘의 참여자 등록, step, 시간 제한, 종료 생명주기를 제공한다.
  • Negotiator: 참여자 UFun·선호·생명주기를 담는 기반을 제공한다.
  • MechanismState: 현재 step·시간·실행·종료 상태를 표현한다.
  • MechanismStepResult: 단계 완료 여부와 최종 agreement를 NegMAS 실행기에 반환한다.
  • Mechanism 종료·시간 제한·checkpoint·callback: 실행 제어, 중간 상태 저장, 종료 통지를 제공한다.
