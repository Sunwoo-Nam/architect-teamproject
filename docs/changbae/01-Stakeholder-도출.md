# 1. 주요 Stakeholder 10개 역할 도출 — 다자간 협상 범위

> **과제 범위** (사용자 지시, 2026-08-04): 본 분석은 **다자간 협상(N-party Negotiation)** 으로 범위를 한정한다.
> 3인 이상의 사용자가 각자의 PPA를 투입해 공동 합의(모임 일정·장소, 여행 계획 등)에 도달하는
> 시나리오 2([`annex/상호작용-시나리오-9종.md`](../../annex/상호작용-시나리오-9종.md))가 중심이며,
> 협상 알고리즘은 **NegMAS 기반** — 각 참여자가 자기 옵션 공간(OutcomeSpace)을 효용 함수(Ufun)로 점수화하여
> 최고점 후보를 제안하고, 수신자는 자기 효용이 threshold 이상이면 수락·미만이면 거절 후 역제안하는
> 2자 교대 제안 프로토콜을 **다자로 확장**하는 설계이다.
> 그룹 합의 후 서비스 예약(시나리오 6)은 확장 단계, 그 외 시나리오(B2C 1:1, 가전 중재, 원격 케어 등)는 범위 외로 한다.
>
> 입력: [`docs/03-Stakeholder.md`](../03-Stakeholder.md)의 18개 역할, [`annex/Stakeholder-원본표.md`](../../annex/Stakeholder-원본표.md)
> 방법: Sommerville·Wiegers의 stakeholder 식별 원칙 + Bass(*Software Architecture in Practice*)의 이해관계자 범주 커버리지 점검

---

## 1.1 선정 기준 (분석자 판단)

1. **범위 정합**: 다자간 협상의 성립·검증에 직접 이해관계가 있는 역할을 우선한다. 범위 외 시나리오(B2C·가전·원격 케어)만 대표하는 역할은 제외한다.
2. **Key Player 우선**: 원본 영향도↑/관심도↑ 분면의 역할은 범위에 부합하는 한 포함한다.
3. **범주 커버리지**: 이해관계자 범주(사용자 / 획득자 / 설계자 / 구현자 / 운영자 / 플랫폼 / 평가자·검증자)가 모두 대표되어야 한다. 이 7개 범주는 Bass 4판이 나열하는 이해관계자 역할 목록을 분석자가 본 과제에 맞게 재구성한 것이다.
4. **관심사 중복 병합**: VOC가 실질적으로 겹치는 역할은 병합하고 명시한다.

## 1.4 병합·재정의 결정의 근거

- **S7 병합**: 원본 ID 9(Security/Privacy)와 ID 17(개인정보 보안)은 관심사(최소 권한·데이터 보호·감사 / PII 흐름 통제)가 세부 전개 관계라 하나의 관점으로 병합한다.
- **S2 재정의**: 원본 "Counterparty User"의 VOC(노출 최소화·일방 결정 방지·사후 확인·즉시 반영)는 다자에서 **N-1명 각각에게 적용**되며, 추가로 "다른 참여자들에게 내 선호가 역추론되는 것"이라는 다자 고유 우려가 생긴다 (분석자 추론 — 원문 VOC에는 없음).
- **S6 재정의**: 원본 AI/ML Engineer의 관심사(intent 인식·on-device 추론·memory personalization·self-improving)는 유지하되, 포커스 알고리즘(효용·threshold·양보·집계)의 설계 책임을 전면에 둔다.
