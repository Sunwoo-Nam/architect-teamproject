# 35. 설계 문제 — 이탈·무응답 처리 구조 (Departure & Unresponsiveness)

> 문제 정의·의존: [`30`](30-설계-문제-총괄.md) §30.1 · 평가 축: [`20`](20-핵심-QA-확정.md)의 확정 QA 10개
> 관련 CFR: B11 이탈·재참여 · I10 장애 격리·부분 진행

---

## 1. 문제 정의

여러 명이 참여하는 협상에서는 누군가 응답을 멈추는 일이 반드시 생긴다 — 폰이 꺼지거나, 비행기 모드가 되거나, OS가 앱을 죽이거나. 그때 정해야 하는 것은 두 가지다: **누가 그 사실을 알아차리는가**(감지), 그리고 **남은 사람들은 어떻게 하는가**(지속). 이것을 정하지 않으면 한 명의 무응답이 전원의 무한 대기가 된다.

단, "몇 초를 기다렸다가 이탈로 볼 것인가" 같은 시한 값은 정책이라 본 문제의 대상이 아니다 — 본 문제는 **감지와 지속을 수행하는 component를 어디에 두는가**의 구조 문제다.

## 2. 전제와 제약 (모든 대안에 공통)

- 이탈자가 빠진 뒤의 합의 성립 여부는 완결 규칙([`32`](32-완결-규칙-실행-구조.md))을 남은 인원 기준으로 재적용해 판정한다 — 이 재적용은 어느 대안에서든 일어난다.
- 이탈자가 복귀하면 협상 이력을 인계받고, 이미 확정된 사항에 대해서는 승인 여부를 다시 표명한다 (미승인자에게 효력 없음 — 절대 제약).
- 완전히 죽은 세션의 복구는 Recoverability의 문제([`20`](20-핵심-QA-확정.md) §20.2)이고, 본 문제는 **세션이 살아 있는 동안** 일부가 빠지는 상황을 다룬다.

## 3. 대안

### 대안 A — 중앙 멤버십 관리형 (Central Membership)

**도식**: [`drawio/35-A-중앙-멤버십-관리형.drawio`](drawio/35-A-중앙-멤버십-관리형.drawio)

**구조.** 관리 단말 한 곳의 **Membership Manager**가 전 참여자의 생존 신호(heartbeat)를 받아 이탈을 판정하고, 이탈 발생 시 세션 재구성(남은 인원 확정, 완결 규칙 재적용 트리거)을 전원에게 통지한다.

| Component | 위치 | 역할 |
|---|---|---|
| Membership Manager | 관리 단말 | 참여자 명단과 생존 상태를 관리한다 |
| Departure Detector | 관리 단말 | heartbeat 시한 초과로 이탈을 판정한다 |
| Session Reconfigurator | 관리 단말 | 남은 인원으로 세션을 재구성하고 완결 규칙 재적용을 트리거한다 |
| Heartbeat Sender | 각 참여자 단말 | 주기적으로 생존 신호를 관리 단말에 보낸다 |

**정상 동작:** heartbeat 수신 → 시한 초과 감지 → 재구성 통지 → 협상 재개. **오류 상황:** 관리 단말 자신의 이탈은 이 구조가 감지하지 못한다 — 별도의 승계 절차가 필요하다.

### 대안 B — 분산 상호 감시형 (Distributed Peer Monitoring)

**도식**: [`drawio/35-B-분산-상호-감시형.drawio`](drawio/35-B-분산-상호-감시형.drawio)

**구조.** 관리자가 없다. **전원이 서로** 생존 신호를 교환하고, "저 사람이 안 보인다"는 관찰을 gossip으로 공유해 **과반의 관찰이 모이면 이탈로 확정**한다. 판정도 재구성도 합의로 이루어진다.

| Component | 위치 | 역할 |
|---|---|---|
| Peer Monitor | 각 참여자 단말 | 다른 참여자들의 생존 신호를 관찰한다 |
| Gossip Exchanger | 각 참여자 단말 | 자기 관찰("3번이 안 보임")을 전원과 공유한다 |
| Departure Consensus | 각 참여자 단말 | 과반 관찰이 모이면 이탈을 확정하고 재구성에 합의한다 |

**정상 동작:** 상호 heartbeat → 관찰 공유 → 과반 합의로 이탈 확정 → 재구성. **오류 상황:** 한 단말의 오판(일시적 네트워크 문제를 이탈로 봄)은 과반 합의에서 걸러진다 — 대신 확정까지 왕복이 더 걸린다.

### 대안 C — 대리 응답형 (Stand-in Proxy)

**도식**: [`drawio/35-C-대리-응답형.drawio`](drawio/35-C-대리-응답형.drawio)

**구조.** 이탈을 감지하면 협상을 멈추거나 인원을 줄이는 대신, **지정된 단말이 이탈자의 마지막 상태(마지막 제안·threshold)로 대리 응답하는 Stand-in Proxy를 기동**해 협상을 끊지 않고 이어간다. 복귀하면 Handover Manager가 대리 진행분 이력을 인계하고, 대리 중 잠정 수락된 사항은 본인 재확인을 받는다.

| Component | 위치 | 역할 |
|---|---|---|
| Stand-in Proxy | 지정 단말 | 이탈자의 마지막 제안·threshold를 기준으로 보수적으로 대리 응답한다 (새 양보는 하지 않음) |
| Handover Manager | 각 참여자 단말 | 복귀 시 대리 진행 이력을 인계하고 본인 재확인 절차를 시작한다 |

**정상 동작:** 이탈 감지 → Proxy 기동 → 협상 무중단 지속 → 복귀 시 인계·재확인. **오류 상황:** 대리 응답은 항상 "대리"로 표시되고, 대리 중 잠정 수락은 본인 재확인 전까지 확정 효력이 없다 (절대 제약 준수).

## 4. QA Trade-off 평가표

(SC-의제 축은 세 대안 모두 (0) — 이탈 처리는 의제 조합과 무관하다.)

| QA | A. 중앙 멤버십 관리형 | B. 분산 상호 감시형 | C. 대리 응답형 |
|---|---|---|---|
| Functional Correctness | (0)<br>판정·재구성이 일괄 통지되어 전원이 같은 명단을 본다 — 정확성에 중립 | (0)<br>과반 합의가 오판을 걸러주나 확정 전까지 잠깐 명단이 갈릴 수 있다 — 상쇄 | (−)<br>본인이 없는 동안 대리 응답으로 협상이 진행된다 — 이탈자의 실제 의사와 어긋난 방향으로 갈 수 있어 복귀 후 재확인으로 되돌리는 비용이 생긴다 |
| Fault Tolerance | (0)<br>참여자 이탈은 빠르게 처리하지만 관리 단말 자신의 이탈이 사각이다 | (+)<br>감지의 단일점이 없다 — 누가 빠져도 남은 전원이 감지·확정할 수 있다 | (+)<br>협상이 아예 멈추지 않는다 — 이탈이 흡수되어 잔여 그룹의 진행이 가장 매끄럽다 |
| Analysability | (+)<br>이탈 판정·재구성 이력이 관리 단말 한 곳에 시간 순으로 남는다 | (−)<br>관찰·gossip·합의 기록이 전 단말에 흩어져 "언제 누가 이탈 확정됐나"의 재구성이 번거롭다 | (0)<br>대리 행위가 모두 "대리" 표시로 기록되면 추적은 되나, 본인 행위와 대리 행위를 구분해 읽어야 한다 |
| Scalability (참여자 수) | (0)<br>heartbeat가 전원→한 곳으로 선형이다 | (−)<br>상호 감시 신호가 전원-전원으로 제곱 증가한다 | (0)<br>대리 기동 자체는 추가 메시지가 거의 없다 |
| Scalability (의제 조합) | (0)<br>무관 | (0)<br>무관 | (0)<br>무관 |
| Time Behaviour | (0)<br>이탈 시 재구성 동안 짧게 멈춘다 | (−)<br>이탈 확정에 관찰 공유·합의 왕복이 추가로 든다 — 그동안 협상이 대기한다 | (+)<br>기다림 없이 즉시 대리로 이어간다 — 이탈로 인한 지연이 가장 작다 |
| Recoverability | (0)<br>멤버십 상태가 한 곳에 있어 복구 기준이 명확하다 — 관리 단말이 죽으면 무거워진다 (상쇄) | (−)<br>흩어진 관찰 상태를 다시 모아야 명단이 복원된다 | (−)<br>대리 진행분과 본인 복귀 상태를 병합하는 복구가 가장 복잡하다 |
| Resource Utilization | (+)<br>각 단말은 신호 송신만 하고 감시 계산은 한 곳에 몰린다 — 전체 합계가 가장 작다 | (−)<br>전원이 전원을 감시하는 계산·통신을 진다 | (0)<br>대리 실행 단말에 추가 부담이 있으나 이탈 기간에 한정된다 |
| Confidentiality | (0)<br>오가는 것이 생존 신호뿐 — 협상 내용 노출과 무관 | (0)<br>동일 | (−)<br>이탈자의 선호 정보(마지막 threshold·제안 기준)가 대리 단말로 넘어간다 — 타인 단말에 개인 선호가 이전되는 구조적 노출 |
| Adaptability | (+)<br>이탈 처리 정책 변경이 관리 단말 한 곳으로 끝난다 | (−)<br>전 단말의 감시·합의 규칙이 같은 버전이어야 한다 | (0)<br>대리 허용 여부·대리 방식이 시나리오별 구성 항목으로 추가되어야 한다 |

## 5. 배타성 확인

세 대안은 "이탈이라는 사건을 시스템이 무엇으로 취급하는가"가 다르다 — A·B는 **명단에서 빼는 사건**(빼는 판정을 중앙이 하느냐 합의로 하느냐가 다시 갈림)이고, C는 **빼지 않고 대리로 채우는 사건**이다. A와 B는 판정 권위의 소재가 상호 배타적이며(중앙 판정과 과반 합의 판정이 공존하면 판정 충돌 시 상위 심급이 또 필요), C는 애초에 명단 축소를 하지 않으므로 A·B의 재구성 절차와 목적이 충돌한다 — "대리로 채우면서 동시에 명단에서 뺀다"는 정의상 모순이다.

## 6. 비지배 확인
