# 30. 설계 문제 총괄 — 문제 목록·의존 관계·공통 평가 방법

> 배경: [`08`](08-핵심-QA-중요도-난이도-평가.md) §8.4의 설계 질문에 대한 채택 결정(2026-08-05)에 따라,
> 채택된 설계 문제 8건을 개별 설계 문서(31-38)로 다룬다.
> 문서 번호는 **결정 의존이 없는 문제를 앞 번호, 의존이 있는 문제를 뒷 번호**로 배열한다 — 앞에서부터 읽으면 뒤 문서가 참조하는 결정을 이미 알고 있게 된다.
> 참고: 양보(concession) 전략은 설계 문제로 채택하지 않았다 — threshold를 얼마나 완화할지는 수치 정책(알고리즘)의 문제로, 어떤 값을 골라도 SW component 구성이 달라지지 않기 때문이다. 전략을 갈아 끼우는 자리 자체는 38(시나리오 가변성)에서 다룬다.

## 30.3 공통 평가 방법 (31-38 전 문서 적용)

1. **평가 축**: [`20`](20-핵심-QA-확정.md)의 확정 QA 10개만 사용한다. 다른 QA는 표에 넣지 않는다.
2. **대안 수**: 2-3개. 각 대안은 **SW component 구성이 서로 다른** 구조여야 한다. **같은 component 구성에서 파라미터나 정책만 다른 것은 별개 대안이 아니다** — 이 기준을 모든 문서에서 반드시 지킨다.
3. **배타성**: 대안들은 서로 결합해서 동작할 수 없어야 한다. 결합 가능하면 그 결합형을 하나의 대안으로 재구성한다. 각 문서에 "왜 결합할 수 없는가"를 명시한다.
4. **비지배(non-dominance)**: 어느 한 대안이 10개 QA 전부에서 다른 대안과 같거나 우수하면 안 된다. 모든 대안은 이기는 QA와 지는 QA를 함께 가져야 한다. 스틸맨(각 대안을 가장 강한 형태로 구성)으로 세워도 지배가 발생하면 그 대안을 버리고 경쟁력 있는 대안으로 교체한다. **단, 지배 사실을 숨기고 억지 trade-off를 만들지 않는다** — 이 원칙도 반드시 지킨다.
5. **평가 표기**: 대안별로 각 QA에 **(+) / (0) / (−)** 를 매긴다. 기호는 셀의 맨 앞에 쓰고, 판단 이유는 줄을 바꿔 그 아래에 문장으로 쓴다. 기호만 있는 표는 금지.
6. **서술 원칙**: 쉬운 표현으로 풀어서 쓴다. 기술 용어는 영어 원문을 쓴다(예: Coordinator, broadcast). "이 component가 무엇을 받아서 무엇을 하고 무엇을 내보내는가"를 명시적으로 쓴다.
7. **도식**: 모든 대안은 component diagram을 drawio로 작성한다 (프로젝트 규칙).
   - 저장 위치: [`drawio/`](drawio/) 폴더 · 파일명: `<주제번호>-<대안번호>-<대안이름>.drawio`
   - **같은 주제의 대안 도식들은 결이 같아야 한다**: 공통 부분(단말 배치·공통 component)은 모든 대안에서 같은 위치·같은 모양·같은 색으로 그리고, **그 대안만의 고유 component와 연결만 강조색으로 차별화**한다. 도식을 나란히 놓고 보면 "이건 공통이고, 이 부분이 다르구나"가 바로 보여야 한다. 각 도식에 공통/고유 범례를 넣는다.
8. **문서 템플릿** (전 문서 동일): §1 문제 정의 → §2 전제와 제약 → §3 대안 A/B/(C) (component 목록·역할, 연결과 데이터 흐름, 정상 시나리오, 오류 시나리오, drawio 링크) → §4 QA trade-off 평가표 → §5 배타성 확인 → §6 비지배 확인 → §7 다른 문제와의 결정 의존.
