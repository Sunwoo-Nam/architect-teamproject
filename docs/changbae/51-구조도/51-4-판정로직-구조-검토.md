## 1. 두 판정 로직의 범위(scope) 차이 — 코드로 확인

### 1-A: 이번 라운드 창(window) 판정

```python
unanimous = [c for c in candidates
             if len(votes) == self.n and all(votes[p.pid][c] for p in self.profiles)]
```

`candidates`는 이번 라운드에 배포된 후보 목록뿐이다(직전 수집분). 판정은 "이번 라운드 창 안에서 전원이 O를 준 게 있는가"만 본다. 이전 라운드의 후보·판정은 여기 재등장하지 않는다 — 소진되면 그걸로 끝, 다시 판정 대상이 되지 않는다.

### 방안 2: 누적 집합 교집합 판정

```python
for pid, c in submitted.items():
    bb.proposed_by.setdefault(pid, set()).add(c)
if len(bb.proposed_by) < self.n:
    return None
common = set.intersection(*bb.proposed_by.values())
```

`bb.proposed_by`는 라운드 경계를 넘어 계속 누적된다. 판정은 "1라운드부터 지금까지 각자가 낸 모든 후보의 교집합"을 매 라운드 다시 계산한다 — 이전 라운드에 낸 후보도 여전히 판정 대상으로 유효하다.

### 함의 (도출 — 원문에 직접 서술된 문장 아님)

1-A는 "이번 라운드 후보가 소진되면 그 후보로는 다시 성립할 수 없다"(라운드 창이 매번 닫힘). 방안 2는 "한 번 낸 후보는 계속 유효한 제안으로 남는다"(집합이 단조 증가). 이 차이는 51 원문에 문장으로 명시돼 있지 않다 — 위 코드 동작으로부터의 도출이다.

## 2. 동률 처리 로직 차이 — 원문 근거

- 51 §3-1: "동률 처리 ... O/X는 문턱 통과 여부만 말해 주고, 만장일치 후보를 전원이 제안했다는 보장이 없어 순위 합을 쓸 수 없다" → `RunoffMajority`(추가 결선 투표).
- 51 §4: "라운드 번호=순위 번호 규칙 덕분에 공통 후보에 대해 전원의 순위를 알 수 있다" → `RankSumThenStdThenRunoff`(순위 합 최소 우선, 동률이면 표준편차, 그래도면 결선).

코드 확인(`protocol_styles.py` `Plan1aSao.__init__`, `protocol.py` `Plan2Cumulative.__init__`): 각각 기본 `tie_breaker`로 위 두 클래스를 주입한다. 즉 판정 로직 자체(무엇이 unanimous인지 계산하는 방식)뿐 아니라, 동률이 났을 때 무엇으로 깨는지도 서로 다른 정보(문턱 통과 여부 vs 순위)에 구조적으로 의존한다.

## 3. 대비 표

| | 방안 1-A | 방안 2 |
|---|---|---|
| 판정 창 | 이번 라운드 배포분만 | 세션 시작부터 누적 |
| 판정 조건 | `len(votes)==N and all(votes[p][c])` | `len(proposed_by)>=N and intersection` |
| 동률 해소 | 결선 투표(`RunoffMajority`) — 순위 정보 없음 | 순위 합 최소(`RankSumThenStdThenRunoff`) — 결정론적 |
| 판정 트리거 시점 | 회신 phase 직후 | 제출 phase 직후 (매 라운드) |

## 4. 51-1 §3.3(상태 영속화 단위)과의 관계

51-1 §3.3은 "영속화 부담 차이는 크지 않다"고 결론지었다 — Delivered Set까지 포함하면 1-A도 방안2만큼 이력을 들고 있기 때문이다. 이 문서는 그 이력이 왜 필요한지를 보여준다: 1-A의 로컬 판정 자체는 라운드 창만 보지만, 재시도·복구를 위해 Delivered Set을 별도로 유지해야 하므로 결국 방안 2와 비슷한 양의 상태를 갖게 된다. 즉 51-1의 결론(영속화 부담이 비슷하다)은 유지되지만, 그 이유가 "판정 로직이 같아서"가 아니라 **"판정 로직은 다른데 복구 요구가 이를 상쇄해서"**라는 게 이 문서의 발견이다.

## 5. 다음 그림에 반영할 요소

1. 판정 로직을 플로우차트(조건 분기)로 — "라운드 창" vs "누적 집합"을 박스 범위로 시각 대비한다.
2. 동률 처리 분기를 판정 로직 끝에 이어 붙여 tie_breaker 클래스명까지 표시한다.
3. 51-1 §3.3과의 상호 참조 각주(영속화 부담이 비슷한 이유가 판정 로직 때문이 아니라는 점).
