# 5. Functional Correctness의 정의 (제안)

> 배경: PL 지시(2026-08-04) — *"Functional Correctness가 가장 중요한 QA이며, 이를 어떻게 정의할 것인지도 함께 고민할 것."*
> 본 문서의 계층 분해와 측정 기준은 **분석자 제안**이며, 팀 합의를 거쳐 05-NFR·07-QAS에 반영해야 확정된다.

---

## 5.1 왜 별도의 정의가 필요한가

**ISO/IEC 25010:2023의 Functional Correctness**는 대략 *"제품이 필요한 정밀도로 정확한(correct) 결과를 제공하는 능력"* 으로 정의된다(개념 수준 요약). 이 정의는 "정답이 존재하고 비교 가능하다"를 암묵적으로 전제하는데, 본 시스템은 그 전제가 네 가지 이유로 성립하지 않는다.

| # | 어려움 | 내용 |
|---|---|---|
| 1 | **LLM 비결정성** | 같은 입력에도 다른 출력이 나온다. "출력 = 기대값" 방식의 정확성 판정이 불가능 |
| 2 | **정답의 복수성** | 협상 결과는 단일 정답이 없다. "토요일 6시 식당 X"와 "일요일 12시 식당 Y" 모두 '맞는' 합의일 수 있다 |
| 3 | **판정 주체의 주관성** | 최종적으로 '맞았는지'는 사용자의 의도·선호에 비추어 사용자만 판정할 수 있다 |
| 4 | **다자 정합성** | 협상 결과는 나에게만 맞아서는 안 되고 상대(들)에게도 맞아야 하며, 모든 참여자가 **동일한** 결과를 실행해야 한다 (NFR-MAF-11) |

기존 문서의 공백도 이 정의를 요구한다: **NFR-IDS-05는 "의도 해석 정확도(Accuracy)는 별도 평가 항목으로 분리하며 본 NFR의 범위에 포함하지 않는다"** 고 명시하여 기술적 성공률만 다루고 정확도를 비워 두었다. 그 "별도 평가 항목"이 바로 본 문서가 채워야 할 자리다.

## 5.2 제안 — 파이프라인 4계층 분해 정의

핵심 아이디어: **"정확함"을 하나의 수치로 정의하지 않고, Intent → 협상 → 합의 → 실행 파이프라인의 계층마다 "무엇이 틀릴 수 있는가"로 분해**한 뒤, 계층별로 성격에 맞는 판정 방식을 부여한다.

> Functional Correctness = L1 ∧ L2 ∧ L3 ∧ L4
> (어느 한 계층이라도 틀리면 사용자는 "Agent가 틀렸다"고 인식한다)

### L1. Intent Correctness — 의도를 맞게 읽었는가

| 항목 | 내용 |
|---|---|
| 정의 | IDS가 감지·분류한 Intent가 사용자의 실제 의도와 일치한다 |
| 오류 예 | "이번 주말에 만날까?" 대화에서 여행 계획 Intent를 감지해야 하는데 쇼핑 Intent를 생성 / 의도가 없는 잡담에서 Intent를 생성(오탐) |
| 판정 방식 | **통계적** — 정답 라벨 데이터셋 기준 분류 정확도 + 실사용 프록시(제안 알림에 대한 사용자 수락률 / 오탐 신고·무시율) |
| 관련 FR/NFR | FR-IDS-01/02, NFR-IDS-05가 비워 둔 "별도 평가 항목" |

### L2. Constraint Correctness — 지켜야 할 것을 지켰는가

| 항목 | 내용 |
|---|---|
| 정의 | 협상 과정과 합의안이 **결정적으로 검증 가능한 경계(hard constraint)** 를 위반하지 않는다: 위임 정책 범위(FR-MAF-10), 캘린더 물리 충돌, 예산 상한, 공유 금지 데이터(FR-MAF-05), 협상 프로토콜 규칙 |
| 오류 예 | 위임 한도를 넘는 금액 결제 합의 / 이미 확정된 일정과 겹치는 시간 합의 / Private Knowledge 포함 제안 발신 |
| 판정 방식 | **결정적(deterministic)** — 규칙 엔진으로 기계 검증 가능. 목표는 통계가 아니라 **위반 0건** |
| 관련 FR/NFR | FR-MAF-10, FR-MAF-05, NFR-MAF-07("0건"과 동형) |

### L3. Preference Correctness — 좋은 선택이었는가

| 항목 | 내용 |
|---|---|
| 정의 | 합의안이 hard constraint 충족을 넘어 사용자의 선호·과거 이력·컨텍스트(DPA 정보 포함)에 비추어 **사용자가 받아들일 만한** 선택이다 |
| 오류 예 | 규칙 위반은 없지만 사용자가 싫어하는 새벽 시간대 합의 / 항상 가는 단골 대신 평점 낮은 식당 선택 |
| 판정 방식 | **통계적 + 사용자 판정** — 정답이 없으므로 프록시 지표로 측정: **무수정 승인율**(제시안을 수정 없이 승인한 비율), 조건 수정률, 거부율, 재협상 요구율 |
| 관련 근거 | 원본표 "결과 만족도", 01 §1.4.1 "결정 품질 향상" |

### L4. Execution Correctness — 합의한 그대로 실행됐는가

| 항목 | 내용 |
|---|---|
| 정의 | 최종 실행(캘린더 등록·예약·결제)이 합의안과 정확히 일치하고, **모든 참여자가 동일한 결과**를 실행한다 |
| 오류 예 | "토요일 18시" 합의 후 캘린더에 17시 등록 / A는 식당 X, B는 식당 Y로 각각 예약(실세계 충돌) |
| 판정 방식 | **결정적** — 합의 레코드와 실행 결과의 기계 대조. 목표 **불일치 0건** (NFR-MAF-11의 0%와 동형) |
| 관련 FR/NFR | FR-MAF-09, NFR-MAF-11 |

### 판정 방식의 이원화 원칙

| 계층 | 성격 | 기준 유형 | 초기 제안 임계값 |
|---|---|---|---|
| L2, L4 | 결정적으로 검증 가능 | **절대 기준 (위반 0건)** | 위임 범위 위반 0건 · 합의-실행 불일치 0건 |
| L1, L3 | 비결정적·주관적 | **통계 기준 + 사용자 안전판** | L1 분류 정확도 ≥ 90% (NFR-IDS-05의 90%와 정렬, 실측 후 조정) · L3 무수정 승인율 ≥ 70% (분석자 제안 초기치 — 실측 근거 없음, 베이스라인 측정 후 재설정 필요) |

비결정 계층(L1·L3)의 오류가 실세계 피해로 이어지지 않게 막는 최종 안전판은 **사용자 승인(Operability, FR-MAF-08)** 이다. 즉 Functional Correctness의 정의는 Operability와 구조적으로 결합되어 있다 — "Agent는 틀릴 수 있으나, 틀린 채로 실행되지는 않는다."

## 5.3 아키텍처 함의 (04 문서 난이도 H의 근거)

1. **생성-검증 분리 (Generate–Validate)**: LLM 출력(비결정, L1·L3 담당)을 그대로 신뢰하지 않고, 모든 제안·합의안이 **결정적 검증기(L2 규칙 엔진)** 를 통과한 뒤에만 발신·실행되는 계층 구조가 필요하다. 검증기는 동적 생성 Agent를 포함한 모든 행동 경로에 삽입되어야 한다(Safety — Operational Constraint와 공유되는 구조).
2. **합의의 원자적 커밋**: L4의 "전 참여자 동일 결과"는 전원 ACK 후 실행(NFR-MAF-11)이라는 커밋 프로토콜을 요구한다.
3. **판정 가능성의 기록**: L1·L3의 통계 측정과 오류 분석은 협상 전 과정의 완전한 이력(Accountability, NFR-MAF-08)과 재현 하니스(Testability)를 전제한다 — (H,H) 속성들이 서로 맞물리는 지점이다.

## 5.4 미결정 사항 (팀 논의 필요)

1. L3 무수정 승인율의 목표치 — 베이스라인 실측 전에는 임의값이다.
2. L1 정확도 측정용 정답 라벨 데이터셋의 구축 주체·규모 (품질검증팀·AI/ML 협의 필요).
3. 본 정의의 05-NFR 반영 여부와 형식 (반영 시 CLAUDE.md 7항에 따라 07-QAS 동기화 필수).
4. Counterparty 측 correctness(상대 조건의 정확 반영)를 L2에 넣을지, 별도 계층으로 둘지.
