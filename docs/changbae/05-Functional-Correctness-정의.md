# 5. Functional Correctness의 정의 (제안) — 다자간 협상 범위

> 배경: PL 지시(2026-08-04) — *"Functional Correctness가 가장 중요한 QA이며, 이를 어떻게 정의할 것인지도 함께 고민할 것."*
> 범위: 다자간 협상 — NegMAS 기반 효용·threshold 교대 제안 프로토콜의 N-party 확장.
> 본 문서의 계층 분해와 측정 기준은 **분석자 제안**이며 팀 합의를 거쳐야 확정된다.

---

## 5.1 왜 별도의 정의가 필요한가

**ISO/IEC 25010:2023의 Functional Correctness**는 대략 *"제품이 필요한 정밀도로 정확한 결과를 제공하는 능력"* 이다(개념 수준 요약). 이 정의는 "정답이 존재하고 비교 가능하다"를 전제하는데, 다자 협상 시스템에서는 그 전제가 다섯 가지 이유로 성립하지 않는다.

| # | 어려움 | 내용 |
|---|---|---|
| 1 | **LLM 비결정성** | 같은 입력에도 다른 출력. "출력 = 기대값" 비교 판정 불가 |
| 2 | **정답의 복수성** | 그룹 합의는 단일 정답이 없음 — 전원 threshold를 넘는 합의안이 여럿 존재 가능 |
| 3 | **판정 주체의 주관성·다수성** | '맞았는지'는 참여자 각자의 의도·선호로만 판정 가능하며, **판정 주체가 N명** |
| 4 | **공정성 차원** | 전원이 threshold를 넘겼어도 효용 분배가 특정 참여자에게 체계적으로 유리하면 나머지는 "틀렸다(불공평하다)"고 인식 — 정확성에 분배 차원이 추가됨 (분석자 도출) |
| 5 | **전원 실행 정합** | 합의 결과는 N명 모두가 동일하게 실행해야 함 — 1명이라도 다르면 실세계 충돌 (시나리오 6 "이중 확인" 문제의 일반형) |

또한 "크래시 없이 끝났다"(기술적 성공 — Reliability의 몫)와 "전원의 의도에 맞는 결과"(내용적 정확성)는 별개의 축이므로, Functional Correctness는 후자만 겨냥해야 측정이 겹치지 않는다.

## 5.2 제안 — 파이프라인 4계층 분해 정의

**"정확함"을 하나의 수치로 정의하지 않고, 의도 감지 → 효용 구성 → 다자 협상 → 합의 → 실행 파이프라인의 계층마다 "무엇이 틀릴 수 있는가"로 분해**하여, 계층별 성격에 맞는 판정 방식을 부여한다.

> Functional Correctness = L1 ∧ L2 ∧ L3 ∧ L4
> (어느 한 계층이라도 틀리면 참여자는 "Agent가 틀렸다"고 인식한다)

### L1. Intent Correctness — 그룹 조율 의도를 맞게 읽었는가

| 항목 | 내용 |
|---|---|
| 정의 | 시스템이 감지한 그룹 조율 의도(누구와·무엇을·언제까지 합의해야 하는가)가 사용자의 실제 의도와 일치한다 |
| 오류 예 | "우리 언제 볼까?" 단톡 대화에서 참여자 구성을 잘못 식별 / 의도 없는 잡담에서 협상을 개시(오탐) |
| 판정 방식 | **통계적** — 정답 라벨 기준 분류 정확도·오탐율 + 실사용 프록시(선제 제안 수락률·무시율) |
| 근거 | 02 §2.6 1단계 (Intent 감지), S6 VOC "Intent 품질이 떨어지면 전부 헛수고" |

### L2. Constraint Correctness — 전원의 경계를 지켰는가

| 항목 | 내용 |
|---|---|
| 정의 | 협상 과정과 합의안이 **N명 각각의 결정적으로 검증 가능한 경계(hard constraint)** 를 위반하지 않는다: 각자의 위임 정책 범위·캘린더 물리 충돌·예산 상한·공유 금지 데이터·프로토콜 규칙. **threshold를 넘는 후보라도 위임 범위 밖이면 수락 불가** (이중 검사) |
| 오류 예 | 참여자 B의 위임 예산을 넘는 금액 합의 / C의 확정 일정과 겹치는 시간 합의 / 공유 금지 정보가 포함된 제안 브로드캐스트 |
| 판정 방식 | **결정적** — 규칙 엔진으로 참여자별 기계 검증. 목표는 **전 참여자 기준 위반 0건** |
| 근거 | S1 VOC "마음대로 결정이 제일 무서움", S7 VOC "단 한 건의 초과도 불가" |

### L3. Preference Correctness — 전원에게 좋은 선택이었는가

| 항목 | 내용 |
|---|---|
| 정의 | 합의안이 (a) 각 참여자의 효용 함수(Ufun)가 실제 선호를 맞게 반영한 상태에서, (b) 전원의 threshold를 넘고, (c) 효용 분배가 특정 참여자에게 체계적으로 편향되지 않는다 |
| 오류 예 | Ufun이 사용자의 "주말 선호"를 놓쳐 평일이 고득점 처리됨 / 전원 threshold는 넘었으나 매번 같은 사람의 1순위만 채택됨(편향) |
| 판정 방식 | **통계적 + 사용자 판정** — ① Ufun 정합: 효용 순위 vs 사용자 실제 선호 순위의 일치율, ② 수용성: **무수정 승인율**·수정률·거부율, ③ 공정성: 참여자 간 효용 분배 지표(반복 협상에서의 편향 추세 포함) — 공정성 지표의 구체 선택은 미결정 (§5.4) |
| 근거 | 원본표 "결과 만족도", 01 §1.4.1 "결정 품질" — (a)(c) 분해는 분석자 도출 |
| NegMAS 대응 | (a) = Ufun 구성 품질, (b) = threshold(aspiration/reservation 수준) 판정, (c) = 다자 집계 규칙의 성질 |

### L4. Execution Correctness — 전원이 합의 그대로 실행했는가

| 항목 | 내용 |
|---|---|
| 정의 | 최종 실행(캘린더 등록·예약)이 합의안과 정확히 일치하고, **N명 전원이 동일한 결과**를 실행한다 |
| 오류 예 | "토요일 18시" 합의 후 한 명만 17시로 등록 / A는 식당 X, B·C는 식당 Y로 실행(실세계 충돌) |
| 판정 방식 | **결정적** — 합의 레코드와 참여자별 실행 결과의 기계 대조. 목표 **전원 불일치 0건** |
| 근거 | 02 §2.6 7단계 (실행), 시나리오 6 "확정 정보를 N명에게 전파하고 승인을 얻는 이중 확인(Double Confirm)" |

### 판정 방식의 이원화 원칙

| 계층 | 성격 | 기준 유형 | 초기 제안 방향 |
|---|---|---|---|
| L2, L4 | 결정적으로 검증 가능 | **절대 기준 (위반 0건)** | 전 참여자 기준 위임 위반 0건 · 합의-실행 불일치 0건 |
| L1, L3 | 비결정적·주관적 | **통계 기준 + 사용자 안전판** | 정확도·무수정 승인율·공정성 지표는 **베이스라인 실측 후 목표치 설정** (사전 임의값 지양) |

비결정 계층의 오류가 실세계 피해로 이어지지 않게 막는 최종 안전판은 **전 참여자의 승인(Operability)** 이다 — *"Agent는 틀릴 수 있으나, 틀린 채로 실행되지는 않는다"* 가 N명 각각에게 성립해야 한다.

## 5.3 아키텍처 함의 (04 문서 난이도 H의 근거)

1. **생성-검증 분리 (Generate–Validate)**: LLM·Ufun이 만드는 제안(비결정)은 참여자별 **결정적 검증기(L2 규칙 엔진)** 를 통과한 뒤에만 발신·수락·실행된다. 검증기는 제안 생성→평가→집계→실행의 전 경로에 삽입된다 (Safety — Operational Constraint와 공유 구조).
2. **합의의 원자적 커밋**: L4의 "전원 동일 실행"은 전원 확인(ACK) 후 실행이라는 커밋 프로토콜을 요구한다 (시나리오 6 Double Confirm의 일반화).
3. **판정 가능성의 기록·재현**: L1·L3의 통계 측정과 공정성 추세 분석은 참여자별 제안·수락의 완전한 이력(Accountability)과 Mock 다자 재현 하니스(Testability)를 전제한다.
4. **Ufun 확인 루프**: L3(a)의 "Ufun이 선호를 맞게 반영"은 협상 전 사용자가 자기 효용 구성(우선순위)을 확인·수정할 수 있는 상호작용(S1의 선호 반영 확인 FR)과 결합될 때 검증 가능해진다.

## 5.4 미결정 사항 (팀 논의 필요)

1. L3 공정성 지표의 선택 — 효용 분배의 어떤 통계(최소 효용, 효용 곱, 분산, 반복 편향 추세 등)를 쓸지. *일반 협상 이론의 후생 개념(예: Nash product)을 참고할 수 있으나 원문 근거가 없으므로 팀 결정 사항* (분석자 표시).
2. L1 정확도·L3 승인율의 목표치 — 베이스라인 실측 전 미설정을 제안.
3. L2 검증기의 규칙 표현 — 위임 정책과 하드 제약의 통합 스키마.
4. 본 정의의 팀 표준 채택 여부와 반영 위치.
