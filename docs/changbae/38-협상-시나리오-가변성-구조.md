# 38. 설계 문제 — 협상 시나리오 가변성 구조 (Scenario Variability)

> 문제 정의·의존: [`30`](30-설계-문제-총괄.md) §30.1 · 평가 축: [`20`](20-핵심-QA-확정.md)의 확정 QA 10개
> 관련 CFR: I3 협상 프로세스 템플릿 · I18 의제 구성 · B9 완결 규칙

---

## 1. 문제 정의

지금 설계하는 것은 "여럿이 약속 잡기" 시나리오지만, 앞으로 **아직 정의되지 않은 협상 시나리오**가 계속 추가될 것이다 — 의제 순서가 다르거나, 라운드마다 주제가 바뀌거나, 중간 승인 지점이 다르거나, 완결 규칙이 다른(전원/다수결/부분 완결) 시나리오들. 요구는 명확하다: **새 시나리오를 코드 변경 없이 수용하는 협상 프로세스 구조**여야 한다.

여기서 정하는 것은 "시나리오를 무엇으로 표현하고, 그것을 무엇이 실행하는가"이다. 이 선택에 따라 새 시나리오를 추가하는 비용(데이터만 추가 vs 코드 작성)과, 잘못 정의된 시나리오가 협상을 망가뜨릴 위험(검증 가능성)이 크게 달라진다.

## 2. 전제와 제약 (모든 대안에 공통)

- **협상 코어** — 라운드 실행, 완결 판정, 메시지 프로토콜, NegMAS 알고리즘 — 는 어느 대안에서든 코드 변경 없이 유지되는 공통 부분이다. 대안이 바꾸는 것은 코어 위에서 **시나리오를 표현·실행하는 층**이다.
- 완결 규칙([`32`](32-완결-규칙-실행-구조.md))과 어젠다([`34`](34-의제-분해-어젠다-구조.md))의 표현이 시나리오 정의에 포함되어야 한다.
- 어떤 대안이든 위임 범위 검사·사용자 승인 등 절대 제약은 시나리오 정의로 우회할 수 없다.

## 3. 대안

### 대안 A — 선언적 템플릿 해석형 (Template Interpreter)

**도식**: [`drawio/38-A-선언적-템플릿-해석형.drawio`](drawio/38-A-선언적-템플릿-해석형.drawio)

**구조.** 시나리오를 **데이터(템플릿)** 로 기술한다 — 의제 순서, 라운드 구성, 승인 지점, 완결 규칙을 선언적 형식으로 적은 문서다. 런타임의 **Process Interpreter**가 템플릿을 읽어 협상 코어의 기능을 순서대로 호출하며 절차를 실행한다.

| Component | 위치 | 역할 |
|---|---|---|
| Scenario Template | 데이터 | 시나리오의 절차 정의 (코드가 아님) |
| Template Registry | 각 단말 | 템플릿의 저장·배포·버전 관리 |
| Process Interpreter | 각 단말 | 템플릿을 해석해 코어 기능 호출로 절차를 진행 |

**정상 동작:** 새 시나리오 = 템플릿 파일 추가 → Registry 배포 → Interpreter가 실행. **오류 상황:** 잘못 정의된 템플릿(끝나지 않는 절차, 모순된 승인 지점)이 올 수 있다 — 로드 시 정적 검사를 하지만 임의 템플릿의 모든 오류를 사전에 걸러내기는 어렵다.

### 대안 B — 시나리오 플러그인형 (Scenario Plugin)

**도식**: [`drawio/38-B-시나리오-플러그인형.drawio`](drawio/38-B-시나리오-플러그인형.drawio)

**구조.** 시나리오마다 **정해진 interface를 구현한 코드 플러그인**을 만든다. **Plugin Loader**가 서명을 검증하고 동적으로 로드해 코어에 결합한다. 절차를 코드로 직접 쓰므로 표현에 제한이 없다.

| Component | 위치 | 역할 |
|---|---|---|
| Scenario Plugin | 코드 산출물 | 시나리오 절차를 interface에 맞춰 구현 |
| Scenario Interface (SDK) | 각 단말 | 코어가 플러그인에게 요구하는 계약 정의 |
| Plugin Loader | 각 단말 | 서명 검증 후 플러그인을 동적 로드 |

**정상 동작:** 새 시나리오 = 플러그인 작성·배포 → Loader가 로드 → 네이티브 실행. **오류 상황:** 플러그인 결함은 해당 시나리오에 격리된다 — 코어는 무변경이지만, "코드 변경 없이"라는 목표 기준으로는 새 시나리오마다 코드 작성이 필요하다.

### 대안 C — 빌딩 블록 조합형 (Block Composition)

**도식**: [`drawio/38-C-빌딩-블록-조합형.drawio`](drawio/38-C-빌딩-블록-조합형.drawio)

**구조.** 미리 만들어 검증한 **블록** — 라운드 유형(동시 제안형/순차형), 승인 유형(경계 승인/최종 승인), 완결 유형(전원/다수결/부분) — 의 **카탈로그**를 두고, 시나리오는 "어떤 블록을 어떤 순서로"라는 **조합 명세(데이터)** 로 정의한다. **Composer**가 명세대로 블록을 엮어 절차를 구성한다.

| Component | 위치 | 역할 |
|---|---|---|
| Block Catalog | 각 단말 | 사전 검증된 절차 블록들의 저장소 |
| Composition Spec | 데이터 | 블록 선택과 순서의 명세 (코드가 아님) |
| Composer | 각 단말 | 명세대로 블록을 엮어 실행 가능한 절차 구성 |

**정상 동작:** 새 시나리오 = 조합 명세 추가(카탈로그 내 조합이면 코드 변경 0) → Composer 구성 → 실행. **오류 상황:** 카탈로그에 없는 형태의 절차가 필요하면 블록을 새로 만들어야 한다(이때만 코드 작성) — 그 전까지 해당 시나리오는 표현 불가.

## 4. QA Trade-off 평가표

(SC-참여자·SC-의제·Confidentiality 축은 세 대안 모두 (0) — 시나리오 표현 방식은 참여자·의제 확장이나 정보 노출과 직교한다. Recoverability도 세 대안 모두 (0) — 어느 쪽이든 절차 정의의 버전 일치만 맞으면 복원 방식이 같다.)

| QA | A. 선언적 템플릿 해석형 | B. 시나리오 플러그인형 | C. 빌딩 블록 조합형 |
|---|---|---|---|
| Functional Correctness | (−)<br>임의로 기술된 템플릿의 절차 오류(모순된 승인 지점, 끝나지 않는 구성)를 사전 검증으로 다 걸러내기 어렵다 — 잘못된 절차로 협상이 진행될 위험 | (+)<br>코드 리뷰·테스트를 거친 구현이라 절차의 정확성을 확보하기 가장 쉽다 | (+)<br>블록 하나하나가 사전 검증되어 있어 조합 규칙만 검사하면 된다 |
| Fault Tolerance | (−)<br>해석기 하나의 결함이 모든 시나리오의 실행에 파급된다 | (0)<br>플러그인 결함은 해당 시나리오에 격리된다 — Loader는 단순해서 견고하다 | (0)<br>블록 결함은 그 블록을 쓰는 시나리오에 한정된다 |
| Analysability | (−)<br>오동작 시 "템플릿이 잘못인가, 해석기가 잘못인가"의 이중 진단이 필요하다 | (0)<br>일반적인 코드 디버깅과 같다 | (+)<br>진단 지점이 블록 단위로 잘게 나뉜다 — "어느 블록에서 어긋났나"가 바로 보인다 |
| Scalability (참여자 수) | (0)<br>직교 | (0)<br>직교 | (0)<br>직교 |
| Scalability (의제 조합) | (0)<br>직교 | (0)<br>직교 | (0)<br>직교 |
| Time Behaviour | (−)<br>실행할 때마다 해석(interpretation) 비용이 붙는다 | (+)<br>네이티브 코드 실행이라 절차 진행의 부가 비용이 가장 작다 | (0)<br>조합 구성 비용이 시작 시 한 번 들고, 실행은 블록 네이티브다 |
| Recoverability | (0)<br>템플릿 버전 일치 전제 하에 동일 | (0)<br>플러그인 버전 일치 전제 하에 동일 | (0)<br>명세·카탈로그 버전 일치 전제 하에 동일 |
| Resource Utilization | (−)<br>해석 계층이 상시 오버헤드를 만든다 | (+)<br>부가 계층 없이 가장 가볍다 | (0)<br>Composer 구성분만 소폭 추가 |
| Confidentiality | (0)<br>직교 | (0)<br>직교 | (0)<br>직교 |
| Adaptability | (+)<br>새 시나리오 = 데이터 추가 — "코드 변경 0" 목표에 유일하게 완전 부합하고 표현도 자유롭다 | (−)<br>새 시나리오마다 코드 작성·서명·배포가 필요하다 (코어는 무변경이지만 목표 기준에서 가장 멀다) | (0)<br>카탈로그 안의 조합이면 데이터만으로 되지만, 밖의 형태는 블록 코드 추가 전까지 표현할 수 없다 |

## 5. 배타성 확인

세 대안은 "시나리오가 무엇으로 존재하는가"가 다르다 — 자유 기술 데이터(A) / 코드(B) / 제한된 어휘의 조합 데이터(C). 실행 층도 그에 맞춰 해석기 / 로더 / 조합기로 대체 관계다. 둘을 함께 두면(예: 템플릿도 받고 플러그인도 받기) 같은 시나리오를 두 방식으로 정의할 수 있게 되어 정의 충돌·검증 이원화가 생기고, 이는 "시나리오 정의의 단일한 표준"이라는 본 문제의 목적과 어긋난다 — 그런 혼합은 별개의 제4안이지 A·B·C의 결합이 아니다.

## 6. 비지배 확인

- A는 FC·FT·Analy·TB·RU에서 진다 (우위: AD) ✓ — 목표(코드 변경 0) 그 자체를 유일하게 완전 충족하는 것이 A의 존재 이유다
- B는 AD에서 진다 (우위: FC·TB·RU) ✓
- C는 TB·RU(B 대비)·AD(A 대비)에서 진다 (우위: Analy·FC) ✓

## 7. 다른 문제와의 결정 의존

- **[`34`](34-의제-분해-어젠다-구조.md)**: 어젠다 구조(단일/순차/병렬)가 시나리오 정의의 표현 항목에 포함되어야 한다 — 34에서 B·C(다중 세션)를 골랐다면 시나리오 정의가 세션 오케스트레이션까지 기술해야 해 A의 템플릿 언어·C의 블록 어휘가 커진다.
- **[`32`](32-완결-규칙-실행-구조.md)**: 32-A(선언적 규칙 해석)를 골랐다면 본 문제의 A(템플릿 해석)와 해석 기반을 공유할 수 있고, C의 "완결 유형 블록"은 32의 규칙 정의를 블록화한 것이다.
- **[`36`](36-개입-시점-모델.md)**: 시나리오 정의에 "승인 지점"이 포함되므로, 36의 개입 반영 지점과 시나리오 정의의 승인 지점 표현이 같은 어휘를 써야 한다.
