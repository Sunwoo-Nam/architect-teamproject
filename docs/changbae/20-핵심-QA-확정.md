# 20. 핵심 QA 확정 (PL 확정본) — 설계 trade-off 평가의 공식 축

> 배경: PL이 지금까지의 분석(05~11 문서)을 바탕으로 핵심 QA 10개를 확정했다 (2026-08-05).
> **이후 모든 설계 문서(31~38)의 대안 trade-off 평가는 본 문서의 10개 QA만을 축으로 사용한다.**

---

## 20.1 확정 핵심 QA 10개

| # | QA (ISO/IEC 25010:2023 하위특성) | 품질 요구 문장 | 측정 항목 ([`10`](10-핵심-QA-측정-계획.md)) |
|---|---|---|---|
| 1 | **Functional Correctness** | 협상이 종료되었을 때 각 참여자의 의도·제약·선호에 비추어 올바른 합의로 판정되는 비율을 최대화해야 한다 — 제약 준수·레코드 일치의 절대 조건은 FR 합격 조건으로 검증한다 ([`21`](21-핵심-QA-측정-정의.md) §21.4) | QA-FC-1 |
| 2 | **Fault Tolerance** | 협상 진행 중 발생하는 일시 오류(메시지 유실·지연·응답 없음·일시 이탈)에도 협상이 중단 없이 정상 완결되는 비율을 최대화해야 한다 | QA-FT-1·2 |
| 3 | **Analysability** | 완료되거나 실패한 협상의 전 과정을 기록만으로 재구성하고 결함의 원인 지점(라운드·참여자·처리 단계)을 특정할 수 있는 비율을 최대화해야 한다 | QA-AN-1 |
| 4 | **Scalability (참여자 수)** | 참여자 수가 증가할 때 합의 시간·메시지 수·자원 사용량의 증가가 참여자 수에 대한 선형 이내로 유지되어야 한다 | QA-SC-1 |
| 5 | **Scalability (의제 조합)** | 의제 수와 의제별 후보 수가 증가할 때 전체 조합을 열거하지 않고도 탐색 시간과 메모리 사용이 정해진 예산 이내로 유지되어야 한다 | QA-SC-2 |
| 6 | **Time Behaviour** | 협상 시작부터 합의 완료까지 걸리는 총 시간을 최소화해야 한다 | QA-TB-1 |
| 7 | **Recoverability** | 완전히 중단된 협상 세션이 저장된 상태로부터 중단 지점에서 재개되고, 재개 후 전 참여자의 협상 상태가 일치하는 비율을 최대화해야 한다 | QA-RE-1 |
| 8 | **Resource Utilization** | 협상 1회가 사용하는 단말 자원(메모리 중심)을 최소화해야 한다 — 예산 초과(OOM) 금지는 FR 합격 조건으로 검증한다 ([`21`](21-핵심-QA-측정-정의.md) §21.4) | QA-RU-1 |
| 9 | **Confidentiality** | 협상 메시지의 관찰만으로 타 참여자의 선호 순위를 복원할 수 있는 정확도를 무작위 추측 수준까지 최소화해야 한다 | QA-CF-2 |
| 10 | **Adaptability** | 새로운 협상 시나리오를 지원할 때 필요한 코드 변경량을 최소화해야 한다 (목표: 템플릿·설정 정의만으로 수용) | QA-AD-1 |

## 20.2 뜻 풀이와 판정 방법

| QA | 뜻 풀이 (무엇을 말하는가) | 판정 방법 (어떻게 재는가) |
|---|---|---|
| Functional Correctness | 합의안을 참여자 한 사람 한 사람의 눈으로 보았을 때 — 내가 원했던 주제였고(의도), 내가 정한 한계(예산·시간대)를 어기지 않았고(제약), 내가 받아들일 만한 선택이었고(선호), 종료 시점에 전원이 동일한 합의 레코드를 갖고 있는가(종결) | [`09`](09-Functional-Correctness-정의.md)의 4계층으로 분리 판정 — 의도 정확성(L1)·선호 정합(L3)은 통계 지표(분류 정확도·정합 판정률), 제약 준수(L2)·합의 종결 정합(L4)은 FR 합격 조건(위반 0건)으로 검증 |
| Fault Tolerance | 메시지가 사라지거나 응답이 늦거나 참여자가 잠시 끊기는 일은 여러 명이 참여할수록 자주 생긴다 — 이런 일시 문제가 협상 전체를 멈추지 않고, 사용자가 눈치채지 못하게 흡수되는가 | 오류를 일부러 주입한 실험(메시지 유실·지연·무응답·이탈)에서 협상이 정상 완결(합의 또는 정상 결렬)된 비율 |
| Analysability | "왜 이 합의에 도달했는가"를 라운드별로 되짚을 수 있고, 문제가 생기면 어느 라운드·어느 참여자·어떤 처리에서 잘못됐는지 기록만으로 찾을 수 있는가 | 완료된 협상의 기록만으로 전 과정을 재구성하는 감사 실험 — 재구성 가능 비율과 원인 특정 소요 시간 |
| Scalability (참여자 수) | 3명일 때 되던 것이 5명·7명이어도 되는가 — 참여자 2배에 메시지 4배(제곱)가 되는 구조는 불합격 | 참여자 수 3·5·7로 같은 협상을 반복하고 시간·메시지·자원의 증가 곡선을 회귀 분석 — 선형 이내인지 확인 |
| Scalability (의제 조합) | 날짜×영화×영화관×시간처럼 조합이 곱으로 커질 때, 모든 조합을 미리 만들면 메모리가 터진다(out of memory) — 만들지 않고도 협상이 되는가 | 의제 수·후보 수를 늘려가며 메모리·탐색 시간을 측정하고, 가지치기 on/off를 대조 |
| Time Behaviour | 사람이 직접 조율하는 것보다 느리면 이 시스템은 존재 이유가 없다 | 합의 도달 총 시간 = 라운드 수(시뮬레이션) × 라운드 1회 실측 시간(온디바이스 추론+통신) |
| Recoverability | 앱 종료·OS의 프로세스 강제 종료·네트워크 완전 단절로 세션이 이미 죽은 뒤에도, 저장해 둔 상태에서 협상을 되살릴 수 있는가 | 임의 시점에 프로세스를 강제 종료 → 복구 성공률, 복구 후 전 참여자 상태 일치 여부, 재동기화 시간 |
| Resource Utilization | 협상은 폰의 백그라운드에서 돈다 — 자원을 많이 쓰면 OS가 죽이고 사용자가 끈다 | 실기기 프로파일러로 협상 1회당 피크 추가 메모리 계측 (CPU·배터리는 보조 관측, OOM 금지는 FR 검증 — [`21`](21-핵심-QA-측정-정의.md)) |
| Confidentiality | 내가 무엇을 제안하고 무엇을 수락·거절했는지를 남이 지켜보면 내 선호 순위가 유추된다 — 이 유추(역추론) 가능성 자체를 낮추는가 | 협상 메시지 기록만으로 타인의 선호 순위를 복원하는 공격 실험 — 복원 정확도가 무작위 추측 수준에 가까운지 |
| Adaptability | 아직 정의되지 않은 협상 시나리오(의제 순서·라운드 주제·승인 방식이 다른)가 추가될 때, 코드를 고치지 않고 받아들일 수 있는가 | 설계 시 참조하지 않은 새 시나리오를 템플릿·설정으로 정의해 실행 — 성공 여부와 코드 변경량(diff) 확인 |

> **Fault Tolerance와 Recoverability의 차이:** 두 QA는 "언제"와 "어떻게"가 다르다. Fault Tolerance는 세션이 **살아 있는 동안** 오류를 흡수해서 **죽지 않게** 하는 능력이고(수단: 재시도·대체 실행 — 사용자는 문제를 모른다), Recoverability는 세션이 **이미 죽은 뒤** 저장된 상태에서 **되살리는** 능력이다(수단: 상태 저장·복원·참여자 재동기화 — 사용자는 중단을 인지했을 수 있다). 발동 조건(일시 오류 vs 완전 중단), 필요한 SW 장치(재시도 로직 vs 영속 저장소·복원 절차), 측정 방법(무중단 완결률 vs 복구 성공률)이 모두 달라 **하나로 합치지 않고 별개 QA로 유지한다.** 합치면 "매 라운드 상태를 저장하면 복구는 쉬워지지만 시간·자원을 쓴다" 같은 두 품질 사이의 trade-off가 보이지 않게 된다.

## 20.3 확정 10개에 들지 않은 항목의 지위

다음 항목들은 측정·관리 대상([`10`](10-핵심-QA-측정-계획.md))으로는 유지되지만, 설계 대안의 trade-off 평가 축으로는 사용하지 않는다:

| 제외 항목 | 지위 |
|---|---|
| QA-TE-1 시험 용이성 | 전 QA 측정의 전제 조건 — 대안 간 우열 축이 아니라 모든 대안이 공통으로 갖춰야 할 기반 |
| QA-OC-1 운용 제약 준수 | 위반 0건의 절대 제약 — trade-off 대상이 아니라 모든 대안이 지켜야 할 불변 조건 |
| QA-OP-1 운용성/사용자 통제 | 개입 시점 모델([`36`](36-개입-시점-모델.md))의 문제 정의 자체에 내장되어 다뤄짐 |
| QA-CX-1 공존성 | OS 정책 준수 — 배포 전 검증 항목 |
| QA-CF-1 정책 기반 비공개 보호 | 위반 0건의 절대 제약 (Confidentiality 축은 역추론 방지 QA-CF-2만 사용) |
| QA-FC-2 효용 분배 균형 | 완결 규칙([`32`](32-완결-규칙-실행-구조.md)) 설계의 참고 지표로만 사용 |
| QA-FT-2 참여자 상실 지속 | Fault Tolerance 축의 판정 범위에 포함해 평가 |
