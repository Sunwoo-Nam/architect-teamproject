# 32. 설계 문제 — 완결 규칙 실행 구조 (Consensus Rule Execution)

> 문제 정의·의존: [`30`](30-설계-문제-총괄.md) §30.1 · 평가 축: [`20`](20-핵심-QA-확정.md)의 확정 QA 10개
> 관련 CFR: B9 합의 완결 규칙 · D1 승인 수집 · 관련 지표: QA-FC-2 효용 분배 균형 (참고)

---

## 1. 문제 정의

협상 라운드에서 참여자들이 수락/거절 표를 냈을 때, **"합의가 성립했는가"를 판정하는 일**을 어디서 어떤 component가 수행하는가의 문제다. 어려운 이유는 완결 규칙이 하나가 아니기 때문이다 — 시나리오에 따라 **전원 합의**여야 하는 경우, **다수결**이면 되는 경우, **승인한 사람들만 추려 부분 완결**하는 경우가 모두 있고, 아직 정의되지 않은 규칙도 올 수 있다.

이 판정을 잘못 설계하면: 참여자마다 성립 여부를 다르게 판단해 일부는 "합의됐다", 일부는 "아직이다"로 갈리거나(정확성 훼손), 판정하는 곳이 죽으면 표가 다 모였는데도 협상이 끝나지 못하거나(감내성 훼손), 새 규칙이 올 때마다 코드를 고쳐야 한다(적응성 훼손).

## 2. 전제와 제약 (모든 대안에 공통)

- 각 참여자의 수락/거절 판단 자체는 NegMAS threshold 판정으로 각자 단말에서 이루어진다 — 본 문제는 그 **표들을 모아 성립을 판정하는 부분**만 다룬다.
- 어떤 대안이든 위임 범위 검사(threshold를 넘어도 위임 밖이면 수락 불가)와 "승인하지 않은 참여자에게 확정 효력 없음"은 동일하게 지켜진다.
- 성립 판정 이후 확정 레코드의 전파는 별도 문제([`37`](37-합의-확정-구조.md))다.

## 3. 대안

### 대안 A — 중앙 판정형 (Central Verdict)

**도식**: [`drawio/32-A-중앙-판정형.drawio`](drawio/32-A-중앙-판정형.drawio)

**구조.** 판정을 맡은 단말(예: 개시자) 한 곳에 **Consensus Evaluator**를 두고, 전 참여자의 표를 모아 규칙에 따라 판정한 뒤 결과를 배포한다. 완결 규칙은 코드가 아니라 **선언적 정의(데이터)** — "수락 수 ≥ 전체" 또는 "수락 수 > 절반" 같은 조건식 — 로 로드되어 Rule Interpreter가 해석한다.

| Component | 위치 | 역할 |
|---|---|---|
| Vote Collector | 판정 단말 | 참여자들의 수락/거절 표를 수집하고 시한을 관리한다 |
| Rule Interpreter | 판정 단말 | 시나리오에 지정된 완결 규칙 정의(데이터)를 읽어 조건 충족 여부를 계산한다 |
| Verdict Publisher | 판정 단말 | 성립/미성립/결렬 판정 결과를 전 참여자에게 배포한다 |
| Vote Submitter | 각 참여자 단말 | 자기 표를 판정 단말에 제출한다 |

**정상 동작:** 표 수집 → 규칙 해석·판정 → 결과 배포. **오류 상황:** 판정 단말이 죽으면 표가 모여 있어도 성립 판정이 멈춘다 — 복구 절차로 이관될 때까지 협상이 대기한다.

### 대안 B — 분산 합치 판정형 (Distributed Verdict)

**도식**: [`drawio/32-B-분산-합치-판정형.drawio`](drawio/32-B-분산-합치-판정형.drawio)

**구조.** 판정하는 곳을 따로 두지 않는다. 전 참여자가 표를 서로에게 브로드캐스트하고, **각 단말이 동일한 규칙 모듈로 각자 판정**한 뒤, 판정 결과를 교환해 서로 일치하는지 대조한다.

| Component | 위치 | 역할 |
|---|---|---|
| Local Verdict Engine | 각 참여자 단말 | 수신한 표 전체를 놓고 자기 단말에서 성립 여부를 판정한다 |
| Verdict Exchange | 각 참여자 단말 | 자기 판정 결과를 전원과 교환한다 |
| Mismatch Resolver | 각 참여자 단말 | 판정이 갈리면(표 누락 등으로) 표를 재수집해 재판정을 중재한다 |

**정상 동작:** 표 브로드캐스트 → 각자 판정 → 판정 결과 교환·일치 확인. **오류 상황:** 어느 단말이 죽어도 나머지가 판정을 낼 수 있다. 대신 표 도착 차이로 판정이 갈릴 수 있고, 그때 Resolver의 재수집·재판정 왕복이 추가된다.

### 대안 C — 서명 누적형 (Signature Accumulation)

**도식**: [`drawio/32-C-서명-누적형.drawio`](drawio/32-C-서명-누적형.drawio)

**구조.** 판정자가 아예 없다. 합의 후보 문서가 참여자들을 돌면서 **수락하는 사람의 서명이 문서에 누적**되고, 규칙이 요구하는 서명 수(전원/과반/지정 인원)가 채워지는 순간 **문서 스스로가 성립의 증명**이 된다.

| Component | 위치 | 역할 |
|---|---|---|
| Signature Accumulator | 각 참여자 단말 | 후보 문서를 받아 수락이면 자기 서명을 첨부하고 다음으로 넘긴다 |
| Threshold Monitor | 각 참여자 단말 | 문서의 서명 수가 규칙 조건을 충족하면 성립을 선언하고 순환을 종료한다 |

**정상 동작:** 문서 순환 → 서명 누적 → 조건 충족 시 성립. **오류 상황:** 문서를 쥔 단말이 지연되면 그만큼 전체가 기다린다. 문서 유실 시 마지막 보유 단말의 사본에서 복원한다.

## 4. QA Trade-off 평가표

(SC-의제 축은 세 대안 모두 (0) — 성립 판정 방식은 의제 조합 처리와 무관하다.)

| QA | A. 중앙 판정형 | B. 분산 합치 판정형 | C. 서명 누적형 |
|---|---|---|---|
| Functional Correctness | (+)<br>판정이 한 곳에서 한 번만 이루어져 전원이 동일한 성립 결과를 받는다 — 판정 갈림이 구조적으로 없음 | (−)<br>표 도착 차이로 단말마다 판정이 갈릴 수 있다 — Resolver가 못 잡으면 일부는 성립, 일부는 미성립으로 인식 | (+)<br>서명이 붙은 문서 자체가 증명이라 "성립했는데 아닌 줄 아는" 상태가 존재할 수 없다 |
| Fault Tolerance | (−)<br>판정 단말이 죽으면 표가 다 모였어도 성립 판정이 멈춘다 | (+)<br>판정 지점이 없어 누구든 판정 가능 — 단말 하나의 실패가 판정을 막지 못한다 | (−)<br>문서를 쥔 단말의 지연·실패가 곧 서명 수집 정지다 |
| Analysability | (+)<br>표·판정·근거가 판정 단말 한 곳에 모여 "왜 성립했나"의 재구성이 가장 쉽다 | (−)<br>N개의 판정 기록을 모아 대조해야 하고, 판정 갈림·중재 이력까지 얽힌다 | (+)<br>서명 체인 자체가 시간 순서의 증적 — 문서 하나가 곧 감사 자료다 |
| Scalability (참여자 수) | (0)<br>표 수집·결과 배포가 선형 — 판정 단말 부하만 N에 비례 | (−)<br>표 브로드캐스트에 더해 판정 결과 교환까지 전원-전원으로 늘어난다 | (−)<br>서명이 순차로 쌓여 수집 시간이 인원수에 비례한다 |
| Scalability (의제 조합) | (0)<br>무관 | (0)<br>무관 | (0)<br>무관 |
| Time Behaviour | (+)<br>표 제출 → 판정 → 배포의 한 왕복으로 끝난다 | (−)<br>각자 판정 후 결과 교환·대조라는 추가 단계가 매번 붙는다 | (−)<br>순차 서명이라 성립 확인까지의 시간이 가장 길다 |
| Recoverability | (0)<br>판정 상태가 한 곳이라 참여자 복구는 쉽지만, 판정 단말이 죽으면 수집된 표까지 함께 복구해야 해 무겁다 — 상쇄 | (−)<br>부분 판정 상태가 전 단말에 흩어져 있어 복구 시 재조립이 복잡하다 | (+)<br>복원할 것이 서명 누적 문서 하나 — 어디까지 진행됐는지가 문서에 그대로 있다 |
| Resource Utilization | (0)<br>계산이 판정 단말에 집중되나 총량은 작다 | (−)<br>같은 판정 계산을 전원이 중복 수행한다 | (+)<br>한 번에 한 단말만 서명 작업 — 총 자원 소모가 가장 적다 |
| Confidentiality | (0)<br>표가 판정 단말에만 모여 참여자 간에는 비공개 가능 — 대신 한 단말이 전원의 표를 본다 | (−)<br>전원이 전원의 수락/거절을 본다 — 역추론 재료가 가장 많이 노출된다 | (+)<br>공개되는 것은 최종 서명 사실뿐 — 중간의 망설임·거절 이력을 문서에 남기지 않는 구성이 가능하다 |
| Adaptability | (+)<br>새 완결 규칙 = 선언적 정의 추가 — 판정 단말 한 곳만 새 정의를 로드하면 된다 | (−)<br>전 단말의 규칙 모듈이 동시에 같은 버전이어야 한다 — 배포·불일치 문제 | (0)<br>서명 수 조건으로 표현되는 규칙(전원·과반·지정 수)은 쉽게 수용하나, 그보다 복잡한 규칙(가중 투표 등)은 표현이 어렵다 |

## 5. 배타성 확인

성립 판정의 권위가 어디에 있는가 — 한 곳(A), 각자 합치(B), 문서 자체(C) — 는 하나만 선택해야 한다. 둘 이상을 동시에 두면 판정 주체가 둘이 되어 서로 다른 결론이 났을 때 어느 쪽이 맞는지 정할 상위 판정이 또 필요해진다(무한 후퇴). component도 대체 관계다: A의 Evaluator, B의 Verdict Engine+Resolver, C의 Accumulator+Monitor는 같은 일을 다른 곳에서 하는 장치라 공존하면 역할이 충돌한다.

## 6. 비지배 확인

- A는 FT·Rec·RU·Conf에서 진다 (우위: FC·Analy·TB·AD) ✓
- B는 FC·Analy·SC-참여자·TB·Rec·RU·Conf·AD에서 진다 (우위: FT) ✓
- C는 FT·SC-참여자·TB에서 진다 (우위: Rec·RU·Conf) ✓

## 7. 다른 문제와의 결정 의존

- **[`31`](31-제안-토폴로지.md)**: A는 star(31-A)의 Coordinator와 자연스럽게 결합되고, mesh(31-B)에서는 판정 단말을 따로 선출해야 한다. C는 ring(31-C)의 문서 순환과 결이 같다 — 토폴로지와 판정 구조를 엇갈리게 고르면 두 경로가 공존해 복잡도가 커진다.
- **[`35`](35-이탈-무응답-처리-구조.md)**: 참여자가 줄었을 때 "규칙을 남은 인원 기준으로 재적용"하는 주체가 본 결정의 판정 주체와 같아야 한다.
- **[`37`](37-합의-확정-구조.md)**: 성립 판정(본 문제)과 확정 레코드 전파(37)는 연속 단계다 — C(서명 누적)를 고르면 37의 서명 순환형과 문서를 공유할 수 있어 결합 이득이 있다.
