# 22. Quality Attribute Workshop — 핵심 QA 우선순위 선정

> 배경: PL 지시(2026-08-09)로 [`20`](20-핵심-QA-확정.md)의 확정 핵심 QA 10개에 대해 QAW(Quality Attribute Workshop)를 수행한다.
> 참석자: [`01`](01-Stakeholder-도출.md)의 stakeholder 10개 역할. 각 역할은 01·02·05 문서의 역할 정의·요구사항을 페르소나로 부여한 **독립 sub-agent가 시뮬레이션**했다 — 실제 인물의 채점이 아니며, 문서에 기록된 이해관계만 반영된다.

---

## 22.1 방법 — QAW 원전과 본 워크숍의 변형점

SEI의 QAW는 아키텍처가 만들어지기 전에 이해관계자들이 모여 품질 속성 요구를 도출·우선순위화하는 촉진형(facilitated) 워크숍으로, 8단계로 진행된다: ① 워크숍 소개 → ② 비즈니스/미션 발표 → ③ 아키텍처 계획 발표 → ④ 아키텍처 드라이버 식별 → ⑤ 시나리오 브레인스토밍 → ⑥ 시나리오 통합 → ⑦ 시나리오 우선순위화 → ⑧ 시나리오 정제 (SEI, *Quality Attribute Workshops (QAWs), Third Edition*, 2003).

본 워크숍은 원전을 다음과 같이 변형해 적용했다 — 변형 사실을 명시한다:

| 구분 | QAW 원전 | 본 워크숍 |
|---|---|---|
| 평가 대상 | 브레인스토밍으로 생성한 품질 속성 시나리오 | [`20`](20-핵심-QA-확정.md)에서 이미 확정된 QA 10개 (④~⑥단계는 01~20 문서로 선행 완료) |
| 우선순위화 방식 | 투표 (각자 시나리오 수의 약 30% 표를 배분) | 중요도·난이도 각 1~10점 채점 (PL 지시) — ATAM Utility Tree의 (Importance, Difficulty) 쌍 평가를 정밀화한 척도로, 04·07·08의 H/M/L 평가와 같은 계열이다 |
| 토론 | 시나리오 통합·정제 과정의 상호 토론 | 2라운드 Delphi식 재론 — 이견(표준편차) 상위 3개 QA에 대해 평균과 2점 이상 벌어진 채점자가 반대 근거를 읽고 재채점 |

**운영 규칙** (분석 조건):
- **정의**: 중요도 = 이 과제에서 이 QA가 얼마나 중요한가. 난이도 = 이 QA를 만족시키는 것이 SW 구조적으로 얼마나 어려운 작업인가 (PL 정의).
- **채점 앵커**: 중요도 10~9 = 무너지면 과제 실패 / 8~7 = 주요 시나리오에서 즉시 체감 / 6~5 = 일부 미달 단기 감수 가능 / 4~3 = 특정 상황에서만 문제 / 2~1 = 이번 범위에서 무시 가능. 난이도 10~9 = 알려진 구조로 달성 방법 불명확(연구 수준) / 8~7 = 여러 component에 걸친 구조 결정 + 상충 QA trade-off 조율 / 6~5 = 표준 패턴은 있으나 다자 확장 설계 필요 / 4~3 = 알려진 해법 적용 / 2~1 = 기성 컴포넌트로 해결.
- **독립 채점**: 각 역할은 자기 역할의 01·02·05 기록과 20·21(§21.2)만 읽고 채점했다. 기존 평가 문서(04·07·08·11)와 타 역할의 점수는 차단했다 (앵커링 방지).
- **난이도 취합 범위**: 중요도는 10개 역할 전원, 난이도는 기술 역할 8인(S3~S10)만 취합한다 — 비기술 역할(개시·참여 사용자)은 SW 구조 난이도 판단의 신뢰도가 낮다 (PL 확정).
- **우선순위 산식**: 우선순위 점수 = 중요도 평균 + 난이도 평균 (PL 확정) — 중요하고 어려운 항목이 아키텍처가 집중할 대상이라는 ATAM의 ASR 논리를 따른다.

## 22.2 최종 우선순위 (결론)

등급 기준 (분석자 정의 — §22.1의 채점 앵커 경계와 일치시킴): **H** = 평균 7.0 이상 (앵커의 "주요 시나리오에서 즉시 체감"/"여러 component에 걸친 구조 결정" 경계 이상), **M** = 5.0 이상 7.0 미만 (앵커의 "일부 미달 감수 가능"/"다자 확장 설계 필요" 구간), **L** = 5.0 미만 (앵커의 "특정 상황에서만 문제"/"알려진 해법 적용" 이하). 괄호 안은 각 축 내 순위다.

| 순위 | QA | 중요도 평균 (순위 · 등급) | 난이도 평균 (순위 · 등급) | 우선순위 점수 | 해석 |

AN은 사용자·MX H/W가 품질 검증팀의 논거(실기기 의존 없는 검증 방식은 기록 기반 재구성이 무너지면 전체가 무력화됨)에 상향했고, FC는 저점자 2명(SRE 4→6, MX H/W 5→7)이 상향하고 고점자 전원이 유지해 1위 합의가 더 단단해졌다.

## 22.7 이견 분석

1. **Confidentiality — 재론 후에도 이견 최대(중요도 σ 2.12)**. 수요 당사자(참여 사용자 8, Security/Privacy 10, 개시 사용자 9)와 비당사 기술 역할(PL·Architect·알고리즘 5, SRE·MX H/W 4)의 격차는 역할 이해관계의 실질적 차이라 토론으로 소거되지 않는다. 반면 **난이도는 σ 0.33(전원 8~9)으로 전 항목 중 최고 합의** — "가장 어렵다"는 데는 아무도 이견이 없다. 해석: CF의 종합 2위는 평균이 만든 순위이므로, 설계 결정([`33`](33-정보-공개-구조.md))에서는 "평균적으로 두 번째로 중요한 QA"가 아니라 **수요 당사자에게는 거부권(위임 자체를 시작하지 않음), 나머지에게는 부차적인 비대칭 QA**로 다루어야 한다.
2. **Recoverability(σ 1.85) — 운영 대 프로젝트 관리의 시각차**. SRE 10·MX H/W 8·MAF 8 대 PL 4·알고리즘 4. PL의 "PoC 데모는 재시작으로 대체 가능" 논거와 운영 계열의 "온디바이스에서 프로세스 종료는 일상" 논거가 맞선 것으로, 재론 대상(상위 3개)에 들지 않아 미해소로 남았다. 다만 PL 페르소나의 저점 근거는 과제를 PoC로 보는 전제에 기대고 있다 — 전제의 타당성은 §22.8 참조.
3. **Resource Utilization 최하위(10위)의 해석 주의**. MX H/W 혼자 10을 주고 나머지가 3~7을 준 것은 RU의 절대 제약(OOM 강제 종료 금지)이 [`21`](21-핵심-QA-측정-정의.md) §21.4에서 FR 합격 조건으로 이관되어, QA 축에는 "예산 내에서 얼마나 아끼는가"의 정도 문제만 남았기 때문이다. **10위는 "자원을 무시해도 된다"가 아니라 "절대선은 FR이 지키고 있다"는 뜻**이다.
4. **Adaptability 9위 — PL 지정 QA의 하위권**. 20에서 PL이 직접 핵심 QA로 지정했던 항목이나, 워크숍에서는 Architect(8)만 상위를 주고 사용자(2~3)·운영(4)·보안(4)이 낮게 봤다. "이번 과제(시나리오 2 검증)의 성패"와 "플랫폼의 장기 가치"가 다른 시간 축에 있다는 것이 원인이며, PL 본인 페르소나도 5를 줬다 — 기록해 두고 PL의 재확인을 권한다.
5. **우선순위와 설계 문서의 연결**. 상위 3개(FC·CF·SC1)를 좌우하는 결정은 [`33`](33-정보-공개-구조.md)(CF의 사실상 유일한 주 축)과 [`31`](31-제안-토폴로지.md)(SC1의 지배 요인)이다 — [`40`](40-설계-단계-레포트.md) §40.4의 관찰("Confidentiality는 33에서만 주 축", "의존의 병목은 31")과 정합하며, 결정 순서 권고(31 먼저)를 이 우선순위가 재지지한다.

## 22.8 방법의 한계

- **시뮬레이션 한계**: 참석자는 실제 이해관계자가 아니라 01·02·05 문서를 페르소나로 부여받은 sub-agent다. 문서에 기록되지 않은 이해관계(조직 정치, 일정 압박 등)는 반영되지 않으며, 실제 워크숍의 대체가 아니라 **문서화된 요구사항의 일관성 있는 우선순위 투영**으로 읽어야 한다.
- **척도 주관성**: 채점 앵커로 통제했으나 역할 간 척도 사용이 완전히 일치한다는 보장은 없다. 순위 해석은 점수 차 0.5 이내 항목 간에는 유보적이어야 한다 (4~8위 구간: 13.3~12.0).
- **재론 범위**: 2라운드는 표준편차 상위 3개 QA로 한정했다. SC2(σ 2.00)·RU(σ 1.91)·REC(σ 1.85)도 이견이 상당하나 재론하지 않았다 — §22.7-2·3에 이견 구조만 기록했다.
