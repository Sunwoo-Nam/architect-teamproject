# 21. 핵심 QA 측정 정의 — QA당 핵심 지표 1개

> 배경: [`20`](20-핵심-QA-확정.md)에서 확정한 핵심 QA 10개의 측정을 정의한다 (PL 지시, 2026-08-06).
> 본 문서가 **핵심 QA 측정의 정본**이다 — [`10`](10-핵심-QA-측정-계획.md)의 측정표 중 목표 수준 정의는 본 문서로 대체되며, 10의 테스트 환경 정의와 실험 방법은 그대로 참조한다.

---

## 21.1 측정 원칙

1. **QA당 핵심 지표는 1개다.** 여러 지표를 병렬로 재면 "이 QA를 달성했는가"의 판정이 흐려진다 — 대표성 있는 지표 하나로 판정하고, 나머지 관측값은 원인 분석용 보조 데이터로만 쓴다.
2. **QA 지표는 연속적인 정도(degree)여야 한다.** 높을수록 좋거나 낮을수록 좋은 스칼라 값이어야 하고, 목표는 "어떤 수준 이상/이하"로 정의된다.
3. **"위반 0건", "불일치 0건", "일치 100%" 같은 on/off 조건은 QA 지표가 아니다.** 그것은 기능이 맞게 동작하는가의 문제, 즉 **FR의 합격 조건**이다. 이런 조건들은 §21.4로 이관해 FR 검증(합격/불합격 판정)으로 다룬다 — QA 평가에는 넣지 않는다.
4. **목표값에서 임의 상수를 최소화한다.** 목표는 ① 수학적 기준선(선형 지수 1, 전체 열거 지수 1, 무작위 추측 확률), ② 자기 실측 앵커(무주입 베이스라인, 실환경 오류율, 물리적 하한, 단말 예산), ③ 공학적 안전 계수(차수 여유) 중 하나로부터 도출한다. 측정 잡음의 여유는 임의 상수가 아니라 **신뢰구간 판정**으로 처리한다. 그래도 남는 분석자 판단은 그렇게 표시하고 보정 조건을 함께 적는다.
5. **모든 지표는 기계적으로 판정한다.** 실사용자 평가는 수행하지 않는다 — 수용성 판정이 필요한 지표는 사전 등록된 프로파일 기준의 Mock 판정기로 대체한다. 측정의 1차 용도는 **설계 대안 PoC의 비교**다: 대안별 핵심 기능만 구현한 PoC에 동일 하니스·동일 시드를 적용하고 대안만 교체해 잰다.

## 21.2 핵심 지표 요약표

| QA | 핵심 지표 | 방향 | 목표 수준 | 측정 환경 |
|---|---|---|---|---|
| Functional Correctness | 정합 판정률 (Mock 판정기의 "수정 불요" 판정 비율) | 높을수록 좋음 | **≥ 70%** | ENV-A + Mock 판정기 |
| Fault Tolerance | 내성 여유 배수 (임계 주입 강도 ÷ 실환경 오류율) | 높을수록 좋음 | **≥ 10배** | ENV-A (앵커는 ENV-B 실측) |
| Analysability | 인과 재구성 성공률 (정상·결함 표본 공통, 건당 30분 한도) | 높을수록 좋음 | **≥ 95%** | ENV-A |
| Scalability (참여자 수) | 확장 지수 b (합의 시간 ∝ N^b) | 낮을수록 좋음 | **95% 신뢰구간 하한 ≤ 1** (선형 초과가 통계적으로 확인되지 않아야 함) | ENV-A×B 합성 |
| Scalability (의제 조합) | 조합-메모리 탄력성 c (피크 메모리 ∝ 조합 수^c) | 낮을수록 좋음 | **95% 신뢰구간 상한 < 1** (전체 열거 기각) | ENV-B |
| Time Behaviour | 프로토콜 오버헤드 비율 (합의 시간 ÷ 필수 추론 시간 합) | 낮을수록 좋음 | **≤ 2** | ENV-B (3인 판정 + 7인 보조 보고) |
| Recoverability | 복구 시간 비율 (복구 소요 ÷ 정상 라운드 1회 시간) | 낮을수록 좋음 | **≤ 1** | ENV-A |
| Resource Utilization | 협상 1회당 피크 추가 메모리 | 낮을수록 좋음 | **앱 가용 예산의 ≤ 50%** (예산은 단말 실측으로 고정) | ENV-B |
| Confidentiality | 역추론 이득 (공격자 정확도 − 무작위 기준선) | 낮을수록 좋음 | **≤ +10%p** | ENV-A |
| Adaptability | 신규 시나리오 수용 공수 (실작업 시간 평균) | 낮을수록 좋음 | **≤ 8시간 (1인일)** | 개발 환경 + ENV-A |

## 21.3 지표별 정의와 목표 산정 근거

**1. Functional Correctness — 정합 판정률 ≥ 70%**
- **정의**: 시스템이 제시한 합의안에 대해 **Mock 판정기**가 참여자별 정답 프로파일 기준으로 "수정 불요"로 판정한 비율. 산식 = 수정 불요 판정 수 ÷ 전체 판정 수 (참여자-협상 단위로 집계).
- **순환 판정의 차단**: 판정기가 협상 에이전트와 같은 정보로 판정하면 측정이 순환한다(시스템이 최적화한 함수로 시스템을 채점). 그래서 **정답 프로파일(의도·제약·선호의 전체 명세)은 판정기에만 봉인**하고, 에이전트에는 부분 정보(사용자 발화·위임 범위)만 준다 — 지표는 "부분 정보에서 출발한 시스템이 참여자가 실제 원하는 것에 도달했는가"를 잰다.
- **목표 산정 논리**: 이 시스템의 가치는 "맡기면 알아서 되는 것"이다. 제시안 3건 중 1건 넘게 손봐야 한다면 사용자는 "결국 내가 직접 고르는 게 낫다"고 판단하게 되어 위임 가치가 무너진다 — 수정 요구가 1/3을 넘지 않는 수준, 즉 70%를 기준으로 한다 (분석자 제안). 파일럿 실측에서 베이스라인이 크게 다르면 보정한다.

**2. Fault Tolerance — 내성 여유 배수 ≥ 10배**
- **정의**: 주입 강도(세션당 오류 이벤트 비율)를 높여가며 정상 완결 분포를 측정했을 때, **완결 분포가 무주입 베이스라인 대비 유의하게 저하되기 시작하는 임계 강도**를 실환경에서 실측한 오류율로 나눈 배수. "얼마나 심한 오류 환경까지 견디는가"를 잰다.
- **왜 이 지표인가**: "완결률 ≥ X%" 형태는 (100 − X)%의 실패를 감수한다는 뜻인데 그 X를 논리적으로 정할 방법이 없다. 내성 여유 배수는 그 문제가 없다 — 앵커 두 개(무주입 베이스라인의 완결 분포, 실환경 오류율)가 모두 **실측값**이고, 목표는 그 사이의 여유 크기다. 저하 판정에 합의/결렬 **구성비**를 쓰므로, 오류를 만나면 즉시 결렬해버리는 퇴화 전략도 결렬률 급증이 저하로 잡혀 걸러진다.
- **목표 산정 논리**: 실환경 오류율(무선 유실·타임아웃)은 장소·시간대에 따라 수 배 단위로 변동한다. 변동이 배수 단위인 값에 대한 여유는 **한 차수(10배)** 를 확보해야 안전하다는 공학적 안전 계수 논리다.

**3. Analysability — 인과 재구성 성공률 ≥ 95% (건당 30분 한도)**
- **정의**: 표본 세션(정상 + 결함 주입)에 대해, 진단자가 **로그만으로** 인과를 30분 안에 정확히 재구성한 비율. 재구성 과제는 세션 유형별로 통일된 형식이다 — 정상 세션: "합의를 성립시킨 결정 요인(어느 라운드의 어떤 제안·수락이 결정적이었고, 각 참여자의 효용 근거는 무엇이었나)", 결함 세션: "원인 3요소(어느 라운드 · 어느 참여자 · 어느 처리 단계)".
- **왜 정상 세션도 재는가**: 기록의 용도는 결함 진단만이 아니다 — 성공 사례의 인과가 기록에서 재구성되어야 모델 개선·강화 학습·skill화 같은 후속 활용이 가능하다. 다만 "모든 결정 지점에 근거가 기록되어야 한다"는 **기록 완전성 요구 자체는 on/off 조건이므로 FR로 검증**하고(§21.4), 이 QA는 그 기록으로 사람이 실제로 인과를 재구성할 수 있는 정도를 잰다.
- **목표 산정 논리**: 표본 40건 중 실패 2건(95%) — 재구성 실패가 5%를 넘으면 개별 실수가 아니라 로그 체계의 구조적 사각(기록 안 되는 경로)이 있다는 신호로 본다. 30분 한도는 한 번의 집중 작업 단위 안에 진단이 끝나야 실무에서 쓰인다는 기준이다 (분석자 제안).

**4. Scalability (참여자 수) — 확장 지수 b, 95% 신뢰구간 하한 ≤ 1**
- **정의**: 참여자 수 N ∈ {3, 5, 7}에서 측정한 합의 도달 시간을 시간 ∝ N^b 로 회귀했을 때의 지수 b와 그 신뢰구간.
- **목표 산정 논리**: 요구([`20`](20-핵심-QA-확정.md))는 "선형 이내"이고 선형의 수학적 기준선은 **b = 1**이다. 측정 잡음 때문에 점추정이 1을 조금 넘을 수 있는데, 그 여유를 임의 상수로 두는 대신 **통계 판정**으로 처리한다: b의 95% 신뢰구간 하한이 1을 초과하면 — 즉 "선형보다 나쁘다"가 통계적으로 확인되면 — 위반이다. 기준선은 수학적 1 하나뿐이고 임의 상수가 없다. 참고로 전원-전원 직접 통신의 이론값은 b ≈ 2다.

**5. Scalability (의제 조합) — 조합-메모리 탄력성 c, 95% 신뢰구간 상한 < 1**
- **정의**: 전체 조합 수 S(= 의제별 후보 수의 곱, K×L×M×P)를 늘려가며 측정한 피크 메모리를 메모리 ∝ S^c 로 회귀했을 때의 지수 c와 그 신뢰구간.
- **목표 산정 논리**: 앵커가 양쪽에 있다 — 상계는 **전체 열거의 이론값 c = 1**(모든 조합을 생성·보관하면 메모리가 조합 수에 정비례), 하계는 **순차 좁히기 설계의 이론값 c ≈ 1/d**(의제 d개를 차례로 좁히면 메모리가 곱 Πnᵢ이 아니라 합 Σnᵢ 규모 — d = 4면 약 0.25). 판정은 "c의 95% 신뢰구간 상한 < 1", 즉 **전체 열거 구조가 통계적으로 기각되어야 한다**로 하고, 점추정이 설계 이상값 1/d에서 얼마나 떨어져 있는지를 함께 보고한다. 두 앵커 모두 수학적 도출값이라 임의 상수가 없다.

**6. Time Behaviour — 프로토콜 오버헤드 비율 ≤ 2 (3인 기준 판정, 7인 보조 보고)**
- **정의**: 실측한 합의 도달 시간 ÷ 필수 추론 시간 합. 분모는 그 세션에서 실제 발생한 온디바이스 LLM 추론 호출 시간의 합 — 어떤 구조를 쓰든 지불해야 하는 **물리적 하한**이다. 비율에서 1을 뺀 부분이 프로토콜(통신 왕복·대기·조정)이 얹은 시간이다.
- **왜 이 지표인가**: "X분 이내" 형태의 절대 상한은 X의 근거를 외부에서 빌려와야 하는데 객관적 원천이 없다. 오버헤드 비율은 분모가 자기 실측된 물리 하한이라 임의성이 없고, 토폴로지([`31`](31-제안-토폴로지.md))·확정 구조([`37`](37-합의-확정-구조.md)) 같은 설계 대안의 차이가 정확히 이 비율에 나타나므로 **PoC 대안 비교의 감도**가 좋다. 절대 시간은 참고치로 함께 보고한다.
- **목표 산정 논리**: 비율 2 = **프로토콜이 얹는 시간이 본질 작업(추론) 이하**여야 한다는 기준이다. 조정 비용이 본질 작업을 넘어서는 구조는 배보다 배꼽이 큰 것이다 (분석자 제안).
- **측정 범위**: 판정은 기준 시나리오(3인 — 과제 원문의 대표 사례)로 한다. 참여자 증가에 따른 추세 판정은 SC-참여자(b)의 소관이므로 여기서 중복하지 않되, **N = 7의 비율을 보조 보고**해 "3인에서만 빠른" 착시를 막는다.

**7. Recoverability — 복구 시간 비율 ≤ 1**
- **정의**: 강제 중단 후 복구에 걸린 시간 ÷ 정상 라운드 1회 시간(같은 하니스에서 실측). "복구가 얼마나 싼 사건인가"를 잰다.
- **왜 이 지표인가**: "복구 성공률 ≥ X%"는 (100 − X)%의 복구 실패를 감수한다는 뜻인데, 재개 실패나 재개 후 상태 불일치는 감수할 수 있는 성질의 것이 아니다 — 따라서 **복구의 성공과 상태 일치는 FR 합격 조건으로 이관**하고(§21.4), QA는 복구의 **비용**을 잰다.
- **목표 산정 논리**: 비율 1 = **복구가 한 라운드 지연보다 싸야 한다**는 내부 준거다. 협상 흐름에서 라운드 1회는 자연스러운 시간 단위이므로, 복구가 그 안에 끝나면 참여자들에게 중단은 "한 턴 늦은 것"과 구별되지 않는다. 분모가 자기 실측값이라 임의 상수가 없다.

**8. Resource Utilization — 협상 1회당 피크 추가 메모리, 앱 가용 예산의 ≤ 50%**
- **정의**: 기준 시나리오 협상 1회 동안의 피크 메모리에서 협상 시작 직전 메모리를 뺀 **증가분**(MB). 온디바이스 LLM이 이미 메모리를 상주 점유하는 단말에서 협상 계층이 추가로 얼마를 쓰는가를 잰다.
- **왜 메모리인가**: 배터리는 게이지 해상도(1%)와 기저 소모 잡음 때문에 측정 분산이 크고, 이 시스템의 실제 자원 병목은 LLM 상주로 압박되는 메모리다. 메모리는 프로파일러로 직접·재현 가능하게 측정된다. SC-의제(c)와의 역할 분리: c는 조합 확장에 따른 **증가 추세**, 본 지표는 기준 시나리오에서의 **절대 수준**이다 — 같은 관측값을 두 QA에 이중 계상하지 않는다.
- **목표 산정 논리**: 앵커는 **대상 단말에서 실측한 앱 가용 예산**(LLM 상주 후 앱이 안전하게 쓸 수 있는 메모리 한도)이다. 협상 계층이 그 절반을 넘으면 앱의 나머지 기능과 동시 실행 여유가 없어지므로 **예산의 50% 이하**를 기준으로 한다 (절반 배분은 분석자 제안). 예산 수치는 단말 실측 절차(§21.5-8)로 고정한다. 예산 초과로 인한 강제 종료(OOM) 금지는 FR 조건이다(§21.4).

**9. Confidentiality — 역추론 이득 ≤ +10%p**
- **정의**: 협상 메시지 기록만 입력받는 **고정된 공격자 모델**이 타 참여자의 선호 순위를 복원한 정확도에서, 무작위 추측의 기대 정확도(후보 k개의 1순위 맞히기면 1/k — 수학적으로 계산되는 기준선)를 뺀 값.
- **공격자 모델의 고정**: 자동 협상 분야에서 제안 이력로부터 상대 선호를 추정하는 **상대 모델링(opponent modeling)** 은 확립된 기법이며, 그중 **빈도 기반 모델(frequency model)** 이 단순·재현 가능하면서 성능이 좋아 표준으로 쓰인다 (Baarslag et al., *Learning about the opponent in automated bilateral negotiation*, 2016 서베이). NegMAS에 해당 구현(`UFunModel` · `FrequencyUFunModel` 컴포넌트)이 있어 그대로 쓴다. **공격자 = NegMAS의 frequency 계열 상대 모델(버전 명기)로 고정·봉인**한다 — 공격자가 바뀌면 대안 간·시점 간 비교가 무너지기 때문이다.
- **목표 산정 논리**: 협상이 성립하려면 정보가 일부 오가야 하므로 이득 0은 달성 불가능한 이상값이다. +10%p는 관찰을 누적해도 개인의 선호를 실용적으로 확신할 수 없는 수준이라는 판단 경계다 (분석자 제안 — 정보 공개 구조([`33`](33-정보-공개-구조.md)) 대안 확정 후 보정).

**10. Adaptability — 신규 시나리오 수용 공수, 평균 ≤ 8시간 (1인일)**
- **정의**: 설계 시 참조하지 않은 신규 협상 시나리오 표본(2종 이상)을 수용하는 데 든 **실작업 시간**(man-hour)의 평균. 시나리오 문서 수령부터 ENV-A에서 해당 시나리오의 협상이 정상 완결될 때까지, 대기 시간을 제외하고 집계한다.
- **공수 측정의 신뢰 확보**: 공수는 수행자 개인차에 흔들리는 값이므로 절차로 통제한다 — 수행자 2인이 독립 수행해 평균하고(개인차 완화), 시나리오 수행 순서를 수행자 간 교차하며(학습 효과 통제), 수행자는 협상 코어 개발자가 아닌 팀원으로 한다(코어 내부 지식으로 인한 왜곡 방지). 코드 변경량(diff)을 병행 기록해 "빨랐지만 코어를 고친" 경우를 검출한다 — 코어 무변경은 FR 조건이다(§21.4). 표본 2종의 공수 측정은 통계라기보다 실증이므로, 결과는 신뢰구간 없이 개별값과 평균을 그대로 보고한다.
- **목표 산정 논리**: 코드를 고치는 순간 구현·리뷰·테스트·배포의 릴리스 주기(통상 주 단위)에 묶인다. 1인일(8시간) 이내라는 목표는 "새 시나리오 지원이 릴리스가 아니라 구성 작업으로 끝난다"의 경계를 시간으로 옮긴 것이다 (분석자 제안).

## 21.4 FR 합격 조건으로 이관된 항목 (QA 지표에서 제외)

다음 조건들은 정도가 아니라 **되느냐/안 되느냐**의 문제이므로, QA 측정이 아니라 해당 FR의 합격 판정(acceptance)으로 검증한다. 어기면 "품질이 낮은 것"이 아니라 "기능이 틀린 것"이다.

| 이관 조건 | 검증 위치 (FR) |
|---|---|
| 위임 범위를 초과한 수락·실행 없음 | CFR-C2 위임 초과 차단 |
| 승인하지 않은 참여자에게 확정 효력 없음 | CFR-B9 완결 규칙 · CFR-D1 승인 수집 |
| 종결 시 확정 당사자 간 합의 레코드 동일 | CFR-F1 확정 전파·인계 (합의 종결 정합 L4) |
| 중단 후 재개 실패·재개 후 참여자 간 상태 불일치 없음 | CFR-I8 그룹 세션 저장·복구 |
| 결정 지점 기록 완전성 — 모든 제안·수락·판정에 입력, 효용값, threshold, 적용 규칙이 기록됨 | CFR-H2 추적·감사 로그 · CFR-H1 이력 조회 |
| 신규 시나리오 수용 시 협상 코어 코드 무변경 | CFR-I3 프로세스 템플릿 (코드 변경 없는 정의·교체) |
| 지정된 비공개 정보의 원문 노출 없음 | CFR-G3 차등 필터링 (QA-CF-1) |
| 협상 중 메모리 한도 초과(OOM)로 인한 강제 종료 없음 | CFR-I14 자원 상한 강제 |
| 협상 메시지의 위·변조 통과 없음 | CFR-G1 인증·암호화 채널 |

> 이 조건들은 각 실험(경계값 주입·적대적 케이스 포함)에서 함께 검사하되, 결과는 합격/불합격으로만 보고한다 — QA 점수에 섞지 않는다. 특히 **기록 완전성**은 Analysability 측정의 전제이자 모델 개선·강화 학습·skill화의 데이터 기반이므로, 스키마(기록 필드 목록)를 FR 검증 항목으로 명시 관리한다.

## 21.5 측정 절차 — 환경 · 테스트 · 방법

테스트 환경은 [`10`](10-핵심-QA-측정-계획.md) §10.2의 정의를 따른다 — **ENV-A** Mock 다자 시뮬레이션(스크립트된 참여자 + 기록·재생 하니스 + 장애 주입기), **ENV-B** 실기기(Galaxy 단말 + 프로파일러/adb + 온디바이스 LLM 실추론). 실사용자 평가는 수행하지 않으며, 수용성 판정은 페르소나 프로파일 기반 Mock 판정기가 맡는다.

모든 실험에 공통되는 통제 조건:
- **대안 비교 통제** — 측정의 1차 용도는 설계 대안([`31`](31-제안-토폴로지.md)-[`38`](38-협상-시나리오-가변성-구조.md)) PoC의 비교다. 대안별 PoC에 **동일한 하니스·시나리오·시드**를 적용하고 대안 구현만 교체한다. 하니스가 대안 내부에 의존하면 비교가 오염되므로, 하니스는 프로토콜 경계(메시지·로그)만 본다.
- **기준 시나리오 고정** — 별도 언급이 없으면 "3인 · 단일 의제(일정 조율) · 전원 승인 완결 규칙"을 기준 조건으로 쓴다. 변형 시나리오는 보조 실험으로만 돌린다.
- **재현성** — ENV-A의 난수(오류 주입 스케줄, Mock 응답)는 시드로 고정해 같은 실험을 그대로 재생할 수 있게 한다.
- **통계 보고** — 비율·지수형 지표는 점추정과 함께 **95% 신뢰구간을 병기**한다. 목표 경계에 걸리면 표본을 늘려 재판정한다.

---

**1. Functional Correctness — 정합 판정률 (ENV-A + Mock 판정기)**
- **테스트 설계**: 참여자별 **정답 프로파일**(의도·제약·선호의 전체 명세)을 사전 등록해 판정기에 봉인하고, 협상 에이전트에는 부분 정보(사용자 발화·위임 범위)만 준다. 시나리오 10종 × 참여자 3인 = 판정 표본 30건 이상.
- **절차**: ① 정답 프로파일 등록·봉인 ② ENV-A로 협상 실행 → 합의안 생성 ③ Mock 판정기가 합의안을 정답 프로파일과 대조 — 의도 부합 · 제약 충족 · 선호 수용선(효용 하한) 이상을 모두 만족하면 "수정 불요" ④ 수정 불요 판정 수 ÷ 전체 판정 수.
- **통제**: 판정기의 수용선·대조 규칙은 실험 설계서에 고정하고 대안 비교 전체에 동일 적용한다.
- **보조 관측**: 판정 실패 건의 사유를 4계층(의도/제약/선호/종결)으로 분류해 기록 — 원인 분석용이며 지표에는 넣지 않는다.

**2. Fault Tolerance — 내성 여유 배수 (ENV-A, 앵커는 ENV-B)**
- **테스트 설계**: 강도를 바꿔가며 주입하는 **스윕 실험**. 오류 카탈로그(메시지 유실 · 지연 · 1회 무응답 · 일시 이탈 후 복귀)의 유형 구성비는 고정하고 총량(강도)만 조절한다.
- **절차**: ① **앵커 실측**: ENV-B 실기기 통신에서 실환경 오류율(유실·재전송·타임아웃 비율)을 측정 ② ENV-A 무주입 베이스라인 100회 — 완결 분포(합의율·정상 결렬률·미종결률) 수집 ③ 강도를 실환경의 1×, 2×, 5×, 10×, 20×, 50×로 올리며 각 50회 실행 ④ **임계 강도** = 완결 분포가 베이스라인 대비 유의하게(95% 신뢰구간 분리) 저하되기 시작하는 최소 강도 ⑤ 내성 여유 배수 = 임계 강도 ÷ 실환경 오류율 → ≥ 10배 판정.
- **판정 주의**: 저하 판정은 완결률 단일값이 아니라 **합의/결렬 구성비**로 한다 — 오류 시 즉시 결렬하는 퇴화 전략은 결렬률 급증이 저하로 잡힌다.

**3. Analysability — 인과 재구성 성공률 (ENV-A)**
- **테스트 설계**: 표본 40건 = **정상 세션 20 + 결함 주입 세션 20** (결함은 라운드·참여자·처리 단계가 고르게 분포하도록 선정). 정답 — 정상 세션은 시뮬레이션 내부 기록(결정 요인·효용 값), 결함 세션은 주입 스케줄 — 을 봉인한다.
- **절차**: ① 표본 생성, 정답 봉인 (주입자·진단자 분리) ② 진단자에게 **협상 로그만** 제공 — 코드·시뮬레이션 내부 접근 금지 ③ 건당 30분 한도로 재구성 — 정상: 합의 결정 요인, 결함: 원인 3요소 ④ 정답 대조 → 성공 건수 ÷ 40 (95% 신뢰구간 병기).
- **통제**: 진단자는 로그 체계를 아는 팀원이되 표본 생성 내용을 모르는 사람으로 한다. 부분 정답은 실패로 세되 보조 기록한다.

**4. Scalability (참여자 수) — 확장 지수 b (ENV-A × ENV-B 합성)**
- **테스트 설계**: N ∈ {3, 5, 7}에서 각 **30회**. 합의 시간은 합성한다 — 시간 = (ENV-A의 라운드 수) × (ENV-B의 라운드 1회 실측 시간, N별 실측).
- **절차**: ① ENV-A에서 N별 라운드 수 분포 수집 ② ENV-B에서 라운드 1회의 wall-clock(추론 + 통신 왕복)을 N별로 실측 ③ N별 합성 시간 산출 ④ log(시간) vs log(N) 회귀로 b와 95% 신뢰구간 추정 ⑤ 판정: **신뢰구간 하한 > 1이면 위반**. 결정계수 R²를 함께 보고한다(낮으면 멱 모형 부적합 신호).
- **보조 관측**: 메시지 총수·피크 메모리의 b도 같은 방법으로 산출해 기록 — 판정은 합의 시간의 b로만 한다.

**5. Scalability (의제 조합) — 조합-메모리 탄력성 c (ENV-B)**
- **테스트 설계**: 의제 구성을 바꿔 전체 조합 수 S를 **10²-10⁵ 범위에서 로그 등간격 6단계 이상**으로 확장(예: 날짜×영화관×영화×시간의 후보 수 조절). 단계 수가 적으면 신뢰구간이 넓어져 판정력이 없다.
- **절차**: ① 단계별 의제 구성 정의(조합 수를 정확히 계산해 기록) ② 실기기에서 협상 실행 중 피크 메모리를 프로파일러로 측정(단계당 5회, 중앙값 사용) ③ log(메모리) vs log(S) 회귀로 c와 95% 신뢰구간 추정 ④ 판정: **신뢰구간 상한 < 1** (전체 열거 기각). 점추정과 설계 이상값 1/d(기준 시나리오 d = 4 → 0.25)의 거리를 함께 보고한다.
- **통제**: 측정 전 앱 재시작으로 메모리 상태를 초기화하고, 협상 외 기능은 꺼서 잡음을 줄인다.

**6. Time Behaviour — 프로토콜 오버헤드 비율 (ENV-B)**
- **테스트 설계**: 실기기 3대의 end-to-end 협상에서 분자·분모를 **같은 세션 로그에서 동시에** 수집한다 — 총 소요 시간(세션 수립-합의안 제시)과 그 세션의 LLM 추론 호출 시간 합.
- **절차**: ① 기준 시나리오로 실기기 3대 협상 5회 ② 세션별 비율 = 총 시간 ÷ 추론 시간 합 ③ 중앙값 → ≤ 2 판정 ④ **보조 보고**: N = 7 구성의 비율을 ENV-A×B 합성으로 산출해 병기(판정에는 쓰지 않음 — 추세 판정은 SC-참여자의 소관), 절대 시간(분)도 참고치로 보고.
- **판정 주의**: 분모는 "실제 발생한" 추론 시간이다 — 대안이 추론 호출 자체를 늘리면(예: 재협상 유발) 분모가 커져 비율이 좋아 보일 수 있으므로, 추론 호출 횟수를 함께 보고해 비정상 증가를 검출한다.

**7. Recoverability — 복구 시간 비율 (ENV-A)**
- **테스트 설계**: 중단 유형 {프로세스 강제 종료, 네트워크 완전 단절} × 중단 시점 {라운드 진행 중, 승인 수집 중, 확정 절차 중} 의 그리드 6칸 × 각 10회 = 60회. "확정 절차 중"의 중단 시점 정의는 확정 구조([`37`](37-합의-확정-구조.md)) 대안별로 다르므로 하니스에 대안별 어댑터를 둔다.
- **절차**: ① 장애 주입기로 지정 시점에 강제 중단 ② 복구 절차 기동 ③ **FR 판정 먼저** — 중단 지점 재개 여부와 전 참여자 상태 일치를 로그 대조로 확인, 실패는 결함으로 보고하고 지표 집계에서 제외(§21.4) ④ 성공 건의 복구 소요 시간 ÷ 같은 하니스에서 실측한 정상 라운드 1회 시간 → 비율의 중앙값 ≤ 1 판정.
- **판정 주의**: "처음부터 다시 시작"으로 살아난 케이스는 FR 실패다 — 재개(resume)를 재는 것이지 재시작(restart)이 아니다.

**8. Resource Utilization — 피크 추가 메모리 (ENV-B)**
- **테스트 설계**: 먼저 **앱 가용 예산을 실측으로 고정**한다 — 대상 단말에서 온디바이스 LLM 상주 후 앱이 안전하게 쓸 수 있는 메모리 한도(OS의 앱 메모리 한도에서 LLM 상주분과 앱 기본 점유를 뺀 값)를 측정해 실험 설계서에 기록한다. 이후 모든 판정은 이 수치 대비 비율로 한다.
- **절차**: ① 앱 재시작·기준 상태(협상 외 기능 차단) ② 협상 시작 직전 메모리 기록 ③ 기준 시나리오 협상 1회 실행, 피크 메모리 측정 ④ 증가분 = 피크 − 시작 직전, 5회 반복 중앙값 ⑤ 증가분 ÷ 앱 가용 예산 ≤ 50% 판정.
- **보조 관측**: CPU 점유·배터리 소모를 함께 기록하되 판정에는 쓰지 않는다. OOM 강제 종료 발생은 FR 위반으로 별도 보고한다(§21.4).

**9. Confidentiality — 역추론 이득 (ENV-A)**
- **테스트 설계**: 공격자 관점은 **참여자 관찰자**(정상 참여자가 자기에게 도착한 메시지만으로 타인의 선호를 추정)로 고정한다 — 외부 도청자는 암호화 채널 FR의 문제라 여기서 재지 않는다. **공격자 구현은 NegMAS의 frequency 계열 상대 모델(`FrequencyUFunModel`, 버전 명기)로 고정·봉인**한다.
- **절차**: ① 선호 프로파일을 무작위 생성한 협상 100회 실행, 참여자 시점의 메시지 기록 수집 ② 공격자 모델로 타 참여자의 1순위 후보 추정 ③ 추정 정확도 측정 ④ 무작위 기준선(후보 k개면 1/k) 차감 → 이득(%p), 95% 신뢰구간 병기.
- **판정 주의**: 이득은 정보 공개 구조([`33`](33-정보-공개-구조.md))의 대안별로 달라지는 값이다 — 대안 비교와 최종 판정에 **같은 공격자 모델**을 써야 비교가 성립한다.

**10. Adaptability — 신규 시나리오 수용 공수 (개발 환경 + ENV-A)**
- **테스트 설계**: 설계 시 참조하지 않은 **신규 시나리오 2종 이상**을 봉인해 둔다(예: 회식 메뉴·장소 동시 협상, 모임 역할 분담 — 의제 구조·완결 규칙이 기준 시나리오와 다른 것으로 선정). **수행자 2인**은 협상 코어 개발자가 아닌 팀원으로 하고, 시나리오 수행 순서를 수행자 간 교차한다.
- **절차**: ① 수행자가 시나리오 문서를 받고 작업 시작(작업 로그 개시) ② 시나리오 정의 작성 → 배포 → **ENV-A에서 해당 시나리오의 협상이 정상 완결**되면 종료 ③ 실작업 시간 집계(대기·중단 제외 — 작업 전환을 타이머 로그로 기록) ④ 수행자 2인 × 시나리오 2종의 개별값과 평균 보고 → 평균 ≤ 8시간 판정.
- **보조 관측**: 코드 변경량(diff LoC)을 함께 기록 — 시나리오 층 변경은 규모를 보고하고, **코어 변경이 발생했다면 공수와 무관하게 FR 위반(§21.4)으로 보고**한다.
