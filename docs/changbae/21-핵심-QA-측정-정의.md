# 21. 핵심 QA 측정 정의 — QA당 핵심 지표 1개

> 배경: [`20`](20-핵심-QA-확정.md)에서 확정한 핵심 QA 10개의 측정을 정제한다 (PL 지시, 2026-08-06).
> 본 문서가 **핵심 QA 측정의 정본**이다 — [`10`](10-핵심-QA-측정-계획.md)의 측정표 중 목표 수준 정의는 본 문서로 대체되며, 10의 테스트 환경(ENV-A/B/C)과 실험 방법은 그대로 참조한다.

---

## 21.1 측정 원칙

1. **QA당 핵심 지표는 1개다.** 여러 지표를 병렬로 재면 "이 QA를 달성했는가"의 판정이 흐려진다 — 대표성 있는 지표 하나로 판정하고, 나머지 관측값은 원인 분석용 보조 데이터로만 쓴다.
2. **QA 지표는 연속적인 정도(degree)여야 한다.** 높을수록 좋거나 낮을수록 좋은 스칼라 값이어야 하고, 목표는 "어떤 수준 이상/이하"로 정의된다.
3. **"위반 0건", "불일치 0건", "일치 100%" 같은 on/off 조건은 QA 지표가 아니다.** 그것은 기능이 맞게 동작하는가의 문제, 즉 **FR의 합격 조건**이다. 이런 조건들은 §21.4로 이관해 FR 검증(합격/불합격 판정)으로 다룬다 — QA 평가에는 넣지 않는다.
4. **목표값에는 산정 근거가 있어야 한다.** 각 목표는 과제 원문·수학적 기준선·사용자 체감 논리 중 하나로부터 도출하며, 산정 논리를 명시한다. 외부 통계를 가장한 근거는 쓰지 않는다 — 도출 논리가 분석자 판단인 경우 그렇게 표시하고, 파일럿 실측 후 보정 조건을 함께 적는다.

## 21.2 핵심 지표 요약표

| QA | 핵심 지표 | 방향 | 목표 수준 | 측정 환경 |
|---|---|---|---|---|
| Functional Correctness | 무수정 승인율 | 높을수록 좋음 | **≥ 70%** | ENV-C |
| Fault Tolerance | 오류 주입 시 무중단 완결률 | 높을수록 좋음 | **≥ 95%** | ENV-A |
| Analysability | 결함 원인 특정 성공률 (건당 30분 한도) | 높을수록 좋음 | **≥ 95%** | ENV-A |
| Scalability (참여자 수) | 참여자 확장 지수 b (합의 시간 ∝ N^b) | 낮을수록 좋음 | **≤ 1.2** | ENV-A×B |
| Scalability (의제 조합) | 조합-메모리 탄력성 c (피크 메모리 ∝ 조합 수^c) | 낮을수록 좋음 | **≤ 0.5** | ENV-B |
| Time Behaviour | 합의 도달 시간 중앙값 (3인·단일 의제 기준) | 낮을수록 좋음 | **≤ 5분** | ENV-A×B |
| Recoverability | 복구 성공률 | 높을수록 좋음 | **≥ 95%** | ENV-A |
| Resource Utilization | 협상 1회당 배터리 소모율 | 낮을수록 좋음 | **≤ 1%** | ENV-B |
| Confidentiality | 역추론 이득 (공격자 정확도 − 무작위 기준선) | 낮을수록 좋음 | **≤ +10%p** | ENV-A |
| Adaptability | 신규 시나리오 수용 리드타임 (평균) | 낮을수록 좋음 | **≤ 8시간 (1인일)** | 개발 환경 |

## 21.3 지표별 정의와 목표 산정 근거

**1. Functional Correctness — 무수정 승인율 ≥ 70%**
- **정의**: 시스템이 제시한 합의안을 참여자가 **수정 요구 없이 그대로 승인**한 비율. 산식 = 무수정 승인 건수 ÷ 전체 합의안 제시 건수 (참여자-협상 단위로 집계).
- **왜 이 지표인가**: 정확성의 최종 판정자는 참여자 본인이다. 의도·제약·선호가 맞았다면 사용자는 고치지 않고 승인한다 — 승인 행동 하나에 세 요소가 종합되어 나타나므로 대표 지표로 삼는다. (계층별 세부 관측값 — 의도 분류 정확도, 선호 프로파일 대비 일치율 — 은 원인 분석용 보조 데이터다.)
- **목표 산정 논리**: 이 시스템의 가치는 "맡기면 알아서 되는 것"이다. 제시안 3건 중 1건 넘게 손봐야 한다면 사용자는 "결국 내가 직접 고르는 게 낫다"고 판단하게 되어 위임 가치가 무너진다 — 수정 요구가 1/3을 넘지 않는 수준, 즉 70%를 기준으로 한다 (분석자 제안). 파일럿 실측에서 베이스라인이 이보다 크게 다르면 보정한다.

**2. Fault Tolerance — 오류 주입 시 무중단 완결률 ≥ 95%**
- **정의**: 일시 오류(메시지 유실·지연·응답 없음·일시 이탈)를 주입한 협상 세션 중, 사용자 개입 없이 정상 완결(합의 또는 정상 결렬)에 도달한 비율.
- **목표 산정 논리**: 사용자가 일상적으로 쓸 때(예: 주 5회, 월 20회) 협상이 중단되는 경험이 **월 1회 미만**이면 "가끔 이상한 도구"가 아니라 "믿을 만한 도구"로 인식된다는 체감 기준에서 95%(20회 중 1회 미만)로 설정한다 (분석자 제안). 오류 주입 강도(주입 빈도·유형 분포)는 실험 설계에서 고정해 비교 가능성을 확보한다.

**3. Analysability — 결함 원인 특정 성공률 ≥ 95% (건당 30분 한도)**
- **정의**: 원인을 알고 주입한 결함 표본에 대해, 담당자가 **로그만으로** 원인 3요소(어느 라운드 · 어느 참여자 · 어느 처리 단계)를 30분 안에 정확히 특정한 비율.
- **왜 시간 한도를 거는가**: 한도 없이 "언젠가 찾으면 성공"으로 재면 지표가 변별력을 잃는다. 30분은 한 번의 집중 작업 단위 안에 진단이 끝나야 로그 기반 분석이 실무에서 쓰인다는 기준이다 (분석자 제안).
- **목표 산정 논리**: 표본 20건 중 19건(95%) — 특정 실패가 5%를 넘으면 로그 체계에 구조적 사각(기록 안 되는 경로)이 있다는 신호로 본다.

**4. Scalability (참여자 수) — 확장 지수 b ≤ 1.2**
- **정의**: 참여자 수 N ∈ {3, 5, 7}에서 측정한 합의 도달 시간을 시간 ∝ N^b 로 회귀했을 때의 지수 b. (메시지 수·메모리도 같은 방법으로 관측하되, 판정은 사용자 체감에 직결되는 합의 시간의 b로 한다.)
- **목표 산정 논리**: 수학적 기준선이 명확하다 — **b = 1이 선형**(참여자 2배 = 시간 2배)이고, [`20`](20-핵심-QA-확정.md)의 요구가 "선형 이내"다. 측정 잡음과 고정 비용(세션 수립 등)의 영향을 감안한 판정 여유 20%를 더해 b ≤ 1.2로 한다. 참고로 전원-전원 통신의 이론값은 b ≈ 2(제곱)로, 1.2는 그 중간이 아니라 선형 계열임을 판정하는 경계값이다.

**5. Scalability (의제 조합) — 조합-메모리 탄력성 c ≤ 0.5**
- **정의**: 전체 조합 수 S(= 의제별 후보 수의 곱, K×L×M×P)를 늘려가며 측정한 피크 메모리를 메모리 ∝ S^c 로 회귀했을 때의 지수 c.
- **목표 산정 논리**: 수학적 기준선이 명확하다 — **전체 열거(모든 조합 생성·보관)의 c = 1**이다. c = 0.5는 조합이 4배로 늘 때 메모리는 2배 이하만 는다는 뜻으로, "전체를 만들지 않는 구조"임을 정량적으로 판정하는 경계다: 가지치기·지연 생성이 실제로 동작하면 생성되는 후보가 조합 수의 일부(대략 제곱근 규모 이하)에 머무른다는 설계 의도의 수치화다 (분석자 제안).

**6. Time Behaviour — 합의 도달 시간 중앙값 ≤ 5분 (3인·단일 의제 기준)**
- **정의**: 협상 시작(세션 수립)부터 합의안 제시까지의 시간. 라운드 수 분포는 ENV-A 시뮬레이션으로, 라운드 1회의 실제 시간(온디바이스 추론+통신)은 ENV-B 실측으로 얻어 합성한다. 기준 시나리오를 3인·단일 의제(일정 조율)로 고정해 비교 가능성을 확보한다.
- **목표 산정 논리**: 과제 원문(01 §1.2.1)이 밝힌 현재 상태는 "일정 조율 한 건에 메시지·캘린더·예약 사이를 5~10번 왕복"이다. 사람의 왕복 1회는 상대의 확인·응답 대기를 포함해 보수적으로 잡아도 수 분이므로, 사람 직접 조율은 최소 수십 분(대개 그 이상)이다. 시스템이 그 **1/10 이하 수준인 5분** 안에 합의안을 내놓으면 체감 우위가 논쟁의 여지없이 성립한다는 논리다.

**7. Recoverability — 복구 성공률 ≥ 95%**
- **정의**: 세션 강제 중단(프로세스 kill·네트워크 완전 단절) 후 복구를 시도한 케이스 중, **중단 지점에서 재개되고 전 참여자의 상태가 일치**하는 데까지 성공한 비율. (재개했지만 상태가 어긋난 경우는 실패로 센다 — 성공의 정의에 포함시켜 지표를 하나로 유지한다.)
- **목표 산정 논리**: 중단 자체가 드문 사건이므로 사용자가 "중단 + 복구 실패"를 함께 겪을 확률은 두 확률의 곱이다. 복구가 95%면 그 복합 확률이 무시할 수준이 되어, 사용자 입장에서 "끊겨도 되살아나는 도구"라는 신뢰가 성립한다 (Fault Tolerance와 같은 20회 중 1회 미만 체감 기준, 분석자 제안).

**8. Resource Utilization — 협상 1회당 배터리 소모율 ≤ 1%**
- **정의**: 협상 1회(시작~합의안 제시)가 소비하는 단말 배터리의 백분율. 실기기 프로파일러로 측정한다. (메모리·CPU는 관측하되, 사용자가 직접 체감하고 기능을 꺼버리는 판단 기준은 배터리이므로 대표 지표로 삼는다.)
- **목표 산정 논리**: 하루 3회 협상을 가정하면 일 3% — 배터리 사용 내역 화면에서 사용자의 눈에 띄어 "이 기능 끄자"는 판단을 유발하지 않는 수준이어야 한다. 개별 기능의 일 소모가 한 자릿수 초반%를 넘으면 사용자 인지가 시작된다는 판단에서 회당 1%를 기준으로 한다 (분석자 제안 — 단말 기종별 실측으로 보정).

**9. Confidentiality — 역추론 이득 ≤ +10%p**
- **정의**: 협상 메시지 기록만 입력받는 공격자 모델이 타 참여자의 선호 순위를 복원한 정확도에서, **무작위 추측의 기대 정확도(수학적으로 계산되는 기준선)** 를 뺀 값. 예: 후보 5개의 1순위 맞히기 무작위 기준선은 20% — 공격자가 28%를 맞히면 이득은 +8%p.
- **왜 "이득"으로 재는가**: 절대 정확도는 후보 수에 따라 달라져 비교가 안 된다. 무작위 기준선과의 차이는 후보 수와 무관하게 "메시지 관찰이 실제로 얼마나 정보를 흘렸는가"만을 잰다 — 기준선이 수학적으로 정의되므로 객관적이다.
- **목표 산정 논리**: 협상이 성립하려면 정보가 일부 오가야 하므로 이득 0은 달성 불가능한 이상값이다. +10%p는 관찰자가 여러 번 관찰을 누적해도 개인의 선호를 실용적으로 확신할 수 없는 수준이라는 판단 경계다 (분석자 제안 — 공격자 모델 확정 후 보정).

**10. Adaptability — 신규 시나리오 수용 리드타임 평균 ≤ 8시간 (1인일)**
- **정의**: 설계 시 참조하지 않은 신규 협상 시나리오 표본(2종 이상)에 대해, 시나리오 정의 착수부터 실행 성공까지 걸린 작업 시간의 평균. 코드 변경량(diff)은 보조 관측값으로 기록한다.
- **왜 시간으로 재는가**: "코드 변경 0"은 on/off 조건이라 QA 지표가 될 수 없다(§21.1-3). 코드 변경 없는 수용이 실질적으로 주는 가치는 **릴리스 주기에 묶이지 않는 빠른 수용**이므로, 그 가치를 직접 재는 연속 지표인 리드타임으로 정의한다.
- **목표 산정 논리**: 코드를 고치는 순간 구현·리뷰·테스트·배포의 릴리스 주기(통상 주 단위)에 묶인다. 1인일(8시간) 이내라는 목표는 "새 시나리오 지원이 릴리스가 아니라 구성 작업으로 끝난다"의 경계를 시간으로 옮긴 것이다 (분석자 제안).

## 21.4 FR 합격 조건으로 이관된 항목 (QA 지표에서 제외)

다음 조건들은 정도가 아니라 **되느냐/안 되느냐**의 문제이므로, QA 측정이 아니라 해당 FR의 합격 판정(acceptance)으로 검증한다. 어기면 "품질이 낮은 것"이 아니라 "기능이 틀린 것"이다.

| 이관 조건 | 검증 위치 (FR) |
|---|---|
| 위임 범위를 초과한 수락·실행 없음 | CFR-C2 위임 초과 차단 |
| 승인하지 않은 참여자에게 확정 효력 없음 | CFR-B9 완결 규칙 · CFR-D1 승인 수집 |
| 종결 시 확정 당사자 간 합의 레코드 동일 | CFR-F1 확정 전파·인계 (합의 종결 정합 L4) |
| 지정된 비공개 정보의 원문 노출 없음 | CFR-G3 차등 필터링 (QA-CF-1) |
| 협상 중 메모리 한도 초과(OOM)로 인한 강제 종료 없음 | CFR-I14 자원 상한 강제 |
| 협상 메시지의 위·변조 통과 없음 | CFR-G1 인증·암호화 채널 |

> 이 조건들은 [`10`](10-핵심-QA-측정-계획.md)의 실험(경계값 주입·적대적 케이스)에서 함께 검사하되, 결과는 합격/불합격으로만 보고한다 — QA 점수에 섞지 않는다.
