# DP02 설계대안 슬라이드 — 표 붙여넣기 문구

> `3-설계대안검토.png` 템플릿 형식에 맞춘 붙여넣기용 문구.
> 장·단점 = 한 문장 + (품질속성↑/↓), Trade Off = "영문 (측정 지표) ★별점 (판단 기준; 수치 미정은 ?)".
> 판단 기준(괄호)은 두 열이 동일하며 별점만 다르다.
> 근거: `DP02-A2A-협상-메시지-구조.md` §2·§3·§4. 평가축 = 확정 5축.

## 헤더 (설계안 행)

- 후보 A · 순수 NegMAS 메시지
- 후보 B · 제약 힌트 확장 Envelope

## 후보 A — 장점

· 외부로 나가는 것이 승인된 OutcomeSpace 값(offer)뿐이라 선호·양보 정보가 직접 노출되지 않는다 (Security↑)
· 메시지와 검증 상태가 작아 추가 런타임 메모리·연산 부담이 적다 (Resource Efficiency↑)
· NegMAS 표준에 가까워 힌트 스키마·버전·fallback 관리가 없어 구현·유지보수가 단순하다 (Maintainability↑)

## 후보 A — 단점

· 상대가 제약을 offer 패턴으로만 추정하므로 시행착오 라운드가 늘어 응답 지연이 커질 수 있다 (Latency↓)
· 다속성 협상에서 유효 합의 후보 탐색이 느려 과업 성공률이 떨어질 수 있다 (Task Success Rate↓)

## 후보 B — 장점

· 상대가 고정/양보 축을 빨리 파악해 협상 라운드 수가 줄어 응답 지연이 감소한다 (Latency↑)
· 다속성 협상에서 합의 후보 탐색이 빨라져 과업 성공률이 오른다 (Task Success Rate↑)

## 후보 B — 단점

· 사유·PII·원문은 아니지만 고정/양보 축이라는 선호 정보가 추가로 노출된다 (Security↓)
· 힌트 블록·로그와 후보 정렬 계산이 추가되어 런타임 메모리·연산 부담이 커진다 (Resource Efficiency↓)
· 힌트 스키마 버전·fallback 정책·감사 항목을 계속 관리해야 해 구현·유지보수 부담이 커진다 (Maintainability↓)

## Trade Off — 후보 A

```
Security (정보 보호)                         ★★★        (외부 노출 선호 정보 항목 수; PII 외부전송 0건)
Latency (응답 지연시간)                      ★★         (합의까지 평균 라운드 수 · 추가 지연 ≤ ? ms)
Resource Efficiency (평균 런타임 메모리 사용량)  ★★☆        (추가 메모리 사용량 ≤ ? MB)
Task Success Rate (과업 성공률)              ★★         (다속성 협상 합의 성공률 ≥ ? %)
Maintainability (구현 복잡성·유지보수성)        ★★★        (추가/수정 대상 모듈·스키마 수)
```

## Trade Off — 후보 B

```
Security (정보 보호)                         ★★☆ (+☆)   (외부 노출 선호 정보 항목 수; PII 외부전송 0건)
Latency (응답 지연시간)                      ★★★        (합의까지 평균 라운드 수 · 추가 지연 ≤ ? ms)
Resource Efficiency (평균 런타임 메모리 사용량)  ★★         (추가 메모리 사용량 ≤ ? MB)
Task Success Rate (과업 성공률)              ★★★        (다속성 협상 합의 성공률 ≥ ? %)
Maintainability (구현 복잡성·유지보수성)        ★★         (추가/수정 대상 모듈·스키마 수)
```
