# DP02 A2A 메시지 구조 예시 (1안 / 2안)

> 발표용 예시. 근거: PoC `poc/dp02-a2a-message-hints` 실제 구현과 샘플 시나리오 `S001`.
> 실제 런타임 위치 — 힌트는 NegMAS `ExtendedOutcome.data["constraint_hint"]`(또는 `ExtendedResponseType.data`)에 담긴다(`01-시나리오-스키마.md`).
> 1안 = 순수 NegMAS 메시지, 2안 = 제약 힌트 확장 Envelope.

---

## 공통 전제 — OutcomeSpace (협상 시작 시 고정·공유)

offer는 값만 실린 **위치 기반 튜플**이며, 각 위치의 뜻은 시작 시 고정·공유된 이슈 순서에서 온다(스키마는 매 라운드 재전송하지 않음).

```
issues (고정·공유)  = [slot, area, budget_band, notice_period]
offer (전송 값)     = ("saturday_lunch", "near_home", "low", "three_days")
                        │                │            │       └ notice_period = three_days
                        │                │            └ budget_band = low
                        │                └ area = near_home
                        └ slot = saturday_lunch
```

값 라벨(`saturday_lunch` 등)도 OutcomeSpace의 허용 값 집합에서 온다. 받는 쪽은 튜플을 자기 OutcomeSpace로 검증한다. `{"slot": ...}` dict 표현은 사람이 읽기 위한 변환일 뿐, SAO의 카논 형태는 튜플이다.

---

## 1안 — 순수 NegMAS 메시지 (offer만, data 없음)

```python
# propose() 반환 = OutcomeTuple 하나 (ExtendedOutcome 아님)
("saturday_lunch", "near_home", "low", "three_days")

# dict view: {"slot":"saturday_lunch","area":"near_home",
#             "budget_band":"low","notice_period":"three_days"}
# 수신측이 보는 것: state.current_offer   (state.current_data 는 None)
```

선호 강도·유보값·양보 가능성은 모두 단말 내부 효용함수(ufun)에만 남고 전송되지 않는다.

---

## 2안 — 제약 힌트 확장 (ExtendedOutcome = offer + data)

### 예시 A — 고정 축 + 양보 축 공개

```python
ExtendedOutcome(
    outcome=("saturday_lunch", "near_home", "low", "three_days"),   # NegMAS 본문(offer)
    data={
        "constraint_hint": {                       # 신규 sibling 필드
            "schema_version": "constraint_hint.v1",
            "anchor": "offered_outcome",
            "issue_constraints": {"slot": "fixed", "notice_period": "relaxable"},
        }
    },
)
# 수신측: state.current_offer  +  state.current_data["constraint_hint"]
```

### 예시 B — 다른 라운드/에이전트 (양보 축만 공개)

```python
ExtendedOutcome(
    outcome=("sunday_evening", "midpoint", "medium", "one_day"),
    data={"constraint_hint": {
        "schema_version": "constraint_hint.v1",
        "anchor": "offered_outcome",
        "issue_constraints": {"budget_band": "relaxable", "notice_period": "relaxable"},
    }},
)
```

### 예시 C — 2안이지만 미지원 상대 → fallback (구조가 1안과 동일)

```python
# 상대 capability.constraint_hint = False 이면 힌트를 붙이지 않고 순수 offer로 전송
("saturday_lunch", "near_home", "low", "three_days")   # data 없음 = 1안과 같음
# fallback 중 힌트가 한 번이라도 전송되면 심각한 실패로 본다.
```

---

## 읽는 규칙

- `issue_constraints` 값은 `fixed`(고정) / `relaxable`(양보 가능) 둘뿐.
- 목록에 **없는 이슈는 "비공개"** 로 해석한다 (누락 ≠ relaxable).
- `anchor: offered_outcome` — flag들은 함께 실린 offer의 축을 가리킨다.
- 수신측은 힌트를 **후보 offer 정렬에만** 반영하고, 수락/거절 최소 조건은 자기 효용함수로 유지한다.

---

## 구조 요약

| | 전송 데이터 구조 | 힌트 |
|---|---|---|
| **1안** | `OutcomeTuple` | 없음 |
| **2안** | `ExtendedOutcome(outcome, data={"constraint_hint": ...})` | `ConstraintHintMessage` (schema `constraint_hint.v1`) |

구조 차이는 딱 한 겹 — 2안은 1안의 `outcome`(NegMAS 본문)을 그대로 두고 `data`에 힌트를 얹는다. "상위 봉투"는 커스텀 클래스가 아니라 NegMAS 내장 `ExtendedOutcome`이다.
