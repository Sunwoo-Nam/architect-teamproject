## 1. 배경 슬라이드

### 1.1 목적
- 협상을 하려면 내 정보의 일부 노출이 불가피함을, 그리고 그 정보가 나가는 **경로가 여러 개**임을 보인다.
- 협상 엔진으로 **NegMAS**를 쓰며, 이때 다루는 **기본 데이터 구조(OutcomeSpace, Ufun)** 가 무엇인지 간단한 예시로 개념을 잡고 넘어간다.
- 결론적으로 이 장의 메시지: **개인정보를 지키면서도 협상은 원활히 진행 가능한 구조가 필요하다(Challenge).**

### 1.2 넣을 내용

**좌측 — "협상을 위해서는 내 정보의 노출이 불가피하다" (현재 초안에 이미 작성됨)**
- 기기 내 정보 원본(예: "토요일 14:00~15:00, 강남 ○○ 의원 진료 예약") → 협상에 필요한 정보(예: 일정="토요일 저녁 가능", 위치="강남 인근 선호")로 축소.
- PII 수준 정보는 제외하고 협상에 필요한 정보만 노출. (PII = Personally Identifiable Information)
- 노출 경로 3가지: ① Cloud LLM ② 상대 Agent ③ 외부 서비스 API. (Orchestration 동작에는 Cloud LLM 사용)
- → 정보가 나가는 모든 경로를 빠짐없이 통제하고, 나가는 정보를 최소한으로 한정해야 한다.

**우측 — "협상은 NegMAS로 — 구조화된 데이터 기반으로 offer를 주고받는다" (현재 초안이 비어 있음: `///`)**
- 고정된 구조화 데이터 **OutcomeSpace**를 사용하며, 이는 협상 시작 시 고정됨.
- 사용자 선호 계산의 근거가 되는 **ufun(효용함수)** 는 단말 외부로 전송되지 않음.
- **개념 그림 2개 추가**(사용자 요청): 간단한 예시로 OutcomeSpace와 Ufun이 각각 무엇인지 보여준다.

### 1.3 근거 자료
- 첨부 슬라이드 1장([1-배경.png](./슬라이드구성/1-배경.png)) — 좌측 내용/예시.

## 2. 기본 아키텍처 슬라이드

### 2.1 목적
- 현재 다이어그램의 **설계 결정 사항**을 설명한다.
- 특히 **PII 금고(Vault)** 가 NegMAS 표준 요소가 아니라 **개인정보 보호를 위해 별도로 추가된 컴포넌트**임을 밝히고, 왜 넣었는지 설명한다.
- 상단 설명 문구가 현재 비어 있음(`////`) → 텍스트 추가 필요.

### 2.2 넣을 내용 (다이어그램 구성 요소)
[DP02-전체구조.drawio](./DP02-전체구조.drawio) 기준:

- **온디바이스 신뢰경계** — 아래 처리 대부분이 단말 내부에서 일어남.
- **단일 프라이버시 게이트웨이** (외부로 나가는 정보의 단일 통제 지점)
  - Schema Registry(승인 issue/value)
  - 정규화기(분류/권한/어휘)
  - 출력 빌더(OutcomeSpace/요청)
  - **PII 금고(Vault)**
- **Meta Agent(협상 두뇌)** — ufun(선호/유보값) → 협상 엔진(NegMAS).
- **Orchestrator(계획 작성)** ↔ Cloud LLM(외부): 구조화 계획 요청.
- **Sub-Agent(실행/조회)** ↔ 외부 서비스 API.
- **상대 PPA(외부)** ↔ 협상 엔진: 오퍼(OutcomeSpace 유효 값).
- 입력원: 사용자 행동 → IDS(Intent 감지), DPA(가전) → 정규화기.

### 2.3 설계 결정 설명 포인트 (텍스트로 추가할 논지)
1. **단일 프라이버시 게이트웨이** — 외부로 나가는 모든 출력을 한 지점에서 정규화·검증한다. (배경 좌측의 "모든 경로를 빠짐없이 통제" 요구에 대응)
2. **PII 금고(Vault) 도입 이유** — NegMAS는 OutcomeSpace·ufun·offer만 다루므로 원본 PII를 담을 자리가 없다. 원본 PII(예: "강남 ○○ 의원")는 협상에 불필요하고 외부로 나가서도 안 된다. 정규화 단계에서 분리된 PII를 **단말 내부 Vault에 격리 저장**하고, 실제 실행(Sub-Agent의 예약·조회 등) 시점에만 참조한다. → Vault는 협상용이 아니라 **실행용 원본 보관 + 협상 경로 격리**를 위한 추가 요소.
3. **ufun의 단말 내부화** — 선호/유보값은 Meta Agent 내부에만 있고, 외부(상대 PPA)로는 OutcomeSpace 유효 값(=offer)만 나간다.
4. **외부 경로별 통제** — Cloud LLM(계획), 외부 서비스 API(실행), 상대 PPA(협상) 각각에 대해 나가는 데이터 형태가 정해져 있다.

### 2.4 근거 자료
- 첨부 슬라이드 2장([2-기본아키텍처.png](./슬라이드구성/2-기본아키텍처.png)).
- [DP02-전체구조.drawio](./DP02-전체구조.drawio) — 컴포넌트/엣지 구성.
- Vault↔Sub-Agent 점선 엣지(drawio의 `e_vault_sub`) = 실행 시점 PII 참조 경로의 근거.

## 3. 설계대안 슬라이드 (후보 A / 후보 B)

### 3.1 목적
- 기본 아키텍처를 고정한 상태에서, **상대 PPA로 나가는 A2A 메시지 구조**를 어떻게 설계할지 두 후보를 비교한다.
  - **후보 A** — 순수 NegMAS 메시지(offer + accept/reject)로 제한.
  - **후보 B** — 확장 Envelope에 **구조화된 제약 힌트**(축별 고정/양보 가능)를 덧붙임.
- 핵심 긴장: **"선호를 숨겨 외부 전송 정보를 최소화(A) vs 제한된 제약 힌트를 공개해 협상 수렴을 빠르게(B)".**
- **결론(확정, 2026-07-06)**: 당사 동일 구현 Agent 전용 전제에서 후보 B 근소 우세(md §4).
