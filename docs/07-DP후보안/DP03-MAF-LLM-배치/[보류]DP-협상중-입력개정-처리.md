# [보류] DP — 협상 진행 중 입력 개정(사용자 변경) 시 N-party 세션 상태 갱신

> **문서 성격**: Design Decision 후보 (보류 — 논의 스냅샷)
> **상태**: 2026-07-03 논의에서 도출되었으나 본격 전개는 보류. 원 논의(서브 에이전트 lifecycle / 메모리)에서 파생된 별개 주제로 판명되어, 원 주제로 복귀하며 본 문서에 스냅샷만 남김.
> **파생 경위**: "서브 에이전트로부터 데이터를 다시 가져와야 하는 상황"의 지배적 트리거가 협상 역학이 아니라 *사용자의 중간 변경 요청*(날짜·장소 변경 등)임이 확인되면서, 로컬 데이터 재확보 문제와 분산 세션 갱신 문제가 분리됨. 본 문서는 후자를 다룸.
> **대응 NFR(예상)**: NFR-MAF-10 · 11 (일관성) ↔ NFR-MAF-02 · 04 (지연·품질) 정면 충돌
> **관계 문서**: [DP04-다자간 네고시에이션 복구(제자리복구)](./DP04-다자간%20네고시에이션%20복구(제자리복구).md) — 경계 확인 필요 (§5)

---

## 1. 풀고자 하는 문제

전제 모델([새제안]DP01 v2 계열): 각 단말이 로컬에서 후보 집합을 생성·점수화하고, 이를 공유한 뒤 정족수 기반 결정론적 알고리즘으로 합의한다.

이 구조에서 협상 진행 도중 사용자가 입력을 개정하면(예: "1월 1일 말고 1월 2일로", "예산 낮춰줘"), 개정의 진짜 비용은 로컬 재조회·재계산이 아니다. **내 후보 집합은 이미 N명에게 공유되어 집계에 반영되어 있으므로**, 비용의 본체는 재공유·재집계다. 본 DP는 이 분산 갱신을 어떻게 수행할 것인가를 결정한다.

- 로컬 재계산은 결정론적이고 저비용 → 결정거리가 아님.
- 분산 갱신은 일관성(NFR-MAF-10/11)과 지연·반응성(NFR-MAF-02/04)이 정면 충돌 → 본 DP의 결정축.

## 2. 후보안

### 후보 A — 세대 교체 (Epoch Restart)

변경 발생 → 로컬 재계산 → "새 세대(epoch) 시작" 선언 → 전원이 현재 집계 상태를 폐기하고 후보 집합을 재공유 → 결정론 집계 재실행.

- **구조**: 세대 번호를 가진 세션 상태 기계. 집계는 세대 단위로 무상태 — 한 세대 안에서 입력은 불변.
- **강점**: 일관성이 구조적으로 보장됨. DP04가 최대 위협으로 지목한 F5(입력 발산)의 표면이 최소화됨 — 세대 내 입력 불변이므로 "단말마다 다른 입력으로 각자 정상 결과를 내는" 상황 자체가 봉쇄됨.
- **약점**: 변경 1회마다 후보 집합 전체 × N명 재전송. 변경이 잦으면 협상이 반복 리셋되는 체감. 모바일 네트워크에서 전송 비용 큼.

### 후보 B — 개정 스트림 (Revision Propagation)

로컬에 후보·점수 계층까지 보관 → 변경 시 이전 제출분과의 차분(delta) 계산 → 개정 이벤트로 전파 → 각 단말이 증분 적용 후 재집계.

- **구조**: 이벤트 소싱 스타일. 후보 집합이 스냅샷이 아니라 개정 이력의 누적으로 정의됨. 버전 벡터 등 개정 순서 보장 장치 필요. DP04의 이벤트 로그·따라잡기 기계 위에 얹힘 ("복구 코드 경로를 따로 만들지 않는다"는 DP04 §4.1 원칙과 정합).
- **강점**: 전송량 최소, 반응 빠름, DP04 복구 경로와 코드 경로 통합.
- **약점**: F5가 정면으로 회귀 — 단말별 개정 적용 시점이 어긋나면 서로 다른 입력으로 집계함. "어느 개정까지 반영하고 집계를 확정하는가"라는 경계 합의 문제 발생(DP01의 "기다림의 끝을 누가 선언하는가" 문제의 재등장). 차분 산출을 위해 이전 제출분 보관 필요 → **메모리는 직관과 반대로 A보다 더 사용**.

## 3. 트레이드오프 요지

| 축 | A 세대 교체 | B 개정 스트림 |
|---|---|---|
| 일관성 (F5 방어) | ★★★ (구조적 봉쇄) | ★ (경계 합의 문제 회귀) |
| 네트워크 전송량 | ★ (전체 × N) | ★★★ (차분만) |
| 반응성 / 지연 | ★ (세대 리셋) | ★★★ |
| 로컬 메모리 | ★★★ (보관 불필요) | ★★ (이전 제출분 보관) |
| 단순성 | ★★★ | ★ (버전·순서 장치) |
| DP04 정합 | ★★ (별도 경로) | ★★★ (경로 통합) |

어느 쪽도 전 열을 이기지 못함 — 진성 트레이드오프.

## 4. 종속 결정 (이 fork의 귀결)

로컬 파이프라인 산출물(후보·점수)의 보관 여부는 독립 DP가 아니라 본 결정의 종속 결정임이 논의에서 확인됨:

- **A 채택 시**: 후보·점수 보관은 선택 사항 (어차피 재계산·전체 재공유).
- **B 채택 시**: 차분 계산 때문에 후보·점수 보관이 필수가 되며, 증분 재계산(의존성 추적)도 비로소 검토 가치가 생김.

## 5. 재개 시 열린 질문

1. **DP04와의 경계 확정.** DP04는 *장애로 인한* 상태 따라잡기, 본 DP는 *의도적 입력 개정*. 별개로 보이나, B안이 DP04의 이벤트 기계를 공유하므로 문서상 중복·충돌 없는 관계 절 명시 필요.
2. **개정 빈도의 실측.** 세션당 사용자 변경 횟수 분포. 극히 드물면(세션당 <1회) A의 전송 비용이 무의미해져 A로 수렴할 수 있음 — DP01의 "제약이 설계 공간을 좁히는" 검사와 동형.
3. **B의 경계 합의 메커니즘.** "개정 반영 마감"을 정책으로 사전 정의 가능한지(DP01 §2.5에서 경계 문제가 정책화 가능하다고 본 것과 연결).
4. **부분 개정의 의미론.** 사용자 변경이 후보 공간 자체를 바꾸는 경우(도메인 변경)와 점수만 바꾸는 경우(선호 변경)를 프로토콜에서 구분할지.
